# 用 Ensemble 委派工作

Ensemble 把任务交给**完整的外部 Harness 会话**（Cursor、Codex、Pi、Claude Code、OpenCode、DSH）。这些会话在后台独立运行，拥有自己的工具、文件访问和上下文；用户在 localhost 面板里能看到每个会话收到的任务、使用的模型、正在执行的步骤和消息，并可以随时直接纠正或停止。

你（主 Agent）留在原来的会话里。面板把主 Agent 显示为来源卡，把被委派的会话显示为执行节点。

## 什么时候委派

适合：边界清楚、能独立完成的工作——只读调研、代码审查、独立实现一个模块、写测试、让另一个模型给第二意见，或把几件互不依赖的事并行做。

不适合：几行就能改完的小事；需要和用户来回确认细节的事；依赖你当前对话里大量隐含上下文、很难写成自包含说明的事。这些自己做更快。

## 标准流程

1. **看谁可用**（不确定时）：调用 `harnesses`。`needs_setup` 表示用户还没登录或配置，把工具返回的提示原样告诉用户，重试没有用。它也标出不写 `model` 时实际用哪个模型：用户在 Ensemble 设置里为这个执行端指定了默认就用那个（会写明来由；指定的默认暂时用不了时也会说明改用了谁），所以没有特别理由不必自己写 `model`。用户定义了角色（`profile`）时也会在这里列出，见下文“用户定义的角色”一节。
2. **写完整的任务说明**：会话看不到当前对话。`task` 里写清目标、约束、验收标准和希望返回什么；用 `context` 传递具体文件路径（绝对路径）、代码片段或链接，而不是让它自己猜。要让它接着**另一个会话的产出**干活时，不要先 `read` 再自己转述，在 `context` 里放 `{ kind: "session", sessionId: "ses_…" }`，Ensemble 会把那个会话真实的最终回答原样交过去（见下文“把上一个会话的产出直接交给下一个”）。
3. **派发**：调用 `delegate`（有合适的、用户定义的角色时传 `profile`，见下文“用户定义的角色”），并用 `cwd` 传入你正在工作的项目目录（绝对路径）——并非所有宿主都会告诉 Ensemble 当前工作区，不传可能落在错误的目录；在插件安装目录里启动时，工具会直接要求你补上 `cwd`。它立即返回会话 id 和面板地址，会话已在后台工作（并发名额满时，回执首句会如实写成“它在排队，有名额时自动开始”），你不需要轮询。互不依赖的任务可以连续派发多次。
4. **打开面板**：把返回的面板地址在宿主自带的浏览器（侧栏或内置浏览器）里打开，让用户能看到。没有浏览器工具时，调用 `open_panel` 并设置 `where="system_browser"`。
5. **等待结果**：调用 `wait`，它在会话完成、用户介入，或某个会话**新出现值得留意的情况**时立即返回（见下文“值得留意的提示”）；会话**提出问题**时也会返回（见下文“会话的提问”）。不要反复调用 `status` 轮询。`wait` 超时只代表还没有结束（可能在排队、启动、运行或待命），可以再等一次，或先做别的事。
6. **取回结果**：用 `read` 读最终答案（`view="result"`，默认）或完整过程记录（`view="transcript"`）。只想知道“哪步报错了”“跑过哪些命令”“改了哪些文件”时，不必拉整段过程记录，用 `view="errors"` / `"commands"` / `"files"`；并行派了多个会话、都结束之后，用一次 `read` 传 `sessionIds` 收回全部结论，不要逐个读（细节见下文“精细读取与批量读取”）。汇报时只陈述会话实际做过的事，不要补写它没有做的步骤。
7. **纠偏或继续**：用 `send`。空闲时它开启同一会话的下一次运行；运行中能否即时纠偏取决于执行端：Claude Code 与 DSH 的消息会排队到下一轮（DSH 一次只接受一条消息），OpenCode 的在下一个步骤边界（当前工具调用结束后）才进入对话。结果会如实说明消息是“已生效”、“只交给了执行端”还是“已排队”，照实转述，不要夸大。
8. **停止**：`cancel` 中断当前运行（会话保留，可再 `send`）；`cancel` 加 `stop=true` 关闭整个会话。

## 用户定义的角色（`profile`）

用户可以在 Ensemble 设置的「角色」里，把一组（执行端、模型、推理强度、访问权限）起一个短名字，比如 `verify`。有角色时，`harnesses` 的末尾会逐行列出它们：每行写着这个角色固定了什么，以及 `usable now` 或 `NOT usable now`（附原因）。没有定义角色时 `harnesses` 里什么也不会多出来，这一节与你无关。

- **什么时候用**：用户点名要某个角色，或 `harnesses` 列出的角色里有一个的名字明显对应这次的活（例如 `verify` 对应独立验收），就传 `profile`，不要自己再挑执行端与模型——那是用户事先定好的选择，换模型世代、换执行端时他只改一次设置。用户这一次明确指定了执行端或模型，按用户说的来。名字只能取 `harnesses` 里列出的，不要编、不要猜。
- **怎么用**：`delegate` 传 `profile="verify"`，`harness` 可以不写。`task`、`context`、`cwd` 照常写，角色不替你写任务说明。
- **覆盖**：你显式传的 `harness`、`model`、`effort`、`access` 按字段覆盖角色；换了 `harness` 时角色的模型与推理强度不会被带过去（它们属于原来的执行端），换了 `model` 时角色的推理强度同样不带；没覆盖的仍按角色。没有理由就别覆盖——尤其不要把角色定为 `read_only` 的活改成 `full`。
- **回执**：返回里多一行 `role "verify": …`，写明每个字段取自哪里（角色、你的调用、默认），以及角色里写了但这次没用上的取值。向用户转述时照这一行说实际用了什么，不要只说“用了 verify”。
- **被拒绝时**：角色不存在（返回 `There is no role named …`，并列出用户定义过的名字），或此刻用不了（返回 `Role "…" cannot be used …`，写明原因），Ensemble 不会退回默认值悄悄派发。不要换个写法反复重试同一个角色，也不要在用户不知情时改用别的执行端或模型：把原因告诉用户（多半要他到设置的「角色」里改，或在「执行端」里开放模型）；用户同意换、或者本来就没有限定，再显式传 `harness`（与 `model`）重新派发。标着 `NOT usable now` 的角色先别选。设置文件整个读不出来是例外：这时 `harnesses` 的角色一栏写 `Roles: unavailable — …`，所有委派都被拒绝（带 `profile` 的返回 `Role "…" cannot be resolved: …`，不带的返回 `Ensemble could not read settings.json. …`），显式传 `harness` 也一样；换写法绕不过去，把原因告诉用户，请他恢复设置文件并重启 Ensemble。

## 宿主没告诉 Ensemble 当前是哪个对话时：传 `conversationId`

有的宿主（例如 **Cursor IDE**：所有对话共用同一个插件进程）不告诉 Ensemble 一次工具调用来自哪个对话。这时 Ensemble 只能把这个插件进程上所有对话派发的任务并成同一个 Main Agent：`status` 会把别的对话的会话也当成你的，用户对某个会话的介入通知也可能被另一个对话先收走。

- 你的上下文里能看到当前对话（Agent）的 UUID 时，在**每一次** Ensemble 工具调用（`delegate`、`status`、`wait`、`read`、`send`、`cancel`、`open_panel`、`harnesses`）里把它原样作为 `conversationId` 传入；同一个对话每次传同一个值。
- **原样抄写，不要编造、不要猜。** 看不到就不传；不要拿会话 id（`ses_…`）、任务标题、时间戳或自己生成的值顶替。
- 宿主自己交出了对话标识时（例如 Codex、Claude Code），这个参数会被忽略，不必特意去找。
- 页面上这个标识会标注为“由 Agent 自报”，因为 Ensemble 无法核对它。传错（比如抄成别的对话的 UUID）会让你的会话并进那个对话的来源；每次传不同的值，每个值各成一个来源；不传则回到按插件进程合并的老样子——仍然能用，只是分不清对话。
- 没传 `conversationId` 又开着多个对话时，`status` / `wait` 的末尾可能出现一句提示，说这个来源可能被多个对话共用（英文原文是 “it may be shared by several conversations”）：照提示显式传 `sessionIds`，或补上 `conversationId`。`wait` 不传 `sessionIds` 时，输出里会先写它实际在等哪几个会话，先核对是不是你自己派的。

## 不要重复派发同一份任务

- 服务端会挡掉短时间内的重复委派：同一个对话在 2 分钟内再次提交本质上相同的 `delegate`（执行端、目录、任务原文、模型与档位、访问级别、上下文、上级会话都一样；标题不算），不会新建会话，而是返回已经存在的那一个。
- 命中时返回文本以 `Not delegated again` 开头，写明那个会话是几秒前创建的、当前处于什么阶段；`structuredContent` 里带 `duplicate: true` 和那个会话真实的 `sessionId`、`runId`、`panelUrl`。把它当作你要的会话：用 `wait` 等它，或在它已完成时用 `read` 取结果；**不要**再调用一次 `delegate`。命中的会话可能已经被归档（回执里有一行 `archived:`），命中本身不会取消它的归档，直接 `read` 取结果即可。
- 失败、已取消、已关闭的会话不算，所以失败后立刻重试照常新建。
- 只有确实要第二个一模一样的会话时（例如对同一份任务并行起多个同款 worker）才传 `allowDuplicate: true`。想让新会话做的事有一点不同，直接把任务写得不同即可，不需要这个参数。

## 把上一个会话的产出直接交给下一个

新会话要用另一个会话的产出时（审阅它写的实现、接着它的调研结论继续、对比两路方案），**不要**先 `read` 取回结果、再用自己的话转述进新任务：转述会丢字、会改写，还白占你的上下文。直接引用：

```
delegate({
  harness: "codex",
  task: "Review the parser change for edge cases and report what is wrong. Do not edit files.",
  context: [{ kind: "session", sessionId: "ses_a", include: ["result", "files"], note: "Only the parser changes matter." }],
  follows: "ses_a",
})
```

- `include` 省略 = 只要最终回答（`result`）；`files` 是它改过的文件清单（路径与变更类型，没有 diff），`error` 是它最后一次失败的错误码与消息；`note` 是你对这次引用的一句说明，原样放在块里。
- Ensemble 在你派发的那一刻读上游会话**自己的事件记录**，把原文逐字放进新会话的提示（块里带着出处：会话、执行端与模型、取样时刻、当时的阶段）；你在回执里看不到这段原文，它在新会话的提示里，面板的“传入的上下文”里能展开看。任务说明仍要写清新会话拿它做什么、验收标准是什么：引用只负责“交什么”，不替你写“做什么”。
- **上游必须已经停下。** 它还在进行（启动中、排队、运行中）时，`delegate` 会被拒绝，错误里点名会话与阶段：先用 `wait` 等它结束，再用同样的 `context` 重新派发。引用不存在的会话也会被拒绝（用 `status` 查有效的编号）。已结束、失败、已取消、已停止、待命的会话都可以引用。
- **看回执，不要想当然。** 回执里每个被引用的会话占一行，写明取自第几次运行、多少字符、有没有被截断、几个路径、哪次运行的什么错误。看到 `none`（没有结果、没有文件改动、没有失败记录）、`not marked final`（它从没把任何消息标为最终回答，交过去的只是它写的最后一条）或 `truncated`（超长，只交了开头）时，如实告诉用户，必要时对上游 `read` 核对，不要说成“已完整交接”。过程说明（commentary）从不当作结果交出去。
- **只引用真正依赖的会话。** 一次最多 10 个不同的会话；一个结果超过 4 万字符会被截断（块里写明了），含引用的整份提示超过 20 万字符会被拒绝。内容很长时，用 `include` 只要需要的部分，或让上游先把摘要写进文件、再用 `file` 上下文指过去。
- 引用**不会自己连线**：要在画布上画出承接关系，同时传 `follows`（见下一节）。同一个会话在 `context` 里写几次会合并成一条。
- 旧版 Ensemble 服务不认识 `session` 条目：`delegate` 会在发出之前就告诉你“服务比插件旧”，请用户重启服务；急用时先 `read` 取回，再用 `text` 上下文传。其余四种上下文（`text`、`file`、`snippet`、`url`）不受影响。

## 同一任务按交接顺序连线

- 下一阶段要用上一阶段的产出时，等上一阶段结束，用 `context` 里的 `session` 条目把它的产出原样交给新会话（不是自己取回再转述，见上一节），再用 `follows` 把新会话挂在交出产出的会话下，并把验收标准写进任务说明。例如 `Main Agent → Sonnet 实现 → DeepSeek 独立验收`。同一项工作的阶段沿一条任务链接续；没有依赖的并行工作保留为并列分支。引用本身不画线：连线只由 `follows` 决定。
- 画布用 `parentSessionId` 连线。要把新会话接在某个已有会话后面（例如修复会话接在代码审阅会话后面），派发时给 `delegate` 传 `follows="ses_…"`（会话 id 可从 `status` 取得）：它优先于自动推断，不改变“谁发起了这次委派”，发起端仍记录实际调用者。接续的链条计入嵌套上限（2 层），超出时报错并说明该改接到链上更靠前的会话。会话 id 不存在时直接报错，不会悄悄落到别处。
- **汇聚（多个上级）**：新会话确实依赖几个会话各自的结果时（例如两路并行的实现做完后，派一个统一的验收或修复会话），`follows` 传一组 id：`follows=["ses_a","ses_b"]`（最多 8 个，超过 8 个会被工具参数校验直接拒绝）；画布上会从每个上级各连一条线。层数取最长的那条上级链，仍计入嵌套上限；不存在的 id 会一次全部报出。只有真有依赖时才这样连：几个会话互不依赖、只是同一批派发的，就各自独立派发，不要为了画线硬连在一起。旧服务（`features` 里没有 `multi-parent`）只会记录第一个上级，`delegate` 的返回里会写明，这时不要指望画布上有其余的连线。
- 不传 `follows` 时，二次委派由桥从 `ENSEMBLE_PARENT_SESSION` 或原生会话标识查找父会话（Codex、Pi、Claude Code、OpenCode、DSH 执行端会自动写入；Cursor 执行端不会，需要连线时请直接用 `follows`）。
- 派发后核对返回里的 `follows session …`（传了多个时是 `follows N sessions: id “标题”, …`，`delegate` 的返回里上级只在这一行说一次）/ `nested under session …` 提示；会话详情里不显示单个上级，只有多个上级时才另有一行 `follows: …`（`wait` 给出的详情与 `status` 的 `detail=true` 里有它），所以单个上级要看上面这两种提示，或在网页里看连线（`read` 的 `view="report"` 的概览表里也有一行 `Parent session`）。宿主无法传递父关系又不适合用 `follows` 时，说明实际限制，不用标题或虚构的发起端代替连线。

## 权限与访问级别

- 被委派的会话**默认就是 Full Access**：没有沙箱，也没有需要任何人批准的闸门，不会停下来等授权。所以任务说明里要把边界写清楚（可以改哪些文件、不能碰什么），因为没有人会在中途替你把关。
- 只有两个级别：`full`（默认）和 `read_only`。只读调研和审查请显式用 `read_only`，写入会直接失败而不是弹出授权。用户定义的角色可以预先写明访问级别（例如 `verify` 固定为 `read_only`），那只是默认值：你显式传 `access` 会覆盖它，所以别为了图省事把角色定好的 `read_only` 改成 `full`。
- 先用 `harnesses` 看每个执行端真正能强制哪些级别；不能强制的级别会被拒绝，而不是悄悄降级。Claude Code 与 OpenCode 的只读依靠工具层限制（工具白名单 / 会话权限规则），并非操作系统沙箱；DSH 的只读由它自己的 read-only 权限模式强制（写入工具被拒绝，shell 命令在它的系统沙箱里运行）。
- 有的宿主（例如 Codex 的默认策略）会在你第一次调用 `delegate` 时先请求用户批准，这是宿主自己的授权，等用户处理即可。若宿主因批准策略为 never 而直接拒绝了调用，如实告诉用户，不要换个说法反复重试。

## 并行时避免冲突

- 同时派发多个会负责写入的会话时，给它们划分互不重叠的文件或目录，并在任务说明里写明。
- 两个会话改同一批文件会互相覆盖；需要对比方案时让它们都用 `read_only`，或各自在不同目录里产出。
- 被委派的会话可以再委派，但有深度上限；超出时工具会返回 `depth_exceeded`，改为自己完成或把结果交回。

## 用户的直接介入

用户可以在面板里直接给子会话发消息、中断或停止它。这些操作会在你下一次调用任一 Ensemble 工具时，附在返回内容末尾（以 “While you were away, the user acted directly on delegated sessions” 开头），列出是哪个会话、做了什么、写了什么。看到后：

- 采纳用户的纠正，不要按原计划重复被纠正过的做法；
- 不要把用户的介入当成失败，也不要撤销用户已经做的事。

## 值得留意的提示（`attention:`）

`status` 和 `wait` 在某个**仍在进行**的会话下面，可能多出几行以 `attention:` 开头的话。它们是 Ensemble 从事件流里算出的**事实**，不是“卡住了”的判决；怎么处理由你决定。`wait` 在出现**新的**提示时会提前返回（返回里标明 `attention`），已经在你开始等之前就存在的提示不会再次打断你，但仍会列在对应会话下面。不想被打断时给 `wait` 传 `attention=false`。

| 提示 | 含义 | 建议 |
| --- | --- | --- |
| 一段时间没有任何事件，也没有进行中的工具调用（约 4 分钟） | 会话既没有产出，也没有在等一个长命令 | 用 `read`（`view="transcript"`；之前读过的话带上 `afterSeq`，只看那之后的进展）看它最后在做什么，再决定是否 `send` 一句、继续等或 `cancel` |
| 有一个工具调用在进行，且很久没有任何事件（约 10 分钟） | 可能是长时间的构建或测试（正常），也可能是挂住的命令 | 看这个工具是什么（是 shell 命令的话，`read` 的 `view="commands"` 会写明它已经跑了多久）；是编译 / 测试就继续等 |
| 这次运行已持续很久（约 60 分钟） | 只是时长，不代表有问题 | 与你预期的工作量对照 |
| 某个文件也被另一个**正在运行**的会话写过（近 10 分钟内） | 并发改同一个文件可能互相覆盖 | 看两边在改什么；必要时让其中一个先停，或重新划分文件范围 |
| 一条补充消息很久还停在“已记录”或“已交给执行端” | 执行端没有确认它生效（运行中纠偏取决于执行端） | 不要当作已生效；看会话是否还在响应，必要时重发或改用排队 |

约定：不要因为一条提示就自动 `cancel`；先读过程记录再动手。会话**已经结束或失败**不会出现在 `attention:` 里，那些由 `wait` 的“已结束”结果和会话状态本身给出。文件重叠只统计执行端明确报告的文件变更（通过 shell 写入的文件看不到）；数字阈值是固定的，目前不能配置。

## 会话的提问（`question`）

被委派的会话遇到需求歧义时，可能停下来**问你一个问题**（Codex 的 `request_user_input` 工具——它在 Codex app-server 协议里的方法名是 `item/tool/requestUserInput`，仓库的手册里写的是这个名字，指的是同一件事；OpenCode 的 `question` 工具）。这不是授权：授权请求仍由 Ensemble 当场应答，会话从不等人放行；提问是会话在等一个**答案**。

- `wait` 在**第一次**告诉你有新提问时提前返回（即使传了 `attention=false`），返回里有一个 `question` 块：提问编号、问题原文、可选项和回复方式。`status` 与 `read` 在它待回答期间一直显示这个块；已经告诉过你的提问不会再次打断 `wait`。
- **回答**：`send` 传 `questionId` 加 `answer`（提问里只有一个问题）或 `answers`（有多个问题时，每个一项、按顺序；多选用标签数组），不需要 `text`。选项必须取给出的标签；问题写明“or write your own”才可以自己写。
- **不回答**：`send` 传 `questionId` 加 `decline=true`（`text` 可作为给会话的一句备注）。会话会被告知你选择不回答，请它自行做合理假设并继续。
- 不确定怎么答时，先 `read` 看它为什么问。用户也可能已在面板里回答了，这时你再回答会收到“已回答”的冲突提示，以面板里的为准。
- 回答送到时会话已经不再等（回合结束、被取消、会话已关闭）会如实告诉你回答没有生效；提问记为过期。没人回答的提问，约 60 分钟后被关闭，会话按自己的假设继续（该时限目前是固定值）。
- 涉及密钥的提问（例如要一个令牌）不会转交：会话被告知走不通，请它换办法。
- 目前只有 Codex 与 OpenCode 的提问会转交，且只用假的执行端验证过，没有在真实的 Codex / OpenCode 上触发过；其余执行端的提问行为见仓库的手册（https://github.com/JiangYain/Ensemble/blob/main/docs/manual.zh-CN.md）。`harnesses` 的 `can:` 一行会写明某个执行端是否转交（`question relay`）。

## 让宿主在后台盯着会话（看门狗脚本）

`wait` 是你主动去等。想让宿主在**后台**盯着、有事再叫你回来，而不是自己反复调用 `wait`，用随插件分发的脚本：本 Skill 目录下的 `scripts/watch.mjs`。它对服务只读：只向本机的 Ensemble 服务发 GET 请求，从不取消、发消息或改动任何会话，只依赖 Node 自带的模块；它自己唯一会写的是你用 `--state` 点名的那个状态文件。

- **怎么跑（首选 `--wake`，只起一个）**：把 `node <本 Skill 目录>/scripts/watch.mjs --wake …` 作为宿主的**后台命令**启动，不要阻塞等它。一个就够，不必给每个会话各起一个：它盯着所有尚未结束的会话（还没有运行过的待命会话除外）、之后新建的，以及被 `send` 续跑起来的；当前没有可盯的会话时它不退出，等着。出现 `[DONE]`（会话结束）或 `[ALERT]`（值得看一眼）时，它先打印这一行，再等 `--wake-batch` 秒（默认 3，0 为立刻）把同一时刻到的几条一并带上，最后补一行 `[WAKE] …` 摘要，然后**以退出码 10 退出**——这就是它在叫你：宿主只在后台命令**退出**时才会叫醒空闲的主 Agent（在 Cursor 里实测，输出匹配的通知没有把空闲的主 Agent 叫醒，命令退出才会；别的宿主没有验证过）。被叫醒后先处理它说的事（`[DONE]` 去 `read`，`[ALERT]` 先读依据再决定），然后**用同样的参数把它重新启动**，进入下一轮盯梢。`[INFO]`（包括会话被取消或关闭）与 `[TICK]` 不会让它退出。`--wake` 不能与 `--forever`、`--once` 同用（参数错误，退出码 2）。
- **`--state <文件>`：重启不丢、不重复**。你处理的这段时间它没在运行，期间结束的会话不该丢，说过的事也不该重来。给它一个固定路径的状态文件（脚本自己读写，先写临时文件再改名；它所在的目录必须已经存在）：重启后它把“上次退出之后才结束、还没说过的”会话立刻报成 `[DONE]`，每个会话的事件接着上次读到的位置读，已经提醒过的事在 12 分钟内不重复。**用 `--wake` 就带上它**：没有它，重启后仍然成立的 `[ALERT]` 会立刻再说一遍、马上又把你叫醒。第一次文件还不存在，以“现在”为起点、不补报历史；文件读不出来或版本不认识就当没有（会说一声）。放在 Ensemble 的状态目录里（Windows 默认 `%LOCALAPPDATA%\Ensemble`，由 `ENSEMBLE_HOME` 决定），不要放进仓库；参数不同的看门狗各用各的文件。
- **`--origin`：只盯自己的**。同一个服务可能被多个 Main Agent（多个对话）共用，不加过滤的看门狗会被别人的会话叫醒。`--origin <来源 key>` 只盯这个来源名下的会话（可重复给多个），按会话自己的来源判断，别的来源的会话完全不读。来源 key 在工具的输出里不会出现，所以更省事的是 `--origin-of ses_…`：给一个你派发过的会话 id，脚本取那个会话的来源（该会话要仍在服务的会话列表里，已归档的不行）。两者都不能和点名的会话 id 同用。
- **启动示例（Windows / PowerShell）**：`node "<本 Skill 目录>\scripts\watch.mjs" --wake --tick 0 --state "$env:LOCALAPPDATA\Ensemble\watch-state.json" --origin-of ses_…`。`--tick 0` 关掉周期小结（唤醒式用不着）。退出码：0 盯着的会话都结束了（或 `--once`）、2 参数不对，或点名的会话一个都不存在、3 服务连不上、10 唤醒（有事要处理）。
- **不用 `--wake` 的旧用法**：`node <本 Skill 目录>/scripts/watch.mjs ses_… ses_…`，作为后台命令常驻、有事打印一行；不带会话 id 时盯着所有尚未结束的会话，盯着的会话都结束后它自己退出（`--forever` 常驻）。只有宿主确实会因输出匹配叫醒空闲的你时才值得这样用（例如让宿主在输出匹配 `\[(ALERT|DONE)\]` 时通知你；`[TICK]` 与 `[INFO]` 不必打断你）。宿主没有“后台命令退出或有输出就通知”的机制时，继续用 `wait`，不要自己写轮询循环。
- **输出**：每行 `HH:MM:SS [标签] "会话标题" (会话 id): 事实`。`[ALERT]` 值得现在去看；`[DONE]` 会话已结束，用 `read` 取结果；`[INFO]` 知道就好；`[TICK]` 周期小结（`--tick <分钟>`，默认 5，0 关闭）。
- **什么会触发 ALERT**：服务端算好的“值得留意”（和“值得留意的提示”一节是同一份，口径一致，脚本不另算）；会话在等一个提问的答案（见上一节“会话的提问”）时也出一行，只写第一个问题的一行摘要（最多约 160 个字符，还有更多问题时带 `(+N more)`），回复方式不在这一行里，要用 `status` 看完整的提问；连续 4 次工具调用失败；同一个调用在最近 8 次已结束的调用里出现至少 4 次、其中至少 2 次失败；排队超过 25 分钟而服务仍有空闲名额；会话失败或丢失。文件冲突类报错（`ftruncate`、`EBUSY`、`string to replace not found` 等）只记为 `[INFO]`；会话被取消或关闭也只是 `[INFO]`。
- **不会刷屏**：同一件事持续存在时，隔 12 分钟才再提醒一次；新出现的事马上说。
- **项目自己的规矩默认不检查**。需要时拷一份 `scripts/watch.rules.example.json` 改成自己的（对 shell 命令和文件变更各写若干条正则），用 `--rules 文件` 传入；命中就是 `[ALERT]`。
- **它没有的**：不扫描残留进程，不校验文件完整性，不替你判断对错。和 `attention:` 一样，输出的是有事件依据的事实；不要因为一行输出就自动 `cancel`，先 `read` 再决定。
- **其他**：服务连续两次读不到会说一声；持续 `--gone-after` 分钟（默认 10）就退出，退出码 3。`--once` 只看一遍就走，`--interval <秒>` 调整间隔（默认 30），`--help` 看全部选项。它按 `ENSEMBLE_HOME`（与插件同一套规则）找服务。

## 精细读取与批量读取（`read`）

为了回答一个具体的问题而拉整段过程记录，既费 token 又容易漏看。按问题选视角：

- **刚才哪步报错了**：`view="errors"`。只列真实的失败——失败的工具调用（带命令、退出码与输出末尾几行）、警告与错误级别的提示、失败的运行、没送达的消息；最新的排在最前面，每条带第几轮、事件号与时间。“没有结束事件”的工具调用不算失败，只在末尾另说一行。没有失败时会写明“没有记录到错误”。
- **它跑了哪些命令**：`view="commands"`。列出 shell 类的调用（序号、命令、状态、退出码、耗时），失败的带输出末尾几行。分类不是 shell 的调用（例如 OpenCode 代码模式的 `execute`、Claude Code 的 `BashOutput`）不在其中；怀疑漏了就看 `view="transcript"`。
- **改了哪些文件**：`view="files"`。每个路径一条（创建 / 修改 / 删除、增删行数），只有清单没有 diff；shell 命令里做的改动不在其中。
- **只看某一轮**：任何视角都能加 `runIndex`（从 1 数起；会话空闲时每条 `send` 开始新的一轮）。超出范围会报错并写明有效范围，不会悄悄读成整段。
- **只看新进展**：单个会话的 `read` 末尾有一行 `cursor: #N`（结构化结果里的 `seq` 是同一个数）。下次带 `afterSeq=N`，只会得到之后**新出现或有变化**的内容：更早开始、之后才结束的工具调用会带着最新状态再出现一次，还在输出的文字会标明没写完。没有新事件时只回一行 `No new events since #N.` 加状态行。内容太多时先给最早的一批，末尾的游标指向这一批的结尾，照着它读下一批。游标只对读出它的那个会话有效。盯进展仍然用 `wait`（或看门狗脚本），不要靠反复 `read` 轮询；`afterSeq` 用在你被叫回来之后，补读自上次以来发生的事。
- **并行的会话都结束之后**：`read` 传 `sessionIds`（最多 20 个）一次收回全部。每个会话一块，按你传入的顺序：状态、耗时、工具调用与失败数、改动文件数与前几个路径、令牌与费用（费用没有上报就写“未上报”，不是 $0；用量是各轮合计）、最终回答的开头。没结束的会话按局面分四种写法（措辞是英文）：运行中的，结论一节标 `latest output so far (not final)`、末尾写 `still running — not final`；这一轮已交给执行端启动、还没开始的，写 `starting — not final`；前一轮已结束、后续一轮在排队的，结论取自前一轮并写明是第几轮，末尾写 `next run queued — not started yet`；一轮都没跑过的（含第一轮还在排队），写 `conclusion: none — the session has not run yet`，不附“仍在进行”。总字数用 `maxChars` 控制；某个结论被截断时，对那个会话单独 `read` 取完整答案。某个会话读不到只影响它自己那一块。批量模式不能与 `sessionId`、其他 `view`、`runIndex`、`afterSeq` 合用。`wait` 报告“所有会话都已结束”时，末尾会提示这个用法。
- **要一份能存档、贴进 PR 说明或发给别人的复盘**：`view="report"` 返回一份 Markdown 报告（委派原文、关键步骤、改动文件清单、最终回答、用量）；`scope="tree"` 把它名下委派出去的整棵任务树放进同一份，`detail="full"` 另带工具的输入与输出。内容只来自真实记录的事件，不含推理，也**不做脱敏**——命令、路径、消息原样引用，转给别人之前先自己查一遍有没有密钥；它不能与 `runIndex`、`afterSeq`、`sessionIds` 合用，也不会改动任何会话记录。

这些视角里的内容都来自执行端真实上报的事件，不是概括；汇报时仍然只陈述事件里有的。

## 诚实地汇报

- 透明度来自执行端真实提供的事件：消息、工具调用、命令、文件变更、输出和状态。不要声称拿到了模型内部的完整思考过程。
- 不同执行端的能力不同（中途纠正、中断、继续的支持程度各异）。工具返回里写明了差异，按它说的告诉用户。
- 会话失败时，用 `read` 看错误码和过程（`view="errors"` 直接列出错误与失败的调用），再决定重试、换执行端还是自己接手；把真实原因告诉用户。

## 工具速查

| 工具 | 用途 |
| --- | --- |
| `harnesses` | 哪些执行端可用、模型列表、哪些能力经过验证；用户定义了角色时，末尾列出角色及此刻能不能用 |
| `delegate` | 派发任务，立即返回会话 id 与面板地址；`profile="verify"` 按用户定义的角色派发（显式参数覆盖它）；`follows="ses_…"` 把它接在某个已有会话后面（传一组 id 表示汇聚：它依赖这几个会话的结果）；`context` 里的 `{ kind: "session", sessionId }` 把另一个已结束会话的最终回答（`include` 可加改动文件与最后一次失败）原样交给新会话，不必先 `read` 再转述 |
| `wait` | 阻塞等待完成 / 用户介入 / 新的值得留意的提示 / 会话提出的问题（最长约 45 秒） |
| `status` | 列出会话与进度（优先用 `wait`，不要轮询）。默认不列**已归档**的会话（用户或留存策略移出默认视图的已结束会话，记录都在，`read` 照常能读），末尾一行会写明略去了几个；要列出它们传 `includeArchived=true`，点名的 `sessionIds` 一律返回（标 `(archived)`） |
| `read` | 读结果或过程记录；`view` 可只看失败 / 命令 / 改动文件，`afterSeq` 只读新进展，`sessionIds` 一次收回多个会话，`view="report"` 导出 Markdown 复盘报告 |
| `send` | 中途纠正或继续同一会话；带 `questionId` 时是回答（`answer` / `answers`）或不回答（`decline=true`）会话的提问 |
| `cancel` | 中断运行，或 `stop=true` 关闭会话 |
| `open_panel` | 取得或打开面板地址 |

以上每个工具都接受可选参数 `conversationId`，用法见“宿主没告诉 Ensemble 当前是哪个对话时”一节。
