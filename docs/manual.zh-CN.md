# Ensemble 手册

> 这是 Ensemble 的详细手册。仓库首页的 [README](../README.md) 只放了让 Agent 安装它的提示词；每个功能怎么用、每个执行端实际验证到了什么程度、已知的限制，都在这里。
> 手册区分“在真实环境里验证过”和“只对着模拟的执行端、或只读过代码”两类说法，后者会明说。文中“你已确认”“由你决定”之类的话记录的是项目维护者当时的决定，“用户”指提出需求的人，读的时候当作历史记录。

把工作委派给**完整的外部 Harness 会话**（Cursor、Codex、Pi、Claude Code、OpenCode、DSH），并在 localhost 页面里实时观察、纠偏和接管它们。

Ensemble 是一个 [Agent Plugin](https://agent-plugins.org/)：由 MCP 服务、一个按需启动的本地服务和一个网页组成。你（或当前的主 Agent）在 Codex、Cursor 等宿主里调用它派发任务；每个被派发的会话都是一个真正的 Harness 会话——有自己的工具、文件访问和上下文，不是一次 LLM 请求。主会话继续留在它原来的界面里，Ensemble 页面只展示被委派出去的那些会话。

## 它做什么

- **节点就是被委派的会话。** 发起端（例如“由 Codex 的某个会话派发”）只是来源信息；画布上每个主要节点都是一个完整的 Harness 会话。
- **页面展示真实发生的事。** 收到的任务原文、传入的上下文、执行端、模型、推理强度、工作目录、访问级别、正在执行的步骤、工具调用、命令、文件变更、输出、用量和运行状态。步骤只来自执行端的 SDK / 控制接口实际给出的事件，不由 Ensemble 编写叙述；也不声称能拿到模型内部完整的思考过程。
- **你可以介入。** 在页面里直接给子会话发送纠正、中断当前运行、停止会话。你的介入会记录下来，并在主 Agent 下一次调用任一 Ensemble 工具时同步给它。被委派的会话默认是 Full Access，不会停下来等你批准什么——要介入的是方向，不是授权。
- **如实区分投递状态。** 一条消息可能是“已记录”、“已交给执行端”、“已排队（由 Ensemble 或由执行端）”、“已生效”或“未送达”。执行端没有给出证据时，不会写成已生效。
- **后台持续收集。** `delegate` 立即返回会话 id 和面板地址，会话在后台继续；刷新或关闭网页不会终止正在执行的任务。
- **同一套状态，多个入口。** MCP 桥和网页连接同一个本地服务；从不同宿主发起的委派出现在同一个页面里。

## 快速开始

前置：Node.js ≥ 22.13；至少装好一个执行端——[Codex CLI](https://github.com/openai/codex)、Pi（`npm install -g @earendil-works/pi-coding-agent`）、[Claude Code](https://code.claude.com/docs/en/setup)、[OpenCode](https://github.com/anomalyco/opencode)（`npm install -g @opencode/cli`，需要 2.x）、[DSH](https://www.npmjs.com/package/@deepseek-ai/dsh)（DeepSeek Harness，`npm install -g @deepseek-ai/dsh@latest`；目前只发布了预发布版本，所以必须带 `@latest`；包声明需要 Node ≥ 24.9.0，在本机 Node 22.22.2 上实测可用，但那不是官方支持的组合，要符合官方要求请自行升级 Node）或 Cursor SDK（见下）。Claude Code、OpenCode 与 DSH 需先完成它们自身的登录或模型配置（DSH：在 `dsh web` 的 Settings → Models 里填 DeepSeek API Key，或在启动服务的环境里设 `DEEPSEEK_API_KEY`；没配时第一轮会以 `auth_failed` 失败，dsh 的原文会说明怎么补）。

```powershell
# 1. 看看这台机器上哪些执行端可用，以及缺什么（npx 会把包下载到 npm 缓存里运行，不用先克隆仓库）
npx -y ensemble-plugin@latest doctor

# 2. 把插件装到宿主里。install 会修改用户级配置，所以默认只展示计划；确认后加 --yes
npx -y ensemble-plugin@latest install codex --dry-run
npx -y ensemble-plugin@latest install codex --yes
npx -y ensemble-plugin@latest install cursor --yes        # 在 Cursor 里随后执行 “Reload Window”

# 3. 使用 Cursor 作为执行端时：安装 @cursor/sdk（许可证不允许随插件分发），再登录
npx -y ensemble-plugin@latest install sdk --yes
npx -y ensemble-plugin@latest cursor-login
```

`npx -y ensemble-plugin@latest <命令>` 也可以换成先 `npm install -g ensemble-plugin`，之后直接写 `ensemble <命令>`；从源码克隆运行时写 `node dist/ensemble.mjs <命令>`，本手册后文多用这种写法，意思相同。插件装好之后，宿主启动 MCP 桥用的是复制到宿主插件目录里的那份，不再依赖 npm 缓存或 `npx` 的临时目录（见“npm 包 `ensemble-plugin`”）。

然后在 Codex 或 Cursor 里直接说：

> 用 Ensemble 把这个重构任务同时派给 Cursor 和 Pi，各自独立完成后对比结果。

主 Agent 调用 `delegate` 后会拿到面板地址（默认 `http://127.0.0.1:47821/`），并按 Skill 的指引在宿主自带的浏览器侧栏里打开它；也可以随时运行 `node dist/ensemble.mjs open`。设置 `ENSEMBLE_AUTO_OPEN=system` 可以让第一次委派自动打开系统浏览器。

默认端口被占用时，服务会换到空闲端口。用 `open_panel` 或 `node dist/ensemble.mjs open` 获取当前地址。同一个 `ENSEMBLE_HOME` 里的会话与已保存进度会在重启后读回。端口变化后，旧标签页仍指向旧地址，画布位置等浏览器偏好也按地址分别保存。

`dist/` 是随仓库提交的可运行产物（插件安装时不会执行构建）。改了源码之后用 `npm run build` 重新生成。

### install 到底改了什么

| 命令 | 写入位置 | 说明 |
| --- | --- | --- |
| `install codex` | `~/plugins/ensemble`、`~/.agents/plugins/marketplace.json`，再运行 `codex plugin add` | 只增删名为 `ensemble` 的市场条目，修改前备份；目录里有安装标记才会被覆盖或删除。Codex 会把插件缓存到自己的目录，升级需要重新运行（版本号变化时） |
| `install cursor` | `~/.cursor/plugins/local/ensemble` | Cursor 读 `.cursor-plugin/plugin.json` 与 `.mcp.json`（用 `${CLAUDE_PLUGIN_ROOT}`），所以包里同时带了两套文件 |
| `install sdk` | `<ENSEMBLE_HOME>/runtime`（npm 安装 `@cursor/sdk@1.3.1`） | 只影响 Ensemble 自己的目录 |
| `uninstall codex` / `cursor` | 撤销上面的写入 | 同样先展示计划 |

不想用 `install` 也可以手动操作：把本目录当作插件目录（根目录有 `plugin.json`、`mcp.json`、`skills/`），按宿主自己的方式添加即可。

## 页面里有什么

- **左侧栏与页头**：宽屏（≥ 860px）左边是工作空间栏：顶部是品牌字样和收起按钮，下面是“全部活跃”“全部空间”两个范围，再往下按 Main Agent 分“进行中（有会话在工作或有值得留意的）/ 最近（最多 5 个）/ 更早（默认折叠，选中的在里面时自动展开）”列出；每一项是宿主图标、名字、值得留意的标记，以及运行中的会话数（没有运行中的就是会话总数）。在会话页里，所属 Main Agent 下会展开它名下的会话（当前打开的那个带高亮；最多露出 6 个，多出的折成一行“另有 N 个会话”，点它回到该空间的概览）。栏底是设置，以及只在连接断开时才出现的连接状态。`Ctrl/⌘+B` 或栏头的按钮收起它：收起后没有顶栏，页面其余几何不变，只在左上角留一个只有图标的“展开侧栏”按钮（设置要展开后才能进；`Ctrl/⌘+K` 仍可切换空间）。窄屏（< 860px）没有这根栏，概览页顶部是一条极简顶栏——品牌字样、当前空间的快切入口和设置，会话页没有它。宽屏下页头第一行是当前空间的图标加名字（不是按钮；窄屏顶栏里当前空间的快切入口是带边框的按钮），右侧是视图操作区（“仅工作中”开关、画布 / 列表切换）。列表视图里会话的顺序只取决于创建时间、不随状态变化：顶层会话新的在上，子会话紧跟在各自的上级之后、旧的在上；正在工作的行有一层自行首向右渐隐的静态主题色浅染（画布上的节点已改成整卡里缓慢漂移的氤氲，列表行没有跟着流动），没有左侧色条。会话页侧栏里展开的兄弟会话用同一个顺序（同一个空间里侧栏的先后与列表视图一致；点另一行只换高亮，列表不动）；超过 6 个时露出的是其中连续的 6 行，当前会话在里面就不动，只有它落到这一段之外才滚动、且只滚到刚好能看见它，回到概览或换了 Main Agent 再进来则从最上面重新开始。
- **画布**：来源节点与会话节点之间用连线表示委派关系。连线接在两个节点相对的两条边上，默认是从来源的右缘到会话的左缘；节点被拖到另一侧时，连线随两端此刻的位置改从左缘或上下缘进出，始终是一条平缓的 S 形、不绕环，换边时平滑过渡，停在临界位置附近不会来回翻。节点边缘上的小方点只出现在真有连线接着的地方，运行中是主题色（与流动的点同色）、失败是红色。正在工作的节点（运行中、启动中、排队中）左缘没有色条，整张卡里是极淡的主题色氤氲（两团柔和的朱红，叠加后不超过约 5% 的透明度）：运行中的缓慢漂移，来回一趟二十多到三十多秒、每张卡的相位各不相同，启动中与排队中停在一帧，它画在文字与边框之下，不改布局与文字位置，系统设为“减弱动效”时静止；失败与已失联的节点保留 2px 红色左线；带“值得留意”且不在运行中的节点（启动中、排队中、待命）有 2px 琥珀左线，它在悬停、菜单打开、键盘聚焦、选中、拖动时都在，这些状态的边框与投影反馈与别的节点一样（运行中的节点没有琥珀线，“值得留意”只在头部标记）。会话节点的头部写它在哪个执行端上运行、用的什么模型（执行端的图标与名字，与 Main Agent 卡同一种写法，接着是模型名与推理档位，模拟执行只写“模拟执行”；右端是“值得留意”、待发消息或用户干预的标记与“···”菜单）；头部放不下时先省略模型名，再放不下就连同档位一起收起，模型与档位的全文也挂在正文头像的悬停提示上；正文左边是模型的头像（认得出的模型画家族标，认不出的画中性的闪光，模拟执行画烧瓶），右边两行依次是标题与状态（含已用时间）、最近动作。按住 Ctrl 或空格拖动画布可平移；按住 Shift 拖动可框选节点，Shift 点击可增减选中，Ctrl/⌘+A 全选，选中后可一起拖动，Esc 清除选择。选中两个及以上节点时，画布底部会出现对齐条：左对齐、水平居中、右对齐、顶对齐、垂直居中、底对齐，以及水平、垂直等距分布（至少选 3 个）；对齐以选中节点的整体外框为基准，选中的节点会一并固定在新位置，之后有新会话到达也不会被重新排走。拖动、方向键移动、对齐、分布和“重置节点布局”都可以用 Ctrl/⌘+Z 撤销、Ctrl/⌘+Shift+Z（或 Ctrl+Y）重做，最多保留 100 步；这份历史只存在当前页面里，刷新后清空（节点位置本身仍会保存）。聚焦节点后也可用 Shift+空格选择、方向键移动。新会话出现时，如果它的参照节点（同一上级下的上一个会话；第一个会话则是它的上级会话或来源卡）被你拖到过别处，它会紧挨着参照此刻的位置、从上游“长”出来，并避开已有的节点，不会掉到默认排布的最底下；这个位置会被记住，已有节点不会被挪动，也不进入撤销历史；一个节点都没拖过时，新会话也不会把已有的卡挤开，而是放进下一个空位（见下一条“画布排布与重置”），除了其中“仍会整体重排的几种情形”（有卡消失、上级变了、卡片换尺寸等），只有“重置节点布局”才让整张画布回到默认排布；被“隐藏未在工作的会话”收起后重新显示的会话不算新会话，回到它们本来的位置，不会被摆到别的节点旁边（没拖过的卡也一样回到收起之前的排布，只要那份排布还成立，见“画布排布与重置”里的“隐藏之后再显示”）。你正看着画布时新到的会话如果整个落在视口之外（刚打开、刷新、“重置节点布局”、重新显示被隐藏的会话、从聚焦页回到概览都不算新到），它所在的那一边会出现一枚小胶囊：箭头指向它，同一边来了几个就合成一枚并写出数量，悬停或聚焦时列出各自的标题与状态；点一下，相机沿用现有的弹簧平滑平移到最近的一个，不改缩放、不选中它、不抢键盘焦点，平移途中你一拖动画布就停在当前位置、把控制权还给你；节点露出任何一角、被删除、被隐藏或被点过之后提示就消失，画布不会自己跳。节点位置保存在当前浏览器中；画布右下角的比例尺提供缩放与“适应”（只动相机，不动节点），拖动过节点、或已有的会话卡与此刻的默认排布不一样时，比例尺里还会出现“重置节点布局”，规则见下一条“画布排布与重置”；工具栏还提供“隐藏未在工作的会话”开关（见“隐藏未在工作的会话”一条）与设置（最左边，只有一个齿轮图标；见“设置窗口”一条）。
- **画布排布与重置**：目标是把画布上画出来的全部节点（会话、来源卡，全部空间里还有 Folder / Git 卡；被“隐藏未在工作的会话”或“隐藏相关节点”收起的不算）整齐地、不重叠地放进取景区域（视口扣掉四周留白）：缩放上先守住（默认 100%，点“重置节点布局”时是你此刻的缩放），放不下才缩小。没有手动位置时自动排布，规则是：
  - **整体排一次，之后已有的卡原地不动**（用户的决定：已有卡片原地不动，新卡放进下一个空位，只有点“重置节点布局”才整体重排）：下面的规则在页面打开、刷新、换空间、点“重置节点布局”之后的第一次用来把整张画布排一次；之后新会话到达、取景区域变化（拖动窗口、折叠侧栏）时，已经画在那里的卡一张都不动，新卡放进下一个空位（见“新会话到达时”）。
  - **仍会整体重排的几种情形**（实现时为了让画面成立加的例外，不是用户明确要的，没有经过逐项确认）：有卡消失了（归档、删除，或被“隐藏未在工作的会话”“隐藏相关节点”收起；剩下的节点集合恰好与某份存下来的排布相同时，换回那一份、不整体重排；再显示时先试着还原，见“隐藏之后再显示”）、某个会话的上级变了（改挂、汇聚关系变化）、早就见过的卡重新出现而没有可还原的排布，或者取景区域的宽度越过 720px、卡片在紧凑与宽屏两套尺寸之间切换。越过 720px 的那一次重排是暂定的：此后 0.6 秒内，会话与上级都没变而取景区域又变了（外壳切换时取景区域可能先量到一个过渡值），最多再按新的区域重排两次；过了这段时间，窗口再怎么变，已有的卡也不动。
  - **放得下就保持原样**：先按经典排法（来源按取景区域的形状在 1~4 列里并排，来源在左、会话向右成树）看能不能在缩放上限（默认 100%）下整个放进去；放得下、外框又不是一条细长的竖串，就是这个树，会话只有几个时不为排而排。“细长”是拿外框的宽高比与取景区域的宽高比相比：会话不少于 12 个时，比值要在 0.7 ~ 1.43 之间；会话少时只拦竖串（比值不到 0.55），横向的短串是树本来的样子。另有一条直接的规则：取景区域不比高窄（横屏或正方形）、画布上只有一个来源、这个来源名下至少有 3 个没有子会话的根会话时，不等外框“细长”就直接试网格，免得三个起的独立会话叠成一条竖堆，网格同样要放得进缩放上限才换下经典排法；竖屏里单列本来就贴着取景区域的形状，不受这条管。
  - **放不下就排成网格**：每个来源换成“来源卡在上居中、会话成多列规则网格”或“来源卡在左、会话在右”（见下面“来源卡的摆法统一”）：独立会话排成横平竖直的矩形网格，带子会话的会话让子会话们在它右边装进一个矩形（见下面“小家族竖排”），来源块再按取景区域的宽高比分成几列竖排，在所有排法里取整体能放得最大的一种。同一个来源的会话相邻成组，连线仍是来源到根会话、父会话到子会话；网格里会话卡之间的行距与列距都是 4 的倍数（来源卡与会话之间、Folder 与 Git 卡与来源卡之间的空白不在此列）。窄取景区域（宽度小于 720px，例如宿主的浏览器侧栏）间距收紧、列数更少，也不画 Folder 与 Git 卡。几种排法一样好时取固定的一种，同一份数据永远排出同一个结果：来源块的外形宽高都相同取来源卡在上方的、同样高取更窄的，分列方式的整体缩放相差不到 1% 取列数少的。网格要比经典排法放得更大才换下它：经典排法在缩放上限下本来放得下（只是细长）时，网格也得放得进缩放上限；经典排法放不下时，网格的缩放要大出超过 1%（恰好 1% 不换）。
  - **小家族竖排**（用户的决定：子会话不多的小家族，子会话竖排在父会话右侧、线走缝隙，大扇出照旧）：网格排法里，后代（子会话与它们的子孙，不含自己）不超过 5 个的会话，子会话们在它右边排成一列、一个挨一个，它自己在这一列旁边竖直居中（行数是偶数时靠上半格）；这一整块（包括它自己那一列上下的格子）别家的卡不会占，整体排出来的画布里，小家族的父会话发出的线只走父子之间的缝、不从别的卡后面穿过（来源卡发出的线、汇聚会话的入线（含它到第一个上级的那一条）、Folder 与 Git 的连线不在这条里；子会话一个个到达时落进下一个空位，线不保证不穿卡）。后代超过 5 个的大扇出照旧，子会话按容器宽度折成多列；来源卡名下的根会话不受影响，仍是整张画布网格的一部分。“不超过 5 个”这条界线、行数是偶数时靠上半格、整块不让别家的卡占，都是实现时的取舍。
  - **来源卡的摆法统一**（用户的决定：“全部空间”里各来源卡的摆法统一）：同一张画布里所有来源卡用同一种摆法——都在自己会话块的上方居中，或都在左边——两种各规划一遍，整体缩放更大的采用，一样大取在上方的；只有一个来源块时没有统一可言，仍取它自己的最优。代价是多个来源并排时，整体缩放可能比各挑各的略小。两种各规划一遍取缩放大的、一样大取在上方，以及只有一个来源块时仍取它自己的最优，都是实现时的取舍。
  - **仍放不下才缩小**：排完内容在缩放上限（默认 100%）下还放不下，取景缩到刚好全部入画，下限 16%——“全部节点在画面内”优先于可读（默认排布、“适应”、“重置节点布局”之后都是这样）。节点多到 16% 也放不下（取景区域很窄、会话上百个）时，画面停在 16%，其余需要平移查看。例外是整体排一次时用的是经典排法、之后新会话一个个到来的画布（会话从空白逐个长出来就是这样；经典排法放不下、网格又没有大出 1% 时也是，比如很窄的取景区域）：它仍是那棵经典的树，自动取景按宽度来——宽度优先入画（最低 30%），高度只让步到 72%，再高的内容留在画面外，新到的会话落在画面外时由边缘提示指出；点“适应”才缩到全部入画（见“已知限制”里的例子）。
  - **新会话到达时**（已有的卡不动）：新卡的落点先看规划——规划只是多了这张新卡、没有重排已有的卡，它给的位置没压住别的卡就用；用不上时（规划把已有的卡重排了、位置被占了，或这是该让位的新根会话、接在已满的竖排后面的子会话）按下面的规则落位。新来的根会话先填它所在来源块外框里空着的格子，按阅读顺序（先上后下、每行从左到右）；没有空格才向外长：新开一行（块下面最左的一格）或新开一列（块右边、顶与第一排对齐），取能让全部卡在取景区域里显示得更全的那种；两种一样全时（比如窗口大到两种都能 100%），取长出来之后这个来源块的外形更像取景区域的那种（宽的取景区域多半长一列、窄长的多半长一行），两种离取景区域的形状差不多远（不论偏宽还是偏窄，只比各自的宽高比偏离取景区域宽高比的倍数，相差不到约 5%）时长一行；一边被别的来源块或别家的子会话区域挡住就长另一边。子会话落在它的参照此刻位置的旁边（父会话右边，或上一个兄弟下面），被占了：格点排布里找最近的空位，附近都满了才落到所有卡的下面，经典的树里沿这一列往下让（总放得下，但离该去的地方远一些）；竖排的一列已有 3 张以上、再接一张不如另起一列显示得全时，新的一张落在右边新开的一列。汇聚会话落在同一来源块里所有上级的右边；网格排布里右边没有空位就在所有卡的右边开一列、与第一排对齐。新来源整块（按规划排好的相对位置）放到所有已有的卡下面、左缘对齐。新卡躲开别家的整块区域；新的根会话与 Folder、Git 卡还不占别家竖排的子会话列尾下面那一格（留给那家人的下一个子会话；别家的子会话不受这条拦）。这些落点只取决于当下的取景区域，之后窗口再变也不会让已有的卡动。
  - **隐藏之后再显示**：“隐藏未在工作的会话”或“隐藏相关节点”收起会话时，剩下的卡重新排紧（有卡消失，属于上面的例外；同一批会话以前收起过，就直接复原那一次的排布）；再显示时先还原收起之前的排布——画着的节点集合与某份存下来的排布完全相同就原样还原，收起期间新来的会话放进空位。排布只记在内存里（最近的几份，数量上限只为内存有界）；收起期间有卡被归档或删除、或上级变了，收起之前的那份不再成立：有更早的、仍然成立的存档就用它（其余的卡落进空位），没有才整体重排一次。
  - **“适应”**（比例尺上的按钮，或按 0 / F）只动相机，不动节点位置，也不会让节点重新排；相机按“全部节点入画”取景（下限 16%）。
  - **“重置节点布局”**（拖动过节点，或已有的会话卡与此刻的默认排布不一样时才出现在比例尺里；刚整体排好、或点过之后没有东西可重排就不显示）清除全部手动位置并整体重新排列，用的是同一套规则，只多一个第一约束——你此刻的缩放：按这个缩放排得进画面，缩放不变、只平移；排不进才缩小，缩到刚好放下为止（下限 16%）。重置之后相机处于自动取景，之后新会话到达、“仅工作中”或来源折叠变化、窗口大小变化引起的重新规划都沿用这个缩放，不会跳回按 100% 排的旧形态，也不会改变你保持住的缩放；你一旦平移、缩放或拖动节点，相机就归你。重置记下的缩放只存在当前页面里、按空间分开，再次重置会覆盖它，刷新后回到默认排布（按 100% 排）；点“适应”后相机回到按内容取景，不再保持这个缩放。Ctrl/⌘+Z 只撤销节点位置，不撤销相机。
  - **哪些是用户定的**：上面标明“用户的决定”的几处是用户明确说过的；用户还反复强调过：在当前的缩放百分比下呈现节点，不要频繁缩到很小，不要一条竖到底，要整齐、均匀。其余的界线与取值——12 个会话起算“多”、0.55 与 0.7 的宽高比、3 个没有子会话的根会话起算“竖堆”、5 个后代以内算小家族、竖排的一列至少 3 张才允许另起一列、720px 的紧凑与宽屏界线、经典排法最多并排 4 列、格点排布最多分 16 列、各处平局的取法与 1%、约 5% 的阈值、暂定窗口的 0.6 秒与两次、16%、30% 与 72% 三个缩放界线、存档的份数、新会话落点的比较办法，以及没有写在这里的其他数值——都是实现与验证时的取舍，没有经过逐项确认。
  - **验证范围**：上面的规则由纯几何的单元测试覆盖，并在隔离的服务加无头 Chrome 里用模拟执行端与几块真实画布的数据验证过（窗口 1440×900、1920×1080、1280×720，另有竖屏与窄侧栏；根会话从 1 个逐个到达 60 个；已有卡的位移、重叠、缩放逐项比对）。**没有验证**：真实的 Cursor / Codex 宿主里的样子、真机上的帧率与卡顿（见“已知限制”）、触摸屏上的拖动、Chrome 之外的浏览器、设备像素比不是 1 的屏幕。这些验证早于排布与引擎拆成多个文件。拆分之后，又在隔离的服务加无头 Chrome（软件渲染，窗口 1440×900、设备像素比 1，鼠标与浏览器模拟出来的触摸）里，把拆分之前与之后的两份构建用同一批场景逐步比较（每步比较每张卡的位置、缩放读数、相机、选中集与控制台报错），没有发现稳定的差异，耗时也没有慢于噪声（约 400 个节点上“重置节点布局”拆分之前 707 ms、之后 705 ms；各个系列里偶尔有一次偏离常态的运行（多半是更慢的），拆分之后的构建里出现得更多一些，没有归因）；在拆分之后构建的一份副本里故意各改坏一行的 15 处都被抓到了（8 处直接体现在逐步比较的量里，另 7 处要靠泄漏、落定耗时、触摸间隔等专门的探针）。此前逐个到达、追加、回放、拖动后刷新、隐藏再显示等场景的脚本也在拆分之后重跑过，除下面这一项外同样没有发现稳定的差异；两份构建算出的目标位置在纯计算重放里逐点相同。**没有查明**：开着“隐藏未在工作的会话”、其间陆续来了一批一直在工作的会话的扫描里，拆分之后的构建 3 次完整扫描有 2 次、拆分之前的构建 4 次扫描（其中一次没有扫完）一次也没有，在某个采样点量到过卡片相叠；多次对照实验里量到的相叠都发生在有卡还没到目标位置的时刻（纯计算重放里目标位置本身从不相叠），但拆分之后那两次扫描当时没有保存位置，是不是同一回事没有查明；次数的差别在统计上不显著，也没有解释。此后又做过补测试、删掉没人调用的函数、去掉一个恒为同一个值的参数、改注释这类改动，没有在浏览器里重做：排布的输出用 9 个纯计算脚本核对过，与改动之前逐字节相同，改动后的代码由对应的单元测试覆盖。此后还修了一个拆分之前就有的缺陷：点一张卡进聚焦页、再用浏览器后退，画布右下角的缩放读数停在 100%，而相机实际不在 100%；修复由引擎层与组件层的单元测试覆盖（含把整个概览卸载再挂载的组件测试，故意各改坏一行也都被测试抓到）；此前在真实的 Chrome 里复现过它（读数 100%、相机 56.43%），这一版修复又在隔离的服务（模拟执行端，`scripts/dev-seed.mjs` 灌了 6 个会话）加无头 Chrome（软件渲染，设备像素比 1）里复测了一次：网页用的是 2026-11-24 14:06 构建出的 `dist/web`，页面是“全部空间”，用 Chrome 调试协议（CDP）派发真实的鼠标点击——先（只在第一个场景）点一次比例尺的放大按钮，再点一张卡的中心进入聚焦页——然后调用 `history.back()`；回来之后比例尺里的读数与“适应”的高亮都和离开之前相同，读数也与世界层 `transform` 里的缩放（相机实际的缩放）一致：窗口 1280×800 点放大一次是 92%，760×460 只靠自动取景是 61%，1280×800 什么都不动是 77%，“适应”只在第一个场景亮；后退之前装了一个 `requestAnimationFrame` 采样器，每个动画帧回调里读一次读数与高亮，回来之后第一个出现比例尺的帧起读到的一直是这个值，没有出现过 100%；在拷出来的构建副本里分别去掉修复的两半作对照，同一个脚本都抓得到：去掉挂载之后向新挂载的组件通知相机的那一次（保留卸下时的重置），放大过的那个场景回来之后读数停在 100%、“适应”不亮，而世界层缩放仍是原来的值，另两个场景读数仍然正确（它们靠自动取景之后的那次通知）；去掉卸下时把“已通知的缩放与是否动过”重置回起点的两行（保留挂载时的那次通知），三个场景回来之后读数都停在 100%（第一个场景里“适应”也不亮），世界层缩放仍是原来的值；**没有验证**：只试了 Chrome、窗口 1280×800 与 760×460 两种、设备像素比 1；只用了隔离服务里的 6 个会话，没有用真实服务里大得多的画布；“回来时不会闪一下旧值”只是在每个动画帧回调（绘制之前）里读 DOM 采到的，没有逐帧截屏，也没有在带 GPU 的真实窗口里看过绘制出来的画面；也没有在真实的 Cursor / Codex 宿主里试过。
- **汇聚（一个会话跟随多个上级）**：`delegate` 的 `follows` 传一组会话时（见 MCP 一节的“多个上级”），这个会话在画布上从每个上级各连一条线，画布因此是有向无环图，不只是树。**没有这样的会话时，这一条规则不起作用**（排布、连线、节点位置与没有这条规则时逐字相同）。有的话：它仍然只挂在**画出来的第一个上级**之下（主上级被收起、被归档、没排进来时顺延到下一个，一个都没排进来就当作根），拖动时的参照、“新会话出现在参照节点旁边”都只认这一个，经典排法里它的竖直位置也只跟着这一个；它所在的列被推到同一个来源块里所有上级的右边（用户的决定：汇聚会话一律放在所有上级的右边，可能多占一列、缩放略降）；它至少落在比这些上级所在的最靠右的列再往右一列，它的下级顺着往右排，不会重叠；上级在别的来源块里时没有“左右”可比，不参与推列，连线照样画，随两端此刻的位置选边。网格排法里它先按第一个上级的家族照常排，排出来不在所有上级右边的，才连同自己的子树被摘出来、放到所有上级的右边（行取各上级所在行的平均附近，那里没有空位就上下找最近的空位），原来的家族重新紧排、不留空洞（少见的兜底情形除外：重排之后仍有不满足的，就原地右移，会留下空洞）；新会话到达时汇聚会话同样落在所有上级的右边。规则保证的是“列在所有上级的右边”，不保证连线不穿过别的卡：上级与它隔着两列以上时线本来就避不开。每一对（上级，子会话）一条线；几条线汇到同一个节点时共用它的同一个端口方点（与来源卡向右扇出时共用右缘方点对称），线条的样式与原来一样，汇合处不会更粗或更亮。拖动其中一个节点只让与它相连的线改道，不动别的节点；“重置节点布局”与网格排法里，汇聚会话（必要时连同它自己的子树）落在所有上级的右边（见上），上级在别的来源块里时，跨块的汇聚连线只是改道。画不出来的数据（上下级互指成环）照旧把环上的连线去掉、环上的会话当作根。列表视图与会话页侧栏里它只出现一次，在它的上级里第一个出现在列表中的那个下面；“仅工作中”会沿着它的每一条上级链保留上级；“隐藏相关节点”只在它所有的上级都被收起时才把它一起收起，否则它留着、画在剩下的上级旁。会话页左栏的任务卡里每个上级一行，认不出（记录已不存在、已归档还没加载）的逐个说明。**验证范围**：这一条描述的网页行为在隔离的服务加无头 Chrome（中文与英文，1440 与 860 宽）里验证过：汇聚会话的入边共用端口、挂在第一个上级下并把列推到上级右边、拖动与“重置节点布局”只让相关的线改道、“仅工作中”沿着每条上级链保留、“隐藏相关节点”按所有上级是否都被收起处理、列表与侧栏里只出现一次、任务卡里每个上级一行（含记录已不存在的上级）。网格排法里汇聚会话怎么落（落在所有上级的右边、新会话到达时的落点）是 2026-11-22 那次完整运行之后才改的，不在上面那次浏览器验证里；它由对应的单元测试、另几轮隔离服务加无头 Chrome 里的验证（记录到汇聚会话都落在所有上级的右边、已有的卡不动、没有重叠）和下面说的 2026-11-24 最后一次完整运行覆盖。**没有验证**：真实的 Cursor / Codex 宿主里的样子、触摸拖动、小于 860 的宽度、时间线里改挂事件的文案在汇聚下的呈现。这些验证早于之后的修复与拆分，改动后的代码只由 2026-11-24 最后一次完整运行（三份类型检查没有错误、完整测试没有失败）覆盖。
- **隐藏未在工作的会话**：页头右侧视图操作区里带斜线的眼睛按钮（“仅工作中”）是画布的视图开关，只存在当前浏览器（`ensemble.canvas.hideIdle`，默认关闭，刷新后保持），不改任何会话，服务端与 MCP 都不知道它。打开后画布只留“工作中”的会话——运行中、启动中、排队中，以及待命（`ready`：会话在、此刻没有运行；用户的决定是待命算在工作里）；已经结束的（已完成、失败、已中断、已关闭、已失联）收起。工作中会话的上级会话即使已经结束也会保留，否则子节点会像是直接挂在来源上，那是一条不存在的关系；按钮右上角的数字是真正被收起的会话数，不含这些被保留的上级，也不含待命的会话；有可收起的会话时，悬停提示里写着这两条“为什么它还在”的规则。来源卡上的会话数与运行数、Folder 卡上的“N 个 Main Agent”仍是真实总数；没有任何会话留下的来源卡，以及只服务于它的 Folder 与 Git 卡，会一起收起，剩下的重新排紧（被收起的目录仍按空闲节奏读取 Git 状态，再显示出来时读数是现成的）。会话从工作变成结束时先淡出再合拢；正被拖动、菜单开着或键盘焦点在上面的那张卡，等操作结束再收。拖动过的节点再显示出来时回到它保存的位置；没拖过的卡在收起之前的那份排布还成立时也回到那份排布，收起期间新来的会话放进空位（见“画布排布与重置”里的“隐藏之后再显示”）。全部都不在工作时，画布写明“现在没有正在工作的会话”和已收起的个数，并给出“显示全部会话”。只作用于概览；聚焦视图不受影响。“全部活跃”这个空间里没有这个按钮（这个空间本来就是按同一条规则筛出来的）；空间里一个会话都没有时按钮也不出现。
- **隐藏 Main Agent 的相关节点**：在某个 Main Agent（来源卡）上点右键，或聚焦它后按菜单键 / Shift+F10，菜单里是一项“隐藏相关节点（N 个会话）”，N 是它名下的会话数（含嵌套委派的，与卡片头部的数字同一个口径）。隐藏后它名下的整棵会话树收起，只为它服务的 Folder 与 Git 卡一起收起（和别的 Main Agent 共用的那张留着，直到用到它的来源都被隐藏），剩下的重新排紧；来源卡自己留在原来的先后位置，叠成一摞（右下露出两层边）表示“后面还有东西”，头部的会话数前多一只带斜线的眼睛，点它或再次右键就恢复显示，悬停提示写明收起了几个会话、几个在运行。收起的来源卡没有 Folder 节点可依，所以卡上自己写回工作目录。别的 Main Agent 也被隐藏着时，菜单多一项“全部显示”（带个数）。偏好只存在当前浏览器（`ensemble.canvas.collapsedOrigins`，刷新后保持），不改任何会话，服务端与 MCP 都不知道它；已经没有会话的来源的记录在下一次改动时清掉。会话先淡出再合拢，重新显示的会话回到原来的位置、不算新会话。与“隐藏未在工作的会话”可以同时开：被隐藏的来源只剩卡片，没被隐藏的来源仍只留工作中的会话；两者合起来把所有会话都收起时，不显示“现在没有正在工作的会话”（卡片还在，那句话不实）。隐藏期间新委派到这个 Main Agent 名下的会话不会出现，卡上的会话数与运行指示点如实增加；被隐藏会话上的“值得留意”标记也不会出现在画布上（会话在 `status` 与 MCP 里照常可见）。读屏会播报“画布上显示 N 个会话，另有 M 个已隐藏”与每次操作的结果。只作用于概览；聚焦视图不受影响。
- **节点右键菜单**：在会话节点上任何位置（包括标题链接和“···”按钮）点右键，或聚焦节点后按菜单键 / Shift+F10，弹出的菜单与卡片头部“···”的菜单是同一份：打开会话、复制面板链接、复制会话 ID、中断当前运行、关闭会话、删除记录；现在不能用的项写明原因（例如运行中的会话不能删除）。菜单的左上角落在指针处，右边或下边放不下就向左、向上翻转，离窗口边缘至少留 8px，太矮时菜单内部滚动；键盘打开时没有可信的指针位置，菜单放在节点左上角偏内处。菜单开着时这张卡片保持悬停外观；Esc 或选了一项后焦点回到节点；点菜单外、画布滚轮缩放或平移、调整窗口大小、窗口失焦、Tab、所指会话被删除，菜单都会收起，再在别处右键则换成新位置的菜单，不会叠两层。右键不会打开会话、不会移动节点，也不会改动选中（只有落在多选之外的会话节点上是例外，见下）。
  - **多选后右键**：选中两个及以上节点后，在选中的任一节点上（来源、Git、Folder 节点也算）点右键，弹出多选菜单，第一行写明作用范围“已选择 N 个节点”。第一组是排列：六种对齐、两种等距分布（不足 3 个时不可用并写明原因）、撤销、重做（带快捷键提示，没有历史时不可用并写明原因）和取消选择，与对齐条用的是同一批操作。选中里有会话时多出第二组“其中 N 个会话”：复制会话 ID（多个用换行连接）、中断当前运行、关闭会话、删除记录。每一项后面写的是真正会作用到几个会话，并且只作用于当前能执行的那些：没有运行的不会被“中断”，已关闭的不会再被“关闭”，运行中的不会被“删除”；关闭与删除先弹确认框，写明影响几个、另有几个不受影响。批量动作对每个会话各发一次与单个菜单相同的服务端请求，同时进行，没有事务：完成后用提示如实汇总成功几个、失败几个和失败原因，部分失败时成功的不会回滚。撤销与重做只覆盖节点位置的变动，不覆盖对会话的操作。
  - **右键落在多选之外**：落在选中集合之外的会话节点上，选中收成这一个节点，弹出它自己的菜单（与“···”一致）；落在选中集合之外的 Git、Folder 节点上，没有菜单可给，选中原样不动，浏览器的原生菜单照常出现；落在选中集合之外的来源节点上，选中同样收成这一个来源，弹出它自己的菜单（见“隐藏 Main Agent 的相关节点”）。
  - **仍然是浏览器原生菜单的地方**：没有多选时的 Git、Folder 节点，以及名下已经没有会话的来源节点，画布空白处，输入框，页面上节点以外的其他区域。macOS 上 Ctrl+点击仍是平移（不是右键）；Ctrl+右键才打开菜单。
- **Git 节点**：同一个 Git 工作树只在最左侧显示一张卡，它连到落在该工作树里的每个 Folder 节点（见下一条），再由 Folder 节点连到各自的来源，两段都是静态连线。不同 clone 或 worktree 各自显示，即使分支名和提交相同。卡片上是这个工作树当前的分支（游离 HEAD 时写明）、最近一次提交（短哈希与说明）和工作区状态（多少个文件有改动；有合并冲突时标红）；与上游有差距时头部右端显示领先 / 落后的提交数；悬停可看完整目录、上游、改动明细（已暂存 / 未暂存 / 未跟踪 / 冲突）、远程和读取时间。内容全部来自对该目录运行的只读 `git` 命令，没读到的不画：没有上游就没有领先落后，没有提交就写“还没有提交”。它是定期刷新的快照，不是实时事件流：该目录的来源有会话在运行时约每 4 秒读一次，否则约每 15 秒一次，运行状态一变立刻补读；最近一次读取失败时保留上一次的结果，头部多一个钟表，提示里写明显示的是哪个时刻的状态。读不到 Git 的目录（不是 Git 仓库、目录不存在等）、以及没有工作目录（例如从控制台发起）的来源没有这个节点：前者的 Folder 节点直接连到来源，左边没有 Git。窄画布（低于 720px，例如宿主的浏览器侧栏）放不下多出来的两列（Git 与 Folder），都不画。Git 节点同样可以拖动、框选、对齐，位置保存在当前浏览器里。
- **Folder 节点（工作目录）**：来源（Main Agent）的工作目录是它自己的一张卡，接在来源左边；同一个真实目录只显示一张，用它的每个来源各有一条静态连线。主行是目录名，次行是上级路径（放不下时从开头省略，留下最靠近这个目录的几级；悬停可看完整路径）；头部右端只在不止一个 Main Agent 使用它时才写“N 个 Main Agent”。内容只来自来源自己带着的工作目录，按可信度取第一个有的：宿主为这段对话留在本机的记录（目前只有 Cursor：按对话标识去它的 `state.vscdb` 里查这段对话所在的工作区，没有标识就不查、不猜）；宿主通过 MCP roots 报告的第一个工作区根（Cursor 的不采信：它的插件进程被所有窗口共用，roots 是各窗口目录的并集，认不出是哪一段对话）；这个来源最近一次委派里显式传入的 `cwd`。悬停提示会写明出处：“宿主的对话记录”“宿主报告”或“委派时传入的 cwd”。三者都没有，就没有 Folder 节点，来源卡的目录行写“未知”——不再拿桥进程的启动目录顶替（那多半只是插件被谁拉起来的，与对话在哪个项目里无关）。这个目录只说明来源，不决定被委派的会话在哪干活。一个来源前后几次委派带的目录不同时，取最近一次带着目录的那一次；之前已经记录下来的会话照旧显示它当时存的目录（可能就是旧版本记下的桥进程目录，没有“来历”标注），不会被改写。除此之外没有别的字段：目录里有什么、是不是仓库都不在这张卡上。合并只对路径字符串做规范化，不读文件系统，所以不说目录“存在”或“不存在”：Windows 路径的盘符与目录名大小写、正反斜杠、结尾与重复的分隔符、`\\?\` 前缀视为同一个目录；POSIX 路径区分大小写；`subst` 盘、junction、8.3 短名这类要靠系统才能解开的别名按不同目录对待。位置关系是 Git → Folder → 来源：目录在某个 Git 工作树里时，左边接着那张 Git 卡，同一个工作树里的几个目录共用这一张；目录不在 Git 里就直接连到来源。它不依赖 Git 的读取，一开始就画出，不用等。来源卡因此只剩首次委派时间和宿主给对话起的标题（目录写“未知”的 Agent 来源除外：它没有 Folder 节点，卡上主行写“未知”，时间退到次行；从网页控制台发起的来源本来就没有工作目录，不写“未知”）；窄画布（低于 720px）不画 Folder 节点，这时来源卡自己保留目录行，信息不会消失。Folder 节点同样可以拖动、框选、对齐，位置保存在当前浏览器里（升级后第一次出现的 Folder 节点放在它的来源旁边，已经保存过的 Git 节点位置不会被改动）。
- **设置窗口**：左侧栏底部的“设置”（只有一个齿轮图标，名字在悬停提示和读屏名称里；窄屏在概览页顶栏的右端，宽屏收起侧栏后要先展开侧栏）打开一个居中的窗口，左边是分区导航，右边是当前分区。Esc、点遮罩或右上角的关闭都能关掉，焦点回到“设置”按钮；窗口自己的宽度不超过约 600px 时（例如宿主的窄侧栏）导航收成顶部一条。这里的修改都是即时生效、没有“保存”按钮，窗口记得上次停在哪个分区（只记在页面内存里，刷新后回到第一项）。目前的分区如下（登记表在 `settings/sections.ts`）：
  - **执行端**：每个执行端一张可折叠的卡片（默认只展开第一个；收起的头部已经写着状态、版本和“已开放 n / 总数 个模型”），展开后勾选「允许主 Agent 选用的模型」与允许的推理强度，并可在已勾选的模型里点最右边的方框，为这个执行端指定一个默认模型（方框平时就在，是一圈很淡的细线轮廓，悬停时线变深，选中的那个是朱砂色的线加框里一块朱色的小方块；方向键在方框间移动，「恢复执行端的默认」撤销指定；执行端自己的默认旁会标「执行端默认」）；窗口标题行上的刷新按钮重新探测各执行端。内容与保存规则见下文 `settings.json` 一条，这些选择由服务端统一强制，网页与 MCP 看到的是同一份。
  - **角色**：把一组（执行端、模型、推理强度、访问权限）起一个短名字，主 Agent 委派时按名字选用（`delegate` 的 `profile`，规则见下文 MCP 一节的“委派角色”）：换了模型世代、或把“验证”挪到另一个执行端，只在这里改一次，所有宿主下一次委派就跟着变。一行一个角色，依次是名称、执行端、模型、推理强度、访问权限和删除（分区自己的宽度不到 620px 时一行折成两层：上层是名称与删除，下层是四个下拉框，各带一行小字的名称；不看视口，看分区自己有多宽）；没固定的项显示“默认”，委派时照原有规则走：模型用「执行端」里指定的默认，没有就是执行端自己的默认；推理强度用该模型的默认档位；访问权限是完全访问。没有预置的角色，也没有“说明”之类的字段。点“添加角色”多出一行草稿，名称合格并选了执行端的那一刻自动保存；之后每一次选择、改名（回车或离开输入框）都立即生效，删除先确认，没有保存按钮。下拉框的选项来自真实数据：执行端是此刻所有的执行端（还没就绪的也列出并注明状态，角色可以先建好），模型与推理强度是这个执行端此刻开放给主 Agent 的（也就是你在「执行端」里勾选的），执行端落实不了的访问权限注明“不支持”；换执行端时模型与推理强度回到默认（它们属于原来的执行端），访问权限带着。每一行的方块表示此刻能不能用——实心可用、空心不可用或还没存（用形状而不是颜色），不可用的原因写在这一行下面，例如“模型「…」在 … 上没有开放”；角色本身绝不会被自动改动或删除，改不改由你决定。手改 `settings.json` 造成的无效条目（名称不合规、内容读不出来、这一版不认识的执行端）照样列出并说明原因，不悄悄抹掉。最多 20 个角色；导航项下面的小字写“n/m 可用”（n 个此刻能用，共 m 个）。`settings.json` 整个读不出来时，这一分区只说明角色暂时不可用，没有“添加”（那不是“没有角色”）。存储规则见下文 `settings.json` 一条。
  - **通用**：两项设置，作用范围不同。**界面语言**（中文 / English）只保存在这个浏览器里（`localStorage` 的 `ensemble.lang`），不像模型开放设置那样各宿主共用；选中即生效，窗口里的文字当场换语言。另一项是**并发上限**（同时运行的会话数）：它是服务端的设置，各宿主与所有页面共用（多个标签页实时同步），存在 `settings.json`（见下文），没有保存按钮，改动立即生效、不必重启服务。「限制 / 不限制」两档，限制时在数字框里填 1–1000 的整数，或用两侧的加减钮、上下方向键；Enter、失焦与步进都立即提交，Esc 还原，不合法的数字只在下面提示、不发请求；「恢复默认」清掉这里的指定，回到环境变量或内置默认。调高时排队的会话按先到先得马上开始；调低不会中断任何运行中的会话，占用数可以暂时高于上限，名额随会话结束逐渐收回。数字框下面实时显示服务端的“占用 X · 等待 Y”，并说明现在的上限是在这里指定的、来自环境变量还是内置默认（设置文件里的值无效、或整个文件读不出来时也如实说明）。窄屏的会话页（聚焦视图）既没有侧栏也没有顶栏，也就没有设置入口，回到概览再切换；宽屏的会话页左侧栏仍在，设置在它底部。
  - **历史**：已归档与未归档的会话数、“查看已归档”（进入“已归档”视图，见“历史会话：归档、‘已归档’视图与导出”一条），以及**留存策略**（默认关闭）。留存策略有两项，各自独立：“保留最近 N 天”（`keepDays`）与“最多保留 M 棵任务树”（`keepCount`）；每项是一个复选框加一句话加一个整数框，打开的才生效，两项都不开就不会自动归档。数字框里的字只是草稿，失焦或按 Enter 才提交（Esc 还原），输入过程中不发任何请求；不合法的值（空、小数、0、负数、超出 1–3650 天或 1–10000 棵、夹杂文字）只在下面写一句话、不提交、也不替用户改写；打开复选框不预填任何数字（没有哪个数字是用户的选择），关掉复选框立刻提交“不限”。没有保存按钮。保存会让服务立刻清扫一次，所以网页不在本地估算“会归档几个”（估算与服务端用的是同一套规则、不同的时钟与数据，说错了比不说更糟），保存后只写服务端报告的“上次清扫：时间，归档了 n 个会话”。文案写明它只归档、不删除，任务树里还有会话在工作时整棵树都不会被归档。服务不报已归档个数（旧服务，没有归档）时只写“当前运行的服务还不支持归档”，不画控件。
  - 没有绑定 `Ctrl/⌘+,`：这个组合键在多数宿主里是宿主自己的“设置”，而页面常开在宿主的侧栏里，抢它会冲突。
  - 新增一个设置分区只需三步：在 `src/web/components/settings/` 写一个分区组件；在同目录 `sections.ts` 的 `SECTIONS` 里登记一项 `{ id, labelKey, icon, Component }`（需要时加导航小字 `summary` 与标题行操作 `actions`）；在两份字典里加上 `labelKey` 的文案。窗口、store 与 `openSettings("…")` 的分区 id 类型都由这张表推出，不用再改别处；`sections.test.ts` 检查登记表的不变量。
- **聚焦视图**：点开一个节点——左侧是来源、委派原文、传入的上下文、实际发给执行端的完整提示、会话信息（执行端、模型、推理强度、访问级别及其强制方式、工作目录、原生会话编号）；中间是时间线与输入框（连续的工具调用与推理合成一个默认收起的工作组，只有进行中和失败的步骤带颜色；每条消息下面写着它的投递进度）；右侧是进度、消息记录、文件变更和用量。会话页底部没有任何工具栏：宽屏下左侧栏仍在，设置在它底部；窄屏的会话页没有侧栏与顶栏，设置回到概览再用；只在服务连接断开时保留那一条状态提示。
- **介入**：会话运行中，输入框可以选“纠偏”（在运行中交给执行端，何时生效取决于该执行端）或“排队”（等这次运行结束再处理）；执行端不支持运行中纠偏时只有“排队”，并写明原因；空闲时发送的是同一会话的下一次运行。Enter 发送、Shift+Enter 换行，输入法组字期间的 Enter 不发送；Esc 先让输入框失焦（草稿保留，不会中断运行），再按一次才返回画布。每条干预的投递状态如实区分：已记录、已排队、已交给执行端（不等于已生效）、已生效、失败、已撤回。被委派的会话没有“等待授权”这个状态：默认 Full Access，只读（`read_only`）只在发起方明确要求时使用，写入会直接失败而不是弹出授权。
- **值得留意**：进行中的会话如果出现下列情况，会话卡片头部会出现一个琥珀色的警示标记（有多条时带数字，悬停列出每一条事实），聚焦页右栏摘要的最上面多出一个“值得留意”分区。这里写的是服务端从事件流算出的事实，不是“卡住了”的判决，也不会自动中断任何会话：一段时间没有任何事件且没有进行中的工具调用（4 分钟）；有工具调用在进行、但很久没有任何事件（10 分钟）；这次运行已持续很久（60 分钟）；某个文件在 10 分钟内也被另一个正在运行的会话写过；一条补充消息 2 分钟后还停在“已记录”或“已交给执行端”、没有被执行端确认；执行端提了一个问题、还在等回答（没有时间门槛，一提出就算，见下一条“提问”）。已经结束或失败的会话不出现在这里，状态本身已经说明。同样的内容也出现在 MCP 的 `status` 与 `wait` 里，见下文。
- **提问**：执行端向用户问了一个问题时（来龙去脉见 MCP 一节的“子会话的提问”），时间线里在它被问出来的位置出现一张“提问”卡：问题与可选项逐字来自执行端（已脱敏、按上限整理），选项前是方框（单选里是一块实心小方块，多选里是对勾），有多个问题时标“1 / 3”；执行端允许自己写时多一格“其他”，没有可选项的问题是一个文本框（Enter 提交，多行文本框要 Ctrl/⌘+Enter，输入法组字期间的 Enter 不提交）；下面是“回答”与“不回答，让它自行判断”两个按钮，每个问题都要有回答才能提交；发送中与出错时按钮和状态行的尺寸不变，填到一半的回答切走再回来不丢。回答之后卡片原位变成只读记录，写明谁、何时、选了什么，以及“已交给执行端”（悬停说明：执行端已收下这条回复，它是否读到并采纳，Ensemble 无法确认）；执行端已不再等待（运行结束、被撤回、会话关闭、服务重启、一小时无人回答）时写明原因，回复不会装作送达。状态用方块的形状而不是颜色区分：空心是待回答，实心是已回答，带一道横线的空心是不回答，淡的空心是已过期。待回答期间，Agent 卡头部的琥珀标记与聚焦页摘要最上面的“值得留意”里各有一条“提问待回答：…”，会话本身的状态不变（仍是运行中）。别处（另一个标签页、主 Agent）先回答了：页面自己的回复后到、被服务端拒绝（`409`）时，卡片给一句提示（例如“这个提问刚刚已被回答，页面马上会更新。”），随后跟着事件改成已有的结局；事件先到时，卡片直接变成只读记录，没有这句提示。**验证范围**：只对着模拟的 Codex 与 OpenCode，在隔离的服务加无头 Chrome 里验证过：各种状态的卡片、提交中与失败时尺寸不变、键盘操作、1280 到 320px 的宽度（没有横向溢出）、中文与英文、直角。**没有验证**：真实的 Codex / OpenCode、“已过期（超时）”那张卡的页面截图（只有单元测试）、输入法组字期间的 Enter、真实 Cursor 侧栏里的样子。这些验证早于之后的修复与拆分，改动后的代码只由 2026-11-24 最后一次完整运行（三份类型检查没有错误、完整测试没有失败）覆盖。
- **历史会话：归档、“已归档”视图与导出**：会话越攒越多时，把早已结束的收出日常视图，需要时再翻出来、导成 Markdown 复盘。服务端怎样存、怎样自动清扫见下文“历史会话：冷热分离、归档与留存”，这里只写网页上的规则与取舍。**验证范围**：这一条描述的网页行为在隔离的服务加无头 Chrome 里验证过：画布、列表、侧栏、聚焦页与“已归档”视图里的归档与取消归档，单个会话、整棵树与批量（含确认框）的流程，撤销提示，设置“历史”里的留存表单，空间被归档空之后自动切走，中文与英文、直角，以及用代理剥掉字段与路由模拟的旧服务降级（没有入口、不发请求、不报错）。**没有验证**：真实的 Cursor / Codex 宿主里的样子、真实的旧版本服务（旧服务降级是模拟的）、Chrome 之外的浏览器。这些验证早于之后的修复与拆分，改动后的代码只由 2026-11-24 最后一次完整运行（三份类型检查没有错误、完整测试没有失败）覆盖。
  - **归档是什么**：把会话移出画布、侧栏、列表、快速切换与各处的计数；记录原样保留，随时可以取消归档，界面上没有一句话会让人以为它被删除了。网页不做乐观更新，画面以服务端推来的会话摘要（带或不带 `archivedAt`）为准，所以点下去到画面变化之间隔着一次服务端往返。服务不报 `archivedCount`（旧服务，没有归档）时整套入口都不出现，也不报错。
  - **入口与确认**：会话的“···”菜单与右键菜单里的“归档”——连同它的整棵子树，名下有下级时写成“归档（含 N 个下级会话）”，不确认（可撤销的小动作）；Main Agent（来源卡）右键菜单里的“归档整个 Main Agent 空间（N 个会话）”；多选后右键菜单里的“归档所选（N 个会话）”；页头右侧视图操作区里的“归档已完成会话”（带数量；“全部活跃”里没有它：那里按定义没有已结束的会话；它不在页头第一行，那一行只有文字与图标）。后三种是批量动作，先弹确认框，写明会归档几个、其中几个是随上级一起走的、几个因为任务树里还有会话在工作而留下。成功后的提示带“撤销”（保留 10 秒；撤销就是把这次真正归档的会话取消归档，请求带 `exact: true`，不带回更早就已单独归档的下级。这要新服务加新页面才成立：旧服务忽略 `exact`，撤销时会连带恢复更多，提示里照实写一并恢复了几个）。归档在途时这些入口都禁用，免得连点；失败是一条真实的错误提示，状态不动。
  - **能归档什么**：网页先预判一次，只用来写菜单项、数量与“为什么不能”，服务端才是权威（点下去时状态可能已变，以回执为准）。规则与服务端是同一份代码（`src/shared/archive.ts`）：整棵子树都已结束（已完成、失败、已中断、已关闭、已失联，且没有未确认的消息）的最上层会话；待命（`ready`）不算已结束。不能归档的菜单项不隐藏，而是 `aria-disabled` 并写明真实原因与数字（“还有 N 个会话在工作 / 待命 / 消息没有被确认”）。
  - **“已归档”视图**（路由 `#/archived`）：从左侧栏列表下面的“已归档”一行（右端是数量；没有已归档的会话时不出现）或设置“历史”里的“查看已归档”进入。它不属于任何 Main Agent 空间，是一张按任务树缩进的平铺列表；第一次进入才向服务读取全部已归档的会话（`GET /api/sessions?archived=only`），之后由推送保持最新。每行写标题、执行端与模型、状态、下级数和归档时间，留存策略自动归档的带“自动归档”标记；动作是打开、取消归档、导出，点行身进入聚焦页。一次最多露出 200 行，其余点“显示更多”。没有归档的会话时写“还没有归档的会话”，不画插图。按窄宽度设计（行内容换行、动作留在行尾，目标是约 320px 仍可用），在无头 Chrome 里量过 375 与 320px：没有横向滚动，行内动作都看得到；没有在真实设备与其他浏览器上看过。
  - **聚焦页**：打开已归档的会话时留在原地，不会被当成“不存在”：页头标明“已归档”，顶部一条说明写着归档时间（自动归档的写明是留存策略）与取消归档的后果，旁边是“取消归档”；返回键回到“已归档”视图。正看着的会话被别处归档或被留存清扫时同样原地不动。给已归档的会话发送消息，服务端会先把它取消归档（见下文“自动取消归档”）。
  - **看着的 Main Agent 空间被归档清空**：空间是从未归档的会话里算出来的，名下的会话全归档后它就从侧栏消失。此时网页用与“空间不存在”相同的回退规则（上次看的空间 → 排第一的空间 → 全部空间）改写地址栏，并在确有该空间的已归档会话时给一条提示说明去向；会话若是被删除的则不弹这条（那样说“已归档”就是假话）。
  - **导出 Markdown**：会话的菜单里有“导出 Markdown”（只含这个会话，精简）；有下级时多一项“导出 Markdown（含 N 个下级会话）”；另有一项单独的、非默认的“导出 Markdown（含工具输出）”。一次点击直接下载，不弹对话框、成功不打扰；报告语言跟着当前界面语言；失败是一条真实的错误提示。“已归档”视图的每一行也能导出。报告的内容与格式由服务端的 `GET /api/sessions/:id/report` 决定，网页只负责请求与保存：令牌只在请求头里，下载走浏览器本地的 blob 链接。服务的 `features` 里现在有 `session-report`，但网页没有读它、也就没有探测：只有归档、没有这个接口的旧服务上点导出，得到的是一条带服务端状态的错误提示。服务端的这条路由与报告的规则见“导出会话报告（Markdown）”一节。
  - **取舍与没有回答的问题**（实现时的取舍，用户没有逐项确认）：待命（`ready`）不算已结束，所以不能归档、也让它所在的整棵树不被批量归档（是否算已结束待用户决定）；批量归档需要确认而单个不需要，撤销只留 10 秒；已归档视图一次读全、之后靠推送；没有做“复制为 Markdown”与 Bundle（zip）；没有给主 Agent 用的 MCP 归档工具；留存策略没有试算预览。
- **窄宽度优先**：为宿主浏览器侧栏设计，窄宽度和宽屏都是一等公民；界面支持中文和英文。
- **没有圆角**：整个页面都是直角——卡片、按钮、输入框、菜单、浮层与设置窗口都是；滚动条的拇指在 Chromium 与 Safari 里是直角的细条（走 `::-webkit-scrollbar`），Firefox 没有这个伪元素，用标准的细滚动条属性，拇指的形状由浏览器自己画，页面管不到；设置窗口“角色”分区的下拉框是原生 select，收起时是直角方框，展开后的列表由浏览器 / 系统自己画，同样管不到。状态点、端口方点、计数与分隔点这类小标记一律是方块，靠实心与空心表示状态，不靠圆形；转动标记也不转圈，是空心方块里一道上下推移的带子（系统设为“减弱动效”时停在半满的方块上）。图标线的两端是方头、转角是斜接，轮廓里的圆角都是直角，只有曲率本身就是图形的几枚保留曲线：钟面、刷新弧、放大镜、地球、信息标、眼睛、齿轮、人像和手；Git 标是尖角的实心菱形。例外只有两处：第三方品牌标与模型标保持各家原样；站点图标 `src/web/public/favicon.svg`（`index.html` 里没有引用它，仍是旧的圆角底板，没有重画，等用户决定是重画成直角还是删掉）。用量环不再是例外，它是方环：一条方形路径上按比例切成的几截平头、尖角的虚线，周长就是 token 总量，段间缺口会被挪开、尽量不落在拐角上（挪开会让某一段短于最小长度时保持原样）。`src/web/lib/corner-system.test.ts` 守着这条（检测器本身在同目录的 `corner-system.scan.ts`，检测器自己的样本自检在 `corner-system.selfcheck.test.ts`；扫非测试的 TS / TSX / HTML 时，只有 `corner-system.scan.ts` 这一份非测试文件按精确路径被排除，写在它里面的圆角声明守卫看不到，它只放检测用的纯函数，这一点目前只靠注释约定）：出现任何圆角声明、圆头线帽或圆形几何，测试就会红；藏在自绘外观后面的原生输入框（单选框、复选框，`opacity: 0` 盖在自绘外观上的那种）也要显式写 `border-radius: 0`——原生单选框自带 50% 的半径，不写，别的扫描就看不见，守卫里有专门的一条扫描。

## MCP 工具

| 工具 | 用途 |
| --- | --- |
| `harnesses` | 哪些执行端可用、模型列表、各项能力与访问级别的验证与强制情况；用户在设置窗口里定义了角色时，末尾逐行列出每个角色此刻能不能用（没有角色就什么也不多写，见“委派角色”） |
| `delegate` | 派发任务，立即返回会话 id 与面板地址；`harness` 与 `profile` 至少给一个（`profile` 是用户在设置里定义的角色名，显式传的参数按字段覆盖它）；可选 `follows="ses_…"` 把它接在某个已有会话后面；传一组 id（数组，最多 8 个）表示汇聚——这件事依赖这几个会话的结果，画布上从每个上级各连一条线；`context` 里除了 `text` / `file` / `snippet` / `url`，还可以放 `{ kind: "session", sessionId }`，把另一个会话真实的最终回答（`include` 还可加改动文件与最后一次失败）原样交给新会话，不必先 `read` 再转述（见“把上游会话的产出直接交给下游”） |
| `wait` | 阻塞等待会话结束、用户直接介入，或某个会话新出现值得留意的情况（默认 30 秒，单次最长 45 秒；传 `attention=false` 则只等结束、介入与新的提问）；会话新提了问题时也会提前返回，每个提问只告知一次（见“子会话的提问”）；超时返回 `Timed out after Ns — nothing has finished yet`（N 是秒数；有的已结束时改写 `only K of M sessions have finished`），没结束的会话（可能在排队、启动、运行或待命）照常继续 |
| `status` | 列出会话与进度；默认不列已归档的会话（末尾一行写明略去了几个），`includeArchived=true` 才列出，点名的 `sessionIds` 一律返回（见“历史会话”一节）；有提问待回答的会话下面写出完整的提问与回复方式 |
| `read` | 读结果（`view="result"`，默认）、完整过程记录（`"transcript"`）、只看失败（`"errors"`）、跑过的 shell 命令（`"commands"`）改动的文件（`"files"`）或整份 Markdown 复盘报告（`"report"`，`scope="tree"` 含整棵任务树，见“导出会话报告（Markdown）”一节）；`runIndex` 只看第几轮运行（报告除外），`afterSeq` 只读某个游标之后新出现或有变化的内容；传 `sessionIds`（最多 20 个）则一次收回多个会话的核心结论、改动文件、耗时与费用 |
| `send` | 中途纠正，或在空闲时继续同一会话；带 `questionId` 时是回答（`answer` / `answers`）或不回答（`decline=true`）会话的提问（见“子会话的提问”） |
| `cancel` | 中断当前运行；`stop=true` 关闭整个会话 |
| `open_panel` | 取得或打开面板地址 |

同一个桥接多个宿主会话时，`status` 默认只看当前会话派发的任务，干预通知也只发给原发起会话；需要全局总览时可显式传 `scope="all"`。执行端意外断线时，排队任务会标为未执行。之后收到新的跟进消息，且原生会话可恢复时，才会重新连接原会话。

**精细读取与增量读取。** `read` 的 `view` 默认仍是 `result`，不带新参数的调用输出与以前一致，只在单个会话的读取末尾多一行游标 `cursor: #<seq>`；例外是回答上面那一行与“还没有回答”那一句，现在按会话所处的局面写（见本段末尾）。除 `result` 与 `transcript` 外有三个只取一个侧面的视角：`errors` 只列真实的失败——会话级错误、失败的工具调用（执行端标了失败或退出码非零，带命令、退出码与输出末尾几行）、警告与错误级别的提示、失败的运行与停止原因、没送达的消息——每条写明第几轮、事件号与时间，最新的排在最前面；“没有结束事件”的工具调用不算失败，只在末尾单独陈述一行；没有失败时明说没有记录到，并附状态行。`commands` 列出分类为 shell 的工具调用（序号、命令原文〔最多 500 字，截断时写明〕、状态、退出码、耗时，多轮时带所在运行），失败的带输出末尾几行；分类不是 shell 的调用（如 OpenCode 代码模式的 `execute`、Claude Code 的 `BashOutput`）不会出现在这里。`files` 每个路径一条（创建 / 修改 / 删除 / 重命名、增删行数，多轮运行时标明哪几轮写过），只有清单没有 diff；行数是把每次编辑上报的数字加起来，与结果视图里“每个路径取最后一条”的口径不同，shell 命令里做的改动不在记录里。所有视角都接受 `runIndex`（从 1 数起），越界时报错并写明有效范围，不会悄悄退回整段。`afterSeq` 取上次读取末尾那个游标，只返回此后**新出现或有变化**的内容：更早开始、之后才结束的工具调用会带着最新状态再出现一次（标 `[updated]`），还在流式输出的文字标明尚未写完；没有新事件时只回一行 `No new events since #N.` 加状态行；超出 `maxChars` 时保留最早的、截掉最晚的，游标停在这一页最后一个事件上并写明还剩几条，下一页从那里接着读；`afterSeq` 大于这个会话最新的事件号时报错，不当成 0。结构化结果里的 `seq` 与游标是同一个数字，`status` 与 `wait` 的会话摘要里也带 `seq`。单个会话的 `result` 视图按此刻的局面分五种写法（措辞是英文，与批量读取一一对应）：运行中的，回答标题是 `Latest output so far (the run is still going; this is not a final answer):`，没有回答时写 `No output yet — the session is still working.`；这一轮已交给执行端启动、还没开始的，标题是 `Output so far (the run is still starting; this is not a final answer):`，没有回答时写 `No output yet — the run is starting.`；一轮都没开始过、第一轮在排队的，没有回答时写 `No output yet — the session is queued and has not started.`（用 `runIndex` 指定了某一轮、排队的正是这一轮时，写 `this run is queued and has not started`）；前一轮已结束、后续一轮在排队的，回答取自前一轮，标题是 `Final answer of run #N (the next run is queued and has not started yet):`（执行端没有把它标为最终回答时是 `Last message from run #N (the next run is queued and has not started yet):`），没有回答时写 `The session produced no assistant text in its last run, and the next run is queued and has not started yet.`；没有任何一轮在进行的（含待命与已结束），标题仍是 `Final answer:` 或 `Last message from the session:`，没有回答时写 `The session produced no assistant text in its last run.`，一轮都没跑过的写 `The session has not run yet.`。前四种里的“没有回答”那一句，后面都还接着一句 ``Call `wait` or check the panel.``。排队与启动都不算“在跑”，所以不会写成“最新输出”或“仍在运行”。这一段措辞对应的改动与测试（`src/mcp/format.phase-wording.test.ts` 等）在 2026-11-24 最后一次完整运行（三份类型检查没有错误、完整测试没有失败）里通过。

**批量读取。** `read` 传 `sessionIds`（最多 20 个，重复的只读一次，不能同时传 `sessionId`，也不能与其他 `view`、`runIndex`、`afterSeq` 合用）就一次收回多个会话：每个会话一块，按传入顺序，写状态、最近一轮耗时、工具调用数与失败数、改动文件数与前几个路径、令牌与费用（各轮合计；执行端没有上报费用时写“未上报”，不写成 $0）、最终回答的开头（被截断时写明并指向单独读取）；没结束的会话按局面分四种写法（措辞是英文）：运行中的，结论一节标 `latest output so far (not final)`、末尾写 `still running — not final`；这一轮已交给执行端启动、还没开始的，写 `starting — not final`；前一轮已结束、后续一轮在排队的，结论取自前一轮并写明是第几轮（`conclusion of run #N`），末尾写 `next run queued — not started yet`；一轮都没跑过的（含第一轮还在排队），写 `conclusion: none — the session has not run yet`，不附“仍在进行”；有值得留意的事时，每种情形都附它的行。`maxChars` 是所有会话合计的预算（默认每个会话 2000 字），内容短的先给足、其余平分，每个会话至少保住固定的几行与一小段结论，预算小到放不下时会明说。某个会话读不到（比如编号不存在）只在它那一块里说明，不影响其他会话。一次最多同时向服务取 4 个会话的详情，每份取回后先压成要点再放手，所以同一时刻在内存里的完整详情（含事件）最多 4 份。`wait` 在所有会话都已结束时，输出末尾多一行提示可以这样一次收回结论，结构化结果不变。这些都在桥里完成，只用服务已有的 `GET /api/sessions/<id>`，新桥配旧服务可用，没有提升 `PROTOCOL_VERSION`；`read` 的 `sessionId` 变为可选（JSON schema 的 `required` 不再包含它），两者都不传时报错。**验证范围**：用真实的 stdio 桥接隔离的服务、以及进程内的假服务两路，把 `read` 的各个视角与参数、批量读取、`maxChars` 截断、不存在的编号、没有结论的会话、已归档与冷会话、含数千个事件的大会话、多轮运行都跑过，并抽样与事件对过账；新桥配旧服务、旧桥配新服务也试过。**没有验证**：真实的 Cursor / Codex 宿主里的端到端。这些验证早于之后的修复与拆分，改动后的代码只由 2026-11-24 最后一次完整运行（三份类型检查没有错误、完整测试没有失败）覆盖。

**按对话区分 Main Agent。** 来源（Main Agent）的 key 是 `<宿主>:<会话标识>`，会话标识取宿主交给 MCP 进程的那个（`_meta`、环境变量）；宿主没有交出时退到 `<宿主>:bridge-<桥进程号>`，这个桥上的所有对话就并成了一个来源。Cursor IDE 就是这样：所有对话共用同一个桥进程，宿主不告诉桥这次调用来自哪个对话。为此八个工具都多了一个可选参数 `conversationId`：宿主没有交出标识的发起端，由 Agent 把自己上下文里看得到的对话（Agent）UUID 原样传进来（`skills/ensemble-delegate/SKILL.md` 里教了这一条）。每次调用各自决定来源，优先级是：宿主 `_meta` > 宿主环境变量 > Agent 自报的 `conversationId` > 桥上一次见到的宿主标识 > `bridge-<桥进程号>`。宿主交出的标识永远压过自报的；自报的标识不记进“桥上一次见到的标识”，所以不会被带到下一次不带 `conversationId` 的调用上，也不会被当成“同一个桥出现了多个宿主标识”的异常。格式要求与宿主标识相同：非空、不超过 200 个字符、不含空白，不合格的值在 MCP 参数校验处就被拒绝。`status`（默认只看当前来源的会话）、`wait`（不传 `sessionIds` 时等当前来源仍在跑的会话）、用户干预通知都按这个 key 区分：两个不同的 `conversationId` 之间互不串；不传参数时与以前完全一样。

自报的标识在来源上记为 `sessionRef.source = "declared"`、证据里是 `declared:conversationId`；网页在来源卡的悬停提示、任务面板与聚焦页头部都写“由 Agent 自报”，不伪装成宿主证据。Ensemble 无法核对它：传错成别的对话的 UUID，就会并进那个来源；每次传不同的值，每个值各成一个来源；传了一个不存在的值，只是多出一个来源，不会出别的问题。没有会话标识、只到桥进程级别的来源，如果名下在跑的会话分处几个不同目录（说明这个桥可能被多个对话共用），`status` 与 `wait`（没有显式 `sessionIds` 时）的输出末尾会多一句提示，建议显式传 `sessionIds` 或 `conversationId`；`wait` 不传 `sessionIds` 时还会先写明它实际在等哪几个会话（`structuredContent.waitedOn`）。

服务端靠 `service.json` 与 `GET /api/health` 里的 `features` 公布自己认得的可协商功能（完整名单以 `src/shared/constants.ts` 里的 `SERVICE_FEATURES` 为准，每新增一项功能就多一个名字，例如 `declared-session-ref`、`delegation-profiles`、`multi-parent`），桥据此决定能不能把自报标识作为 `sessionRef` 发过去。没有这个字段的旧服务，来源校验只认 `mcp-meta`、`env`、`console` 三种 `source`，收到 `declared` 会整条拒绝委派；所以桥发现服务没有这个功能时，不发 `sessionRef`（来源 key 只是个字符串，照样按对话区分，证据与标题也照发），并在 `delegate` 的输出里说明——这时页面上看不到对话标识，也没有“由 Agent 自报”的标注。服务升级、重启之后才完整生效。没有提升 `PROTOCOL_VERSION`（仍是 1）：桥与服务的协议版本必须相等，提升会让正在运行的旧服务被新桥当成不兼容。验证范围：单元与集成测试（假执行端、进程内 MCP 传输、隔离的 `ENSEMBLE_HOME`）；没有在真实的 Cursor IDE 里端到端试过 Agent 是否会照 skill 传这个参数，也没有核对它传的值是否总是该对话的 `composerId`。

`delegate` 的可选参数 `follows`（已有会话的 id，`ses_…`）把新会话接在那个会话后面——例如把修复会话接在代码审阅会话后面。它优先于自动推断，只决定画布上的上级，不改变“谁发起了这次委派”；id 不存在时直接报错，接续的链条计入嵌套上限（2 层；跟随多个会话时取最长的那条链，见下一段）。已经创建的会话可以事后改挂上级，但只有 HTTP 入口：`POST /api/sessions/<id>/parent`，带令牌头 `x-ensemble-token`，请求体 `{"parentSessionId":"ses_…"}`，传 `null` 表示不要上级。服务端拒绝：会话或上级不存在、自己做自己的上级、形成环路，以及会让这个会话或它下游任何会话超过嵌套上限的改挂（不会悄悄截断）；已结束的会话也可以改挂，正在运行的不受影响，改挂不产生消息和运行，只记一条 `session.relinked` 事件，重启或重放后结果一致。没有对应的 MCP 工具，网页上也没有编辑入口。

**多个上级（汇聚）。** `follows` 也可以是一组会话 id（数组，最多 8 个，`LIMITS.maxParents`）：这件事依赖这几个会话各自的结果——例如两路并行的实现做完之后，派一个统一的验收或修复会话；画布因此从“树”变成有向无环图，一个会话可以有多个上级、从每个上级各连一条线。互不依赖的会话不要为了画线而连起来；`follows` 只决定画布上的承接关系，不改变谁发起了委派。
- **数据**：会话 meta、摘要、`session.created` 与 `session.relinked` 里新增可选的 `parentSessionIds`（有序、去重），**只在上级多于一个时才有**；`parentSessionId` 始终是第一个上级（“主上级”）。单上级的会话没有这个字段，事件日志、快照、摘要与响应与原来一字不差；只认 `parentSessionId` 的读者（旧桥、缓存里的旧网页、旧日志的重放）读到的仍是一棵树。读上级一律用 `src/shared/lineage.ts` 的 `parentIdsOf`，写一律用 `parentFields`；同一个文件里还有按最长链分层、可达、成环判断的纯函数，服务端、桥与网页共用，遍历都带访问记录，菱形（两个上级有同一个祖先）里的会话只算一次，数据里即使有环也不会死循环。
- **校验**：不存在的上级一次把缺的全部列出（`404 not_found`）；自己做自己的上级、空数组、超过 8 个、两种写法对不上（同时给了 `parentSessionId` 与 `parentSessionIds` 时，前者必须是后者的第一项；`parentSessionId: null` 与 `parentSessionIds` 同时给）都是 `400 invalid_request`；重复的 id 静默去重，保留先后。
- **层数**：取最长的那条上级链（各上级里最深的那个加一），上限仍是 2；超限的错误点名是哪个上级让链太长（`details.deepestParentId`，MCP 据此提示主 Agent）。
- **改挂**：仍只有 HTTP 入口。`POST /api/sessions/<id>/parent` 的请求体可以是 `{"parentSessionIds":["ses_a","ses_b"]}`（整组替换原来的上级；与 `parentSessionId` 同时给时必须对得上），`parentSessionId` 的老写法（含 `null`）不变。新上级里有它自己或它的后代是环，`409 conflict`；整体判断、整体拒绝，不会写一半；下游会话的层数按最长链重算，任何一个超限就整个拒绝，只有层数真的变了的下游会话才记一条 `cause: "ancestor"` 的 `session.relinked`。重放、重启后结果一致。
- **防重复**：比较的是上级的集合，不看先后；同一组上级换个先后顺序不会造出第二个会话。
- **兼容（没有提升 `PROTOCOL_VERSION`）**：服务在 `features` 里公布 `multi-parent`。新桥 + 旧服务：桥看到没有这一项，只发第一个上级（旧服务本来也会悄悄丢掉不认识的字段），并在 `delegate` 的输出里写明“旧服务只记录了第一个上级”，不报错也不拒绝。旧桥 + 新服务：旧桥的 `follows` 只能是一个 id，行为与原来一样。缓存里的旧网页 + 新服务：旧页面不认识 `parentSessionIds`，只按主上级画成一棵树，不出错，刷新后才完整。旧事件日志 + 新服务：照常重放，没有这个字段就是单上级。旧 `summary.json`（格式 1）+ 新服务：不采信，退回完整重放并按新格式重写（升级后第一次启动，每个冷会话多重放一次，不丢数据）。快照格式因此从 1 升到 2：`parentSessionIds` 当初加进摘要时没有升版本，而它只在汇聚时才出现，旧服务重放汇聚会话后写出的快照缺这个字段，却和单上级的快照长得一样，新服务分不出来，汇聚会话就会在界面上变成单上级。新数据 + 旧服务：旧服务读到的是只有主上级的树。
- **MCP 的呈现**：`follows` 是字符串或数组；找不到的 id 一次全报；显式的 `follows` 仍优先于自动推断；已归档的上级逐个先取消归档；`delegate` 的返回文本列出所有跟随的会话（带标题），多个上级在回执里只写一次：`follows N sessions: id “标题”, …`；跟随多个会话时，`wait` 因会话结束而返回时的详情与 `status` 的 `detail=true` 多一行 `follows: …`（单个会话的 `read` 没有这一行；`read` 的 `view="report"` 的概览表里是 `Parent session` 与 `Also follows` 两行），命中重复委派的回执里也有这一行（那是已有会话自己的详情），新建会话的 `delegate` 回执里没有；单上级的输出不变。
- **取舍与没有回答的问题**（实现时的取舍，用户没有逐项确认）：上限 8；主上级就是第一个；旧服务上降级为“只记第一个并写明”而不是拒绝；不新增 MCP 改挂工具；列表与侧栏里的汇聚会话只出现一次、挂在第一个上级下；归档时汇聚会话要等它的上级都归档了才随之归档（见“归档”）；允许跨 Main Agent 的上级。画布上怎么摆见“页面里有什么”的“汇聚”一条。**验证范围**：服务端、MCP 与网页在隔离的服务里验证过：用进程内的 MCP 客户端接真实的桥、再加无头 Chrome（中文与英文，1440 与 860 宽）；单上级会话的画布、列表、归档、报告与 MCP 输出与没有这一功能的基线比对过（没有差异），层数、环、改挂、三种重放路径（热会话、冷快照、完整重放）、防重复、归档、留存与报告里的处理都跑过，新桥配旧服务、旧桥配新服务、缓存的旧网页配新服务、旧日志与旧快照配新服务、新数据配旧服务也都试过（都不崩）。**没有验证**：真实的 Cursor / Codex 宿主里的端到端、时间线里改挂事件的文案在汇聚下的呈现、触摸拖动、小于 860 的宽度。这些验证早于之后的修复与拆分，改动后的代码只由 2026-11-24 最后一次完整运行（三份类型检查没有错误、完整测试没有失败）覆盖。

**把上游会话的产出直接交给下游（`context` 的 `session` 条目）。** 以前主 Agent 要让一个会话接着另一个会话的结果干活，只能先 `read` 取回结果、再用自己的话转述进新任务：转述会丢字、会改写，还白白占着主 Agent 的上下文。现在 `delegate` 的 `context` 有第五种条目 `{ "kind": "session", "sessionId": "ses_…", "include": ["result", "files", "error"], "note": "…" }`：服务端在派发那一刻读上游会话**自己的原始事件日志**，取出它真实的最终回答、改动过的文件清单与最后一次失败，**逐字**放进下游会话的提示（原文用围栏代码块括起来，一个字符都不改写）。`include` 省略就是 `["result"]`，顺序与重复不重要；`note` 是主 Agent 对这次引用的一句说明，原样放在块里。另外四种条目（`text`、`file`、`snippet`、`url`）与没有引用的委派，行为与以前逐字一致。

- **注入的是什么。** 每个被引用的会话一块，英文（它是写给执行端看的），拼在“Context provided with this task:”之后。下面是三样都要时的样子：

  ````text
  Note from the delegating agent: Review only the parser changes.

  #### Final answer (run 2 of 2)
  ```text

  All tests pass.
  ```

  #### Files changed (2 paths across all 2 runs, as reported by the executor)

  - src/parser.test.ts (created)

  None: no run or session failure was recorded (session phase at sampling: done).
  ````

- **怎么取（直接读原始事件，不读页面上的投影）。** 结果：最近一个有“最终回答”（执行端标了 `phase: "final"`）的运行里它最后写的那一条；执行端根本不标阶段的（例如 Claude Code），取最近一个有无标记文字的运行里最后一条，并在块里写明“这个会话从没把任何消息标为最终回答，这只是它写的最后一条，不一定是结论”；**过程说明（commentary）永远不当作结果**，全是过程说明、没有任何文字、没有任何运行时各有一句原因；取的不是最新一次运行时写明“第 N 次运行没有产出，所以取自第 M 次”。文件：所有运行里 `file.changed` 的并集，按路径去重（顺序是第一次出现的先后，类型取最后一次上报的），只有路径与变更类型、没有 diff，并写明经 shell 命令做的改动可能没有被上报。错误：最后一次失败记录（运行失败，或会话级失败）的原始错误码与消息，写明是第几次运行；一次都没有失败过就写 `None`。请求了、却取不到的部分只写一行说明原因与当时的阶段，不留空，也不编。每个块都带出处：会话编号、执行端与模型、取样时刻、当时的阶段、运行数。
- **什么情况下拒绝（不会悄悄丢内容）。** 上游**还在进行**（启动中、排队、运行中）：`409 context_session_active`，点名编号与阶段——它没有定稿，拿到的只会是半截；MCP 的提示是用 `wait` 等它结束之后再派。引用的会话不存在：`404 not_found`（`details.via` 是 `"context"`，不存在的编号一次说全）。引用的会话个数或整份提示超过下面的上限：`422 context_too_large`（写明各部分占多少）。已结束、失败、已取消、已停止、已丢失与待命的会话都可以引用；已归档的、只在磁盘上的冷会话也可以：只读它的日志，不唤醒、不取消归档。
- **上限（都是实现时的取舍，用户没有确认）。** 一次最多引用 10 个不同的会话（`LIMITS.contextSession.maxRefs`；同一个会话写了几次会合并成一条，要的部分取并集）；一个结果最多 4 万字符，超出时**保留开头**并在块里写明保留了多少、省略了多少、去哪里读全文（`maxResultChars`）；文件最多列 200 个路径，其余写明还有多少（`maxFiles`）；错误消息最多 8000 字符，同样写明（`maxErrorChars`）；**含引用的**委派，任务原文加全部上下文合成后超过 20 万字符就拒绝（`maxPromptChars`）。没有引用的委派不受这些上限影响，也不检查合成后的长度。
- **留在记录里的东西。** 展开后的文本冻结在会话的 `meta.task.prompt` 里（页面上的“实际发给执行端的完整提示”）；`meta.task.context[i]` 存结构化的引用（`sessionId`、规范化的 `include`、`note`）加取样时冻结下来的事实 `sample`（上游当时的标题、执行端、模型、阶段、运行数，各部分取到了多少字符、几个文件、哪次运行的什么错误，取样时刻）和这一块在提示里的字符区间 `block`。**正文不存第二份**：页面按区间从提示里切出来，并核对块的标题，对不上就说找不到，而不是展示错位的文字。上游之后继续运行、改名、被归档甚至被删除，下游记录里的“当时交出去了什么”都不变。请求里自带的 `sample` 会在校验时被丢掉，伪造不了；`meta.task.text` 仍是主 Agent 写的任务原文。
- **入口与呈现。** HTTP `POST /api/sessions` 接受第五种条目，响应里多一个可选的 `contextRefs`（每个被引用的会话一项：取样事实加请求的部分，不含区间）。MCP `delegate` 的说明教主 Agent“直接引用、别读了再转述”，回执在“workspace source”一行之前多一块 `context from a session …`，每个被引用的会话一行（取自第几次运行、多少字符、有没有被截断、几个路径、哪次运行的什么错误），只陈述事实，结构化结果里带同样的 `contextRefs`。聚焦页的“传入的上下文”里是一条可点的引用：标题（上游还在就是链接，点进去用 `#/s/<id>`；已经不在就只剩文字并说明）、执行端标记、交接时的状态与读取时刻，下面是各部分取到了什么，以及一个默认收起的“交接的原文”，展开就是当时交出去的那一块。网页的导出报告里这一条只写事实行（取到多少、读取时刻、当时的状态），不重复正文。`send` 没有 `context`，没有改动；`read` 的输出没有改动。
- **引用不会自己连线。** 画布上的承接关系仍然只由 `follows` 决定；`context` 里有 `session` 条目不会让新会话自动接到上游后面，要画线就同时传 `follows`。
- **与“防重复”的关系。** 含引用的委派判重时只比较“请求了什么”（上游会话编号、规范化后的 `include`、备注），不比较当时取到的内容与取样时刻；展开发生在判重之前，所以上游在两次相同提交之间又开始运行时，第二次得到的是 `context_session_active`，不是“重复”。旧会话的判重行为不变。
- **与 `read` 里“最终回答”的差别。** 这里的取法有意不同于 MCP `read` 用的 `finalAnswer`：（1）以前 `read` 读的投影把助手文字按 `assistant:<itemId>` 做键，而执行端的 itemId 在每次运行里都从头编号，后一次运行的文字会并进前一次同号的条目；现在投影的键带上了运行（`assistant:<runId>:<itemId>`，没有运行标识的老事件仍用旧键），`read` 不再把几次运行拼在一起，所以这一条已经不是差别——这里仍直接从事件里按（运行，itemId）合并，互不串。（2）`read` 只看当前或最近一次运行，那次运行没写文字就没有结果；这里回退到最近一个有最终回答的运行，并写明。（3）没有 `final` 标记时 `read` 退回任意一条最后的文字，包括过程说明；这里不会，写明“没有最终回答”。（4）`read` 会去掉首尾空白，也能读到还在流式输出的文字；这里逐字不动，并拒绝仍在进行的上游。这个差别在“多次运行、不标 final、夹着过程说明”的会话上才看得出来；按 itemId 合并的问题已在投影里修掉（键带运行，见 `src/shared/projection-timeline.ts` 的 `itemKey`）。
- **兼容（没有提升 `PROTOCOL_VERSION`，仍是 1）。** 服务在 `features` 里公布 `"context-session-ref"`。新桥配旧服务：旧服务的校验不认识第五种条目，会把整条委派拒掉、只回一句 “Invalid discriminator value”，所以桥在请求之前就拦下，写明“服务比插件旧，请用户重启 Ensemble，或改用 `text` / `file` 上下文”，绝不悄悄把 session 条目去掉再发（那样下游会话会拿不到主 Agent 以为交出去的东西）；其余四种条目不受影响。旧桥配新服务：旧桥的 schema 里没有这一种，行为与以前完全一样。已经保存的旧会话不改写；网页遇到没有取样记录的引用只说“没有记录当时交接了什么”，遇到不认识的条目类型不画、也不报错。
- **没有验证。** 这一部分没有被单独验证过；除了 2026-11-24 最后一次完整运行（三份类型检查没有错误、完整测试没有失败）之外，没有在浏览器与真实宿主里试过；那次运行之后才重建了 `dist/`（只是把现有源码重新打包，没有改源码），随后打包后的冒烟检查（`scripts/check-bundle.mjs`）通过了，但它只走委派、等待、读取这条主链路，不涉及会话引用。具体地：真实执行端（Codex、Claude Code、Pi、Cursor、OpenCode、DSH）的事件形状——哪些会标 `phase`、itemId 怎么编号、会不会在运行结束时补发只带 `phase` 的完成事件——只是按代码与模拟事件推演，没有对真实会话取过；冷会话读日志只对着假存储测过，没有用真实的历史记录；页面的版式、焦点环与键盘操作没有在浏览器里看过；4 万 / 20 万字符等上限没有对照任何真实模型的上下文窗口；主 Agent 是否真会照说明用引用代替转述，没有在真实宿主里试过。留给用户决定的：要不要允许引用仍在进行的会话、取它“到目前为止”的部分（现在一律拒绝）；引用要不要自动连线（现在不连）；`include` 的默认值（现在只有 `result`）；各项上限。

服务端会挡掉短时间内重复的委派：同一个来源（`origin.key`）在 120 秒内（`LIMITS.duplicateDelegationWindowMs`，从已有会话的创建时间起算）再次提交本质上相同的委派，不会新建会话，而是返回已有的那一个。“相同”指执行端、工作目录（规范化后的绝对路径，Windows 上不区分大小写）、任务原文（去掉首尾空白）、模型与推理档位（省略与写明默认值算相同）、访问级别、上下文与上级会话（跟随多个会话时是上级的集合，不看先后）全部一致；上下文里的会话引用只比较“请求了什么”（上游会话编号、取哪几样、备注），不比较当时取到的内容与取样时刻（见“把上游会话的产出直接交给下游”）；标题不参与比较。只和仍然有效的会话比较：正在启动、排队、运行、空闲待命或已完成的会话算（几十秒内做完、又收到逐字相同的委派，几乎一定是重复提交）；失败、已取消、已关闭、已丢失的不算，所以失败后立刻重试不受影响。判定只看服务里已有会话的记录，不另存任何东西，重启后（会话由事件日志重放）照样有效，重启时被标为“已丢失”的会话不再算；同时到达的相同请求也只会建一个会话。命中重复时不写任何事件、不发消息、不启动运行：`POST /api/sessions` 返回 `200`（新建是 `201`）和已有会话的摘要，响应里多一个 `duplicate: { ageMs }`；MCP `delegate` 的返回文本以 `Not delegated again` 开头，说明那个会话是几秒前创建的、当前阶段，并提醒不要再次委派，`structuredContent` 里带 `duplicate: true` 与那个真实存在的会话的 `sessionId`、`runId`、`panelUrl`。确实要第二个一模一样的会话时（例如对同一份任务并行起多个同款 worker），请求体传 `allowDuplicate: true`，MCP `delegate` 的参数同名。

**委派角色（`profile`）。** 用户可以在设置窗口的「角色」里把一组（执行端、模型、推理强度、访问权限）绑到一个短名字上，比如 `verify`；主 Agent 在 `delegate` 里传 `profile: "verify"`，就按这组配置委派。换了模型世代、或把验证挪到另一个执行端，只在设置里改一次，所有宿主下一次委派都跟着变。`harness` 因此不再必填，但 `harness` 与 `profile` 至少要给一个，都没给时在请求服务之前就报错。`harnesses` 的输出末尾，在用户定义了角色时逐行列出每个角色：名称、执行端、模型、推理强度、访问权限（没固定的项写明 default，并带上此刻实际会用的值），以及 `usable now` 或 `NOT usable now` 加原因；没有角色时一个字也不多写（这段文字每个回合都会进上下文）。设置文件读不了是例外：那不是“没有角色”，会写明角色暂时不可用，也写明这期间委派本身被拒绝，即使显式传了 `harness`（``Roles: unavailable — Ensemble could not read settings.json, so `profile` cannot be used until the user restores the file and restarts Ensemble. Delegation itself is refused until then, even with an explicit `harness`.``）。结构化结果里同样带角色清单（`profiles`，设置文件读不了时是 `profilesIssue`）。

显式传的参数按字段覆盖角色，并且不会把一个执行端的模型悄悄套到另一个执行端上：显式的 `harness` 与角色的不同时，角色的模型与推理强度不继承（它们属于原来的执行端），访问权限继承；显式给了与角色不同的 `model` 时，角色的推理强度不继承（档位是按模型的），显式的模型就是角色那个时强度照常继承；显式的 `effort`、`access` 各自覆盖角色的。角色里没固定的项照原有规则走（模型：用户指定的默认，再回落到执行端自己的默认；推理强度：该模型的默认档位；访问权限：完全访问）。角色里的访问权限只是默认值：显式传 `access` 就覆盖它，没有“锁定”这一档（要不要有，留给用户决定）。`delegate` 的回执里多一行 `role "verify": …`，写明每个字段取自哪里（`from the role`、`from your call`、`by default`），以及角色里写了、这次没用上的取值和原因；`structuredContent.profile` 带同样的内容。用了哪个角色只是这次调用的回执，不写进会话记录，页面上也没有显示它。

角色此刻用不了时，`delegate` 直接拒绝并说明，**不会退回默认值悄悄派发**：名字不存在是 `profile_not_found`（附上用户定义过的角色名），存在但用不了是 `profile_unusable`（写明角色名、原因与出路：用户去设置里改这个角色、主 Agent 显式传参数覆盖有问题的那一项、或不传 `profile`），HTTP 状态都是 422。原因有：执行端这一版不认识或没就绪、访问权限该执行端落实不了、用户没有开放这个模型或这一档推理强度，以及条目本身无效（手改 `settings.json` 造成的）。拒绝只追究“角色里写死的取值”出的问题：用不了的是主 Agent 显式传的值时，不在这一层判，交给委派入口原有的校验给出同一套标准错误；所以 `harnesses` 里说“能用”的角色，委派时不会因为同样的原因被拒，而显式覆盖了有问题的那一项，就不再因为它被拒。设置文件整个读不出来时，所有委派都被拒绝（`model_settings_unavailable`，HTTP 422）——带不带 `profile`、是否显式传了 `harness` 都一样：带 `profile` 的写 `Role "<name>" cannot be resolved: Ensemble could not read settings.json. Ask the user to restore a valid settings file and restart Ensemble; until then delegation is refused, with or without a role.`，不带的在模型校验那一关被拒，写 `Ensemble could not read settings.json. Restore a valid settings file and restart Ensemble before delegating.`。角色是服务端在委派的这一刻才读的，解析与评估只有一份代码（`src/shared/profiles.ts`，服务端、MCP 与网页共用），桥里不缓存角色表，也就没有过期的问题；任何走 `POST /api/sessions` 的调用方行为与 MCP 一致，防重复与已有的全部校验看到的都是解析之后的实际取值，不会被角色绕过。存储与写入口见“数据与隐私”一节的 `profiles` 一条。

服务端靠 `features` 里的 `"delegation-profiles"` 公布自己认得角色。新桥配旧服务（没有这一项）时，带 `profile` 的 `delegate` 在请求服务之前就被拦下并写明原因——旧服务会静默丢掉不认识的字段，角色里的模型、推理强度与只读就悄悄没了——改传 `harness`（与 `model`）照常可用，不带 `profile` 的调用不受影响，`harnesses` 也不会多出角色一栏；旧桥配新服务没有问题，旧桥的 `delegate` 本来就要 `harness`，只是用不上角色。请求发出之后才换了服务的情形也照这条规矩处理：`delegate` 的请求因令牌被拒或连接被拒绝而重试时，客户端会重新发现服务；若这时连上的服务声明的 `features` 与构造请求体时不同（例如换成了更旧的版本），就按新服务把整个请求重新构造一遍，沿用上面全部的拒绝与降级规则（旧服务遇到 `profile` 照样拒绝，自报的 `conversationId` 照样降级并在回执里说明），回执说的也是实际发出的那一份，而不是把按旧服务写的请求体原样重发——否则旧服务会静默丢掉 `profile`，角色里的只读就悄悄变成完全访问。功能没变（服务重启成同一个版本是最常见的）时照旧重发，行为不变。**没有覆盖的缺口**：没有发生重试、但并发的请求在“构造请求体”与“发出请求”之间把客户端缓存的服务换成了旧服务，这种情况不会重建。这个缺陷是读代码推出来的，写了用模拟旧服务的测试来覆盖，没有在真实的新旧服务切换里复现。没有提升 `PROTOCOL_VERSION`（仍是 1）。**验证范围**：服务端、MCP 桥与设置窗口的「角色」分区在隔离的服务（真实的 stdio 桥）加无头 Chrome 里验证过：服务端的增删改与各个错误码、手改 `settings.json` 造成的各种有问题的条目、不可用角色的原因、`harnesses` 末尾的角色清单（没有角色时与老桥的输出逐字相同）、`delegate` 的回执与继承规则、网页的键盘操作与中英文，以及新桥配旧服务、旧桥配新服务。**没有验证**：真实的 Cursor / Codex 宿主里用 `profile` 委派（也没有看主 Agent 会不会照 Skill 的建议选角色）、输入法组字期间的 Enter（只有单元测试）、桌面 Chrome 里原生下拉弹层的样子。这些验证早于之后的修复与拆分，改动后的代码只由 2026-11-24 最后一次完整运行（三份类型检查没有错误、完整测试没有失败）覆盖。

**子会话的提问（`question`）。** 被委派的会话遇到需求歧义时，可能停下来问一个问题（Codex 的 `item/tool/requestUserInput`、OpenCode 的 `question`）。这和“授权”是两回事，两条路径互不相干：授权请求（Codex 的 `item/commandExecution|fileChange|permissions/requestApproval`、OpenCode 的 `permission.asked`）仍由 Ensemble 当场应答（Full Access 放行、只读拒绝），从不等人，也从不进入下面的提问机制，会话仍然没有“等待授权”这个状态；提问则是会话在等一个**答案**，直接拒绝它只会让会话瞎猜、返工。用语固定为“提问 / 待回答 / 回答 / 不回答 / 过期”，界面、事件与 MCP 的文字里都不出现“授权、批准、允许、拒绝”。

- **记录与呈现。** 提问是事件日志里的两种记录：`question.asked`（执行端的问题原文、可选项、能不能自己写，经脱敏与长度上限处理）与 `question.resolved`（`answered` / `declined` / `expired`，附谁、何时、回复的投递状态与原因）。时间线上的“提问”卡原地从待回答变成结局，重启与重放后一致；没有新的存储文件、没有新的设置、没有新的会话阶段（会话仍是“运行中”，画布节点的状态呈现不变）。有待回答的提问时，会话摘要带 `openQuestions`。待回答期间它同时是一条“值得留意”（`question`，措辞是“提问待回答：问题（已等待 …）”）：Agent 卡头部的琥珀标记、聚焦页摘要最上面的分区、`status` 的 `attention:` 行都是它；这期间同一个会话不再报“长时间静默”与“工具长时间无消息”（安静是因为在等人）。已经有结局的提问不再算“值得留意”，只留在时间线上。
- **`wait`。** 第一次告诉主 Agent 有新提问时提前返回（返回的第一句是 “Session … is asking a question and waiting for an answer”，结构化结果的 `raised` 里带 `questionId`），即使传了 `attention=false`——提问是一个请求，不是“可能出了问题”的迹象。同一个提问只告诉同一个发起端一次：服务端按来源记着“已告知”的提问编号（只在响应真的交出之后才记，每个来源最多 200 条，存在内存里），没有回答时再次 `wait` 不会立刻又返回；`status` 与 `read` 在它待回答期间一直显示完整的提问。这改掉了一个陷阱：`wait` 原本把“开始等待那一刻已存在的提示”当基线，提问若出现在两次 `wait` 之间就永远唤醒不了它；现在提问不进基线，改按“这个来源是否被告知过”判断，代价是服务端多记一份小的内存状态。用户在网页上回答之后，主 Agent 的 `wait` 是因为那条用户介入通知返回的（原因 `notice`），不是因为提问。
- **回复。** MCP 没有新增第九个工具：`send` 多了可选参数 `questionId`、`answer` / `answers`、`decline`，带 `questionId` 时 `text` 变为可选（不带时仍必填）。`answer` 用于只有一个问题时，`answers` 每个问题一项、按顺序（多选用数组）；回答必须取给出的选项标签（大小写与首尾空白宽容，按原标签送出），提问写明“可以自己写”时才允许写自己的话；`decline=true` 是不回答——会话被告知“对方选择不回答，请自行做合理假设并继续”，`text` 在这里是附给它的一句备注。HTTP 是 `POST /api/sessions/<id>/questions/<questionId>/answer`（请求体 `{ "answer": … }` 或 `{ "answers": […] }`）与 `…/decline`（`{ "note": "…" }`，可省），回执是 `{ questionId, status, outcome, summary }`；网页的提问卡（单选、多选、自填文字，以及“不回答，让它自行判断”）调用的是同一组接口。
- **回复的真实性。** 先把回复交给执行端，成功了才记 `question.resolved`；`delivery: "handed_off"` 的意思是“已交给执行端”，不等于它读到并采纳了。执行端已经不再等待这个提问（这一轮结束、被撤回、进程没了）时，回复不会假装送达：返回 `409`，同时把提问记为过期（原因 `not_waiting`）。同时到达的两个回复只有一个会被送出，另一个得到 `409`（`details.status` 是 `open`）；提问已有结局后再回复同样是 `409`，`details` 里带原来的结局（谁、何时）。执行端拒收这个答案是 `400`（提问仍然待回答；回复在途时若一小时的时限已经到点，回复被拒后提问随即按 `timeout` 过期，不会一直开着），这个执行端不接收回复是 `422 question_unsupported`。会话是主 Agent 发起的、而回答或不回答是用户在网页里做的，会作为一条用户介入通知同步给主 Agent（出现在 `status` / `wait` / `send` 的 `notices` 里）；主 Agent 自己回答的不再通知它自己。
- **过期。** 所属运行结束或被取消、会话被关闭或失败时，提问记为过期（原因分别是 `run_ended`、`cancelled`、`session_closed`；执行端自己撤回的是 `withdrawn`，Ensemble 重启而断开的是 `restarted`）。**一小时**（`LIMITS.question.timeoutMs`，固定值、不是设置）没人回答时，Ensemble 告知执行端“没有人能回答，请自行做合理假设、说明，然后继续”，再把提问记为过期（原因 `timeout`）；这个执行端不接收回复时只记过期、不投递。时限到点时若正好有回复在途，先让那个回复走完：被收下就以它的结局为准；被执行端拒收（提问仍待回答）时，早已到期的时限立刻补上，同样记为过期（原因 `timeout`；执行端那时若已不再等待，则与上面一样记 `not_waiting`）。这个时长是实现时的取舍，不是用户确认的。
- **机密类提问不转交。** Codex 标了 `isSecret` 的提问（例如要一个令牌）整个不转交：立刻回给执行端“走不通”，事件日志里只留一条 `codex.question_secret` 诊断（只写“这是一个机密类提问”，不含问题文字），问题文字不进日志、网页与 MCP。这条诊断是固定的一句话，连标题也不引用；没有进行中的运行、或请求里 `isBlocking: false` 时同样如此。判断读的是原始条目、先于对条目的解析：请求里只要有一条标了 `isSecret`（缺 `id` 或问题正文、转交读不出的条目也算），整个请求就按机密类处理，其余条目不转交，机密条目也不会悄悄消失。退回老办法的那条诊断（`codex.question_unanswered`；没有接入转交、转交没有接手时才会走到）同样不引用机密类条目的任何文字，只写有几个机密类提问、文字没有记录；其余条目的问题原文先脱敏，再压成一行并截到 300 字。接上转交时（`codex.ts` 总会接上），含机密条目的请求在解析条目之前就被拒绝，走不到这条诊断；它对机密类条目的那段处理是纵深防御，只对没接转交的调用方（测试、将来的代码）起作用。
- **哪些提问会转交。** Codex 的 `item/tool/requestUserInput` 与 OpenCode 2.3.0 的 `question`（它的 `form` 事件）。转不了的（读不懂形状、没有进行中的运行、标签经脱敏或截断后与原文对不上、超出条数上限）退回过去的做法——回给执行端“这条路走不通”并留一条诊断（引用的问题原文或标题先经脱敏），不悬着等人（OpenCode 的 `form` 另附一句请它自行判断的说明）。Codex 的 `mcpServer/elicitation/request` **没有改**，仍然取消并记 `codex.elicitation_cancelled`：它来自某个 MCP 服务器，是一份任意的 JSON 表单（也可能是跳转链接或凭据），不是“模型问用户一个问题”，单选 / 多选 / 自填的提问卡表达不了，混进来只会把两类东西搅在一起。访问级别不影响提问：只读会话也可以提问（只读限制的是写入，不是问话；这是实现时的取舍，留给用户决定）。
- **兼容（没有提升 `PROTOCOL_VERSION`）。** 服务在 `features` 里公布 `session-questions`，新桥的每个请求都带 `x-ensemble-accepts: session-questions`。新桥配旧服务：回复前先查 `features`，没有就在请求服务之前拦下并说明“服务比插件旧，不能回复提问，请重启 Ensemble”，普通 `send` 不受影响。发送时令牌被拒或连接被拒、因而重新发现了服务，而它的功能与之前不同（换成了不认识提问的旧服务）时，回复在发出前再被拦一次并同样说明，而不是撞上 404。旧桥配新服务：旧桥不认识提问，服务端不会把提问放进给它的 `attention` 与 `wait` 里，它的 `wait` 也不会因提问返回——**旧桥发起的会话遇到提问时，主 Agent 看不到它，会话要等到一小时的超时兜底，除非用户在网页里回答；这段时间它还占着一个并发名额。**只有升级插件（让主 Agent 用上新桥）才能消除这一点。这个占用最长等于提问的超时（每个提问各算一次），用户在网页里回答即可提前释放；用缩短到 4 秒的时限实测过：并发上限设为 2、两个旧桥会话停在提问上，第三个会话排了约 4.6 秒才启动。
- **验证范围，以及没有验证的。** 只对着模拟的 Codex 与 OpenCode 验证过：用真实的 stdio 桥接隔离的服务、再加无头 Chrome，转交、回复的各种形态、同时回复的竞争与撤回、超时兜底（把时限缩到几秒实测）、`wait` 与值得留意、新桥与旧桥对新旧服务的组合都跑过；执行端“已不再等待”（`not_waiting`）只有单元测试，没有在端到端里构造出来。这些验证早于之后的修复与拆分，改动后的代码只由 2026-11-24 最后一次完整运行（三份类型检查没有错误、完整测试没有失败）覆盖。协议形状的来源与可靠程度：Codex 的请求形状取自 `vendor/` 里生成的协议类型（协议里标着 EXPERIMENTAL，字段以后可能变），回复体 `{ answers: { <问题 id>: { answers: [标签…] } } }` 则是从 Codex 二进制里的结构名（`ToolRequestUserInputAnswer`）推断的；自填文字按普通字符串给（Codex 自己的 TUI 会给备注加 `user_note: ` 前缀，这里没有照做），是否被原样接受没有核对，请求里 `isBlocking: false` 时会退回旧做法；OpenCode 的 `form`（回复 `POST /api/session/<sid>/form/<fid>/reply`，体是 `{ answer: { q0: 文字 | 文字数组 } }`；不回答 `DELETE …/form/<fid>?message=…`）读自 2.3.0 的随包源码。两个执行端的转交都只对着模拟的 Codex / OpenCode 验证过（测试里的），没有在真实的 Codex 或 OpenCode 上触发过提问；真实的 Codex 是否还会为 `request_user_input` 的调用另发一个工具条目（那样提问原文会随工具输入进入事件日志）也没有核对。

**OpenCode** 为每个会话启动一个私有的 `opencode serve --stdio`（只监听 127.0.0.1、随机端口、每个进程一个随机密码，标准输入一关就退出；不碰你可能已经开着的共享服务），经它的 HTTP 接口加 SSE 事件流驱动完整会话。没有用 ACP（没有运行中补充输入）或 `opencode run --format json`（不能纠偏，也没有优雅取消）。访问级别在创建会话时以会话级权限规则写入，不修改你的 `opencode.json`，也不等任何批准；只读只放行 `read` / `glob` / `grep`，其余工具对模型隐藏，提问类的 `question` 在两种级别下都放行，而且不当作授权：Ensemble 把它转交给用户或主 Agent 回答（见“子会话的提问”），转交不了的才撤回并请它自行判断，免得运行悬在没人回答的问题上。取消时 OpenCode 自带的中断只能结束 shell 工具那一层，它启动的子进程会变成孤儿（Windows 上实测），所以 Ensemble 先按 pid 结束整棵进程树（pid 来自事件与 `GET /api/shell`）再发中断，会话仍可继续；服务关闭时同样先停掉运行与工具进程。“结束整棵进程树”在 Windows 上是 `taskkill /T /F`（已验证）；在 Linux 与 macOS 上由 `src/server/executors/process-kill.ts` 实现，**已实现并有测试，但没有在真实的 Linux 或 macOS 上验证过**：读进程表沿父子关系找出全部后代，先对它们发 SIGSTOP 冻结，再读一遍表把新出现的后代也冻结（进程表只是快照，不冻结的话，读表与发信号之间新 fork 出来的子进程会漏网），直到一轮里没有新进程为止——最多 6 轮、冻结阶段总共不超过 3 秒，超过说明这棵树 fork 得比冻结还快，就不再追，带着已知的进程直接结束，并在结果里标明没有收敛——然后统一发 SIGKILL，再用进程表确认它们真的消失了（已死但还没被回收的僵尸不算活着）。每个信号发出前都核对“进程号加起始标记”仍是读表时看到的那个进程（进程号会被复用）；不对进程号 ≤ 1、Ensemble 自己与它的祖先发信号；没有读表时看到的“当初的样子”作凭据时，目标必须是服务进程的后代；读不了进程表就退回只对这一个进程发信号，并如实标出没有处理它的后代。取消与关闭路径是强制的（不先发 SIGTERM，与 Windows 的 `taskkill /F` 对齐：OpenCode 取消时要等根进程消失才发中断，SIGTERM 的宽限只会把这一刻往后推）；只有执行端进程自己的关闭（已经关了标准输入、等过 0.9 秒还不退）保留一步最多 1.5 秒的 SIGTERM，给带信号处理的 CLI 一次落盘的机会。需要 OpenCode 2.x（`npm install -g @opencode/cli`）；Windows 上会依次在 PATH、npm 全局目录里的平台包与官方安装目录里找真正的 `opencode.exe`，也可用 `ENSEMBLE_OPENCODE_BIN` 指定。模型与档位取自 OpenCode 自己的模型目录，默认模型也由它给出；会话留在 OpenCode 自己的会话库里，标题是委派标题；每个私有服务占用约 145–281 MB 内存。已在 Windows 11、OpenCode 2.3.0 上用真实免费模型验证的有：探测、模型与档位、文本 / 推理 / 工具 / 命令 / 文件变更 / 用量事件、中途纠偏、取消后继续、第二轮续聊、服务重启后恢复同一个原生会话、只读强制、Full Access 无授权、嵌套委派的环境变量、中文与带空格的工作目录。**没有验证**的：用你自己的 OpenCode 配置（多个提供商、MCP、插件）运行——私有服务会像平时一样加载那份配置，其中的插件与 MCP 服务会随每个会话各起一份；上下文压缩期间的用量；子 Agent（`task` 工具）开出的子会话在取消时的行为；`delivery: "queue"`；Linux 与 macOS（整个适配器都没有在这两个系统上跑过；取消路径上具体没有验证的有：OpenCode 的中断是否同样只杀 shell 那一层；shell 工具的根进程是否一定是服务进程的后代——不是的话（比如 PTY 里双重 fork 脱离了父子关系），上面的杀树会拒绝动手并标出原因，而不是猜着去杀；冻结收敛在构建、测试这类大量 fork 的真实工具下的耗时与是否有漏网）；经 `.cmd` 外壳启动（只解析、不运行，本机装的是平台包里的真实 exe）。

**DSH**（DeepSeek Harness，`npm install -g @deepseek-ai/dsh@latest`）经官方的 `dsh --profile acp` 驱动：每个会话一个私有的 dsh 进程，以会话的工作目录启动（它的沙箱工作区根取自进程目录），走 ACP v1（stdio 上的 JSON-RPC 2.0）。没有选官方 SDK 接口，因为它没有取消，也拿不到一轮对话的结束结果。权限不靠询问：启动时把环境变量 `DSH_PERMISSION_MODE` 设成 `danger-full-access`（Full Access）或 `read-only`（只读），它盖过你 `settings.yaml` 里的权限设置，所以不改动你的任何 dsh 配置（实测工具的子进程里读不到这个变量）；万一仍收到 `session/request_permission`（实测只有只读会话里模型自己申请提权时才会出现），Full Access 只选“允许一次”、只读选“拒绝一次”，并记一条诊断，不弹窗也不等人。dsh 的更新是整块提交的（没有逐字流），第一次模型调用返回之前它不发出任何事件，所以一次运行要等到第一条更新才记为“已开始”（否则第一次调用就 401 时，模型根本没见过这条消息，却被记成“已生效”），这段时间页面显示“正在连接”。dsh 一次只接受一个 prompt，运行中再发一条会被拒绝（`-32602`），文字不会被注入，所以中途纠偏只能排到这一轮结束后作为新的运行发送，记为“已排队”，不会写成已生效。

取消用 `session/cancel`：dsh 几十毫秒内就会让这一轮以“已取消”收尾，会话照常继续；但它只结束工具的那层 shell，工具启动的子进程会变成孤儿（前台子进程、`cmd /c`、再 spawn 的 node、`Start-Process`、`Start-Job` 五种启动方式都实测到）。所以 Ensemble 在发出取消之前先读一次进程表，给 dsh 的后代拍快照（只在有工具运行时做，超过 9 秒就不等并留一条诊断；Windows 上读一次通常 1–4 秒），运行结束后只结束快照里仍然存活、父进程已经没了的进程（按进程号加创建标记核对，不会误伤新进程或无关的后台进程；“父进程已经没了”看的是快照里记的那个父进程现在还在不在，不看这个进程现在的 ppid，因为 Linux 与 macOS 上孤儿会被 init 或 subreaper 收养、ppid 变成 1，而 Windows 上 ppid 不变），结果记成诊断；代价是在 Windows 上从点取消到页面显示“已取消”实测 0.8–4.6 秒，孤儿在那之后约 2 秒内被清理。运行中关闭会话（例如服务退出）则直接结束整个进程树（Windows 上实测约 0.5 秒，工具的子进程一起结束）；dsh 在标准输入关闭后虽然也会自己退出，但会把工具的子进程留下，所以不走那条路。

**孤儿清理在各平台上的现状**：Windows 的孤儿现象与清理都在真实系统上用真实 dsh 验证过（上面带数字的都是 Windows 的实测）。Linux 与 macOS **已实现、有测试，但没有在真实系统上验证过**（编写时没有运行过任何代码，macOS 更是没有可用的环境）：进程表在 Linux 上直接读 `/proc`（不依赖 `ps`，最小的容器里也有；创建标记取 `/proc/<pid>/stat` 的 starttime，不用换算出来的墙钟时间，免得系统校时后活着的父进程被认成已死、进而误杀它的子进程），在 macOS 上跑 `/bin/ps -axww -o pid=,ppid=,stat=,lstart=,comm=`（`LC_ALL=C`，创建标记取只到秒的 `lstart`；这个输出格式是按 BSD ps 的文档与样例写的，没有在真实的 macOS 上核对过）。两边都把僵尸与已退出的进程排除在表外，并在读完表之后自检——表里必须有 Ensemble 自己、它的父进程要对得上，否则整份表作废。读不了、读不全（比如 `/proc` 里某个进程读失败，而不是“刚好退出”）、读出来对不上，都退回“不清理”并留一条 `dsh.sweep_skipped` / `dsh.sweep_failed` 诊断，绝不猜着动手。结束孤儿时用上面 OpenCode 一段说的办法结束它和它的后代，并在发信号前拿快照里看到的样子再核对一次身份。dsh 与 OpenCode 在这两个系统上是否真的会留下孤儿没有观察过：清理只在快照里有孤儿时才动手，没有孤儿就什么都不做。其它系统（BSD、Solaris、AIX 等）不清理，也不声称做了：`defaultProcessTools` 在那里返回空，`killTree` 只能对那一个进程发信号。

会话由 dsh 自己每轮落盘，服务重启后用 `session/resume` 在新进程里恢复同一个会话（历史、模型与推理档位都在，不会新建会话）。模型与推理档位取自 dsh 自己的配置目录（逐个模型切换读出各自的档位），默认模型也由它给出：本机默认只有 `deepseek-official/deepseek-v4-flash`，档位 off / low / high / max（默认 high）；acp profile 不读 `settings.yaml` 里的模型与提供商；指定了不存在的模型会明说并列出可用的，不会悄悄换成默认模型。探测会起一个临时的 acp 进程（`harnesses`、`doctor` 与设置窗口都用它，在后台进行，约 10–20 秒），并用 dsh 自己的 `--patch` 把会话存储与会话索引挪到临时目录、探测完就删掉，不会在你的 `~/.dsh` 里留下会话。dsh 第一次使用 `acp` profile 时会在 `$DSH_HOME/profiles/acp` 里做一次性初始化（本机实测通常 5–8 秒，电脑刚重启后的冷启动到过 28 秒），并在 `$DSH_HOME` 里留下它自己建的 `.anonymous-user-id`（Ensemble 不读它，也没有核对它的用途）。可执行文件依次从 `ENSEMBLE_DSH_BIN`、PATH、npm 全局目录里找；找到的是 `.cmd` 外壳时直接用 `node` 运行它指向的 JS 入口，不经 `cmd`。Ensemble 不读取、不保存 DeepSeek 凭据：dsh 自己读（`dsh web` 的 Settings → Models 或 `DEEPSEEK_API_KEY`），没配时第一轮会以 `auth_failed` 失败，dsh 的原文会说明怎么补。

已在 Windows 11、dsh 0.2.2-rc.1、Node 22.22.2 上用脚本化的假模型端点验证的有：探测（含模型与档位、探测不留痕）、文本 / 推理 / 工具 / 命令 / 退出码 / 文件变更 / 待办 / 用量事件、模型与档位的设置与报错、中途纠偏排队、取消后继续、五种启动方式的孤儿清理（无关的后台进程不受影响）、运行中关闭、第二轮续聊、服务重启后恢复同一个原生会话、只读强制（含只读下的提权申请被拒绝）、Full Access 无授权、嵌套委派的环境变量（会话里的 shell 工具读得到 `ENSEMBLE_PARENT_SESSION` 与 `ENSEMBLE_PARENT_DEPTH`）、上游 401 的错误形态。**没有验证**的：真实的 DeepSeek 模型运行（没有凭据）与它的用量口径；真实的 429 / 5xx 重试表现（只在直连 ACP 时用假端点看到过，约 15 秒后失败）；用你自己的 `~/.dsh` 配置（插件、MCP 服务）运行；`delivery: "queue"`；Linux 与 macOS（整个适配器都没有在这两个系统上跑过；取消后的孤儿清理已实现但没有验证，具体没有验证的有：dsh 在这两个系统上取消时是否同样只杀工具的 shell 那一层、会不会真的留下孤儿；Linux 上读 `/proc`、macOS 上解析 `ps` 输出在真实系统上的表现，尤其是 macOS 的列格式、日期格式与时区；冻结后统一结束整棵进程树的办法在真实工具进程树上的耗时与是否漏网；没有会回收孤儿的 init 的容器里僵尸进程的处理）。

文件变更只统计执行端明确报告的（Pi 的 `write` / `edit`、Codex 的 `apply_patch`、Cursor 的编辑类工具、Claude Code 的 `Edit` / `MultiEdit`、OpenCode 的 `edit` / `write`、DSH 的 `write` / `edit`）；通过 shell 命令写入的文件不会被逐个列出。

## 宿主里的实际行为

下面是用真实 Codex 0.151.0（Windows 11）做端到端检查得到的，Cursor 一栏明确标注了没有验证的部分。

**Codex 作为发起端**

- 识别：Codex 在每次 MCP 调用的 `_meta` 里带 `x-codex-turn-metadata`（含会话编号、模型、沙箱模式），Ensemble 据此显示“由 Codex 的某个会话派发”，并把同一会话的多次调用归到一起。
- 授权：`delegate` 的标注写在 `src/mcp/delegate-tool.ts`，其余七个工具的标注写在各自的文件里（`src/mcp/status-tool.ts`、`wait-tool.ts`、`read-tool.ts`、`send-tool.ts`、`cancel-tool.ts`、`panel-tool.ts`（`open_panel`）、`harnesses-tool.ts`）。`delegate`、`send`、`cancel`、`open_panel` 标为 `readOnlyHint: false`、`destructiveHint: false`、`openWorldHint: false`（`cancel` 与 `open_panel` 另标 `idempotentHint: true`）；`status`、`wait`、`read`、`harnesses` 标为 `readOnlyHint: true`、`openWorldHint: false`，不写 `destructiveHint`。它们只和本机的 Ensemble 服务通信，`cancel` 只中断运行或关闭会话、不删除任何东西。2026-11-08 用真实 Codex 0.151.0 做了一次隔离检查（`codex exec --ephemeral --ignore-user-config`，批准策略 `on-request`；`exec` 是非交互的，需要批准的 MCP 调用会被直接拒绝）：`delegate` 与随后的 `cancel` 都直接完成，没有被要求批准。更早的版本里 `delegate` 标注过 `openWorldHint: true`，在批准策略为 `never` 的 `codex exec` 里被 Codex 以 “MCP tool call requires approval” 拒绝，所以这条标注是有实测依据的。实测只覆盖了 `delegate` 与 `cancel`，其余六个工具的标注只是代码里的声明，没有逐个在 Codex 里试过。没有验证的：Codex 交互界面里是否仍会提示、通过插件安装的服务器是否使用同一个配置路径、其他宿主的批准策略。
- 工作区：Codex 没有通过 MCP `roots` 告知工作区。按 Agent Plugins 约定，插件的 MCP 服务默认在插件根目录启动，所以委派时必须传 `cwd`；在插件安装目录里启动、又没有 `cwd` 时，`delegate` 会直接拒绝，而不是把一个可写会话放进插件目录。桥从用户主目录或磁盘根目录启动（Cursor 就是这样：它起的插件进程被所有窗口共用，默认目录是主目录）、宿主又没有可信的工作区报告、也没有 `cwd` 时同样拒绝。`cwd` 传空串或只含空白，按没传算，与省略完全一样。Skill 和工具说明都要求主 Agent 传入项目目录。
- 服务寿命：实测 Windows 上 Codex 退出时会连同 MCP 进程的整棵子进程树（包括 detached 子进程）一并终止，Ensemble 服务也随之停止，未完成的运行会在下次启动时被如实标记为“已中断”；已经完成的会话保持原样，后续消息会按需恢复到原生会话。这在预期之内：服务的存活跟随宿主，不额外做常驻（你已确认）。需要常驻时自己运行 `node dist/ensemble.mjs serve`（或 `open`），桥会发现并复用它。

**Cursor 作为发起端**：只做了加载器代码审阅，没有真正在 Cursor 里重新加载并调用过。已知 Cursor 只展开 `${CURSOR_PLUGIN_ROOT}` / `${CLAUDE_PLUGIN_ROOT}`、不展开 `${PLUGIN_ROOT}`，所以包里带了 `.cursor-plugin/plugin.json` 与 `.mcp.json`。支持某个 Harness 作为发起端，不等于它已经能作为执行端：Cursor 作为执行端走的是 SDK 适配器，上表已说明其验证状态。

```text
ensemble <命令>                                （从源码目录运行时写作 node dist/ensemble.mjs <命令>；`ensemble` 是 npm 包的命令名，见“开发”一节）
```

## 历史会话：冷热分离、归档与留存

会话越攒越多（几百个会话、几百 MB 的事件记录）时，服务不该每次启动都把它们全部重放进内存，界面与 MCP 默认也不该被早已结束的会话淹没。这一节说明服务端与 MCP 桥怎样处理，以及这些做法的边界。**验证范围**：服务端与 MCP 桥在隔离的服务里验证过，并用真实历史记录的一份副本（在临时目录里，原件没动）与合成的历史起过服务、导出过报告：启动与内存、快照的校验与回退、冷热切换（读取不会解冻会话）、归档规则与落盘失败时的回滚、留存清扫、新桥与旧桥对新旧服务的组合。**没有验证**：真实的 Cursor / Codex 宿主里的端到端。这些验证早于之后的修复与拆分，改动后的代码只由 2026-11-24 最后一次完整运行（三份类型检查没有错误、完整测试没有失败）覆盖。

**会话目录里的文件。** `<ENSEMBLE_HOME>/data/sessions/<会话>/` 里除了 `events.jsonl`（按会话追加的事件记录，仍是唯一的事实来源），还可能有两份派生文件，都用“先写临时文件再改名”的方式原子写入（临时文件在同一目录下、名字独一无二；Windows 上遇到 `EPERM` / `EBUSY` / `EACCES` 会重试，最终失败时清掉临时文件；`settings.json` 的写盘也用同一个写入器）：

| 文件 | 内容 | 丢了或坏了会怎样 |
| --- | --- | --- |
| `summary.json` | 摘要快照：格式版本（`SNAPSHOT_FORMAT`，目前是 2）、服务算好的会话摘要、最后一条事件的序号、写快照那一刻 `events.jsonl` 的字节数、当时尚未送达主 Agent 的通知条数 | 只是缓存：缺失、损坏、版本不符、或与日志对不上时，服务退回完整重放，什么也不会丢，随后按新内容重写 |
| `archive.json` | 归档标记 `{ "archivedAt": "…", "by": "user" 或 "retention" }` | 不是事件（不占序号、不改会话的更新时间）；删掉它就是取消归档；丢了只是这个会话回到默认视图 |

任何一步都不会删除或改写 `events.jsonl` 里已有的内容（读取时本来就有的两种修复除外：补上缺失的结尾换行、补一条说明记录不完整的诊断事件）；删除会话仍然只发生在用户明确删除时。归档不改变会话的状态与记录。

**冷热分离（默认，`ENSEMBLE_HISTORY_MODE=lazy`）。**

- **热会话**在内存里有完整状态与事件：进行中的（有运行在启动 / 排队 / 运行，或有消息还没被执行端确认）、还有待回答的提问或未送达主 Agent 的通知的、被 `SessionManager` 持有运行时连接的、以及最近 10 分钟（`LIMITS.history.warmMs`，取值明显大于 120 秒的防重复窗口）内有过事件或被取用过的。**冷会话**只在内存里留一份摘要快照，事件日志留在磁盘上。热会话在事件中枢里是一条 `HotSession` 记录（`src/server/session-residency.ts`），冷热切换时整条换掉；启动时读快照与读归档标记各自最多 8 路并行，限流用 `src/shared/map-pool.ts` 的 `mapPool`。事件中枢本身是 `src/server/hub.ts` 的 `EventHub`，它持有按会话 id 索引的各张表，冷热切换、事件写入、查询、启动载入都在这里；不持有这些表的几块在同目录：类型与常量 `hub-types.ts`、订阅与派发（含重入规则）`hub-dispatch.ts`、归档标记的落盘与失败回滚 `hub-archive.ts`（标记表仍归 `EventHub`，`setArchived` 把它交给这里做回滚）、快照的写与启动时的读 `hub-snapshots.ts`、事件区间切片与流式增量同流判断 `hub-events.ts`。
- **启动**：并行读各会话的 `summary.json` 并校验——格式版本、会话 id、`lastSeq` 与摘要里的序号一致、关键结构齐全、会话是稳定的（没有进行中的运行或待确认的消息）、没有未送达的通知、已过 10 分钟保温期，并且 `events.jsonl` 此刻的字节数等于快照记下的字节数（只 `stat`，不读日志；这证明快照对应日志的当前末尾）。都通过的直接登记为冷会话，其余的（缺失、损坏、对不上、还在保温期……）照老办法完整重放；重放之后已经可以冷存的，就地写好快照再放掉。**升级后第一次启动**没有任何快照：服务一个会话一个会话地处理——重放、写快照、放掉——所以内存峰值是最大的那个会话，而不是全部历史；之后的启动只读快照。启动日志的 `sessions loaded` 一行写明热 / 冷 / 已归档的数量、载入方式与耗时。
- **运行中**：后台清扫（每 60 秒，`LIMITS.history.sweepMs`；定时器不阻止进程退出）把过了保温期的稳定会话写好快照再放出内存。放出之前把条件整个重新核对一遍（同一份状态、序号没变、仍允许冻结），任何一项变了就放弃这一轮。**持有运行时连接的会话不会被冻结**：运行时在一次运行结束后仍然连着，直到会话被关闭、连接断开或服务退出，所以刚跑完的会话要等到那之后才会变冷（见下面的限制）。事件日志写盘失败过的会话同样不会被冻结（见下面的限制）。
- **用到时**：需要完整状态的操作（补充消息、停止、取消、改挂上级等）先把会话载回内存（并发的请求合并成一次）；只读的使用（会话详情、事件、`wait`、摘要、列表）不载回：详情与事件直接读日志文件，经一个最近读取的缓存（`LIMITS.history`：最多 8 个会话、合计 64 MB，缓存按日志字节数核对是否过期）。万一有代码路径没先载回就写了冷会话，事件不会丢：先载回、再按原来的次序补记，并在服务日志里记一条警告。
- **一致性**：冷会话与热会话对外的摘要内容相同（`attention` 除外：它只有热会话才有，冷会话是已结束的稳定会话，本来就没有）；删除会话时一并清掉它的快照、归档标记与缓存。`GET /api/health` 的 `sessions` 是全部已知会话（含冷的与已归档的），另有 `sessionsHot` 与 `sessionsArchived`。
- **逃生口**：`ENSEMBLE_HISTORY_MODE=eager` 回到老办法（启动时全部重放、从不冻结，也不读写快照）。

**归档。** 归档只是“移出默认视图”的标记：不改会话的状态与记录、不删除任何东西、随时可以取消。

- **什么能归档**：已结束的会话——阶段是已完成、失败、已取消、已关闭或已失联，并且没有待确认的消息。启动中、排队、运行中的当然不行，待命（`ready`）的也不行（它随时可能被继续用）。归档按子树：归档一个会话就是它和它所有下级一起归档，子树里只要有一个没结束，整棵都不归档（原因 `active`）。取消归档是该会话的整棵子树，加上仍处于归档状态的上级链（取消之后它不会脱离上级单独冒出来）。跟随多个上级的会话（汇聚）有几条上级链：它只有在**所有**上级都已归档、或都在这一次归档里时，才随上级一起走；还有上级留在画布上时它留在原处（不算失败，回执的 `kept` 如实列出它仍跟随着谁），免得一个仍在用的上级的下级凭空消失；“有没有没结束的”也只看真正会一起走的那些——留在原处的汇聚会话还在工作，不挡着上级归档（它没有被藏起来），会一起走的还在工作，则会带走它的那些上级都不归档（原因 `active`）；网页在点之前的预判（菜单里的“含 n 个下级”与不可用的原因、页头与多选的归档个数）读的是同一个范围（`archiveScopeOf`），服务端仍是权威；取消归档则沿它每一条上级链往回找，把仍处于归档状态的上级都带出来；子树里的会话不论经由几个上级走到、有几条路，都只算一次。规则只在 `src/shared/archive.ts` 的纯函数里有一份，HTTP、留存清扫与自动取消归档都走它。撤销刚才那次归档是另一回事：请求带 `exact: true`，只恢复那次回执里的 `changed`，不带下级、也不补上级链。
- **自动取消归档**：给已归档的会话 `send`；`delegate` 的 `follows`（或 `parentSessionId`、`parentSessionIds`；跟随多个会话时逐个取消）指向已归档的会话；已有会话被改挂到已归档的新上级——都意味着它又在用了，先连同它的上级链与子树取消归档。命中“重复委派”（返回已有会话、什么也不新建）本身不算又在用，返回的已有会话不会因此被取消归档；但 `follows` 指向的已归档上级是在判重之前取消归档的，这种情形下它照样会被取消。委派被拒绝（上级不存在、层数超限、引用的会话还在进行或不存在、服务正在关闭）时不会取消任何归档：这些检查都排在取消归档之前；取消归档要等一会儿，其间上级恰好被删或服务开始关闭的话，之后会再查一遍并拒绝，已经取消的归档不回滚。
- **HTTP**：

| 接口 | 说明 |
| --- | --- |
| `POST /api/sessions/archive` | 请求体 `{ "ids": ["ses_…"] }`（一次最多 2000 个），回 `{ "changed": [...], "skipped": [{ "id", "reason" }] }`；`reason` 是 `not_found`、`active`（子树里有没结束的）或 `already`；有汇聚的会话因还跟随着没有归档的上级而留下时，另有可选的 `kept: [{ "id", "follows": [...] }]`（`follows` 是它此刻没被一起归档的上级），没有这种情形就没有这个字段。每个 id 各有各的结局，整个请求只在格式不对时才失败 |
| `POST /api/sessions/unarchive` | 同上；`reason` 是 `not_found` 或 `not_archived`。可选 `exact: true`：只恢复点名的会话，不带上它们仍归档的下级与上级链（撤销刚才那次归档用）；不带或为 `false` 与原来一样；旧服务忽略这个字段；`exact` 不是布尔值时整个请求回 `400` |
| `GET /api/sessions` | 查询参数 `archived`：`exclude`（缺省，已归档的不出现）、`include`（全部）、`only`（只要已归档的）；写错的值回 `400` |
| `GET /api/state` | `sessions` 不含已归档的，多两个可选字段：`archivedCount` 与 `retention` |
| `GET /api/retention` / `PUT /api/retention` | 留存策略，见下 |

归档与取消归档会向所有页面推一条新的会话摘要（`archivedAt` 出现或消失）；摘要里 `archivedAt`、`archivedBy` 是新增的可选字段。这些写入口与其他写入口一样要令牌与同源检查。

**留存策略（默认关闭）。** 存在 `settings.json` 的顶层键 `retention`：`{ "keepDays": 30, "keepCount": null }`，`null` 表示这一项不限；没有这个键或两项都是 `null` 就是关闭。它只**归档**，永远不删除，被归档的会话标记为 `archivedBy: "retention"`。

- **规则**：`keepDays` — 整棵树都已结束、且最后活动（整棵树里最晚的更新时间）早于 N 天的根会话树归档；`keepCount` — 在未归档的根会话树里按最后活动由近到远排，只保留最近的 M 棵，其余已结束的归档。两项都设时满足任一项就归档。树里还有没结束的会话（含待命的）时整棵树都不会被归档，但仍占 `keepCount` 的名额。有汇聚的会话把几棵树连在一起时，按连通的任务图算：它们是一个整体，一起算最后活动、一起占一个名额、一起归档或一起保留（所以这里的“根会话树”就是“连通的任务图”）。
- **何时执行**：服务启动后（在重启对账之后）一次，之后每小时一次，以及 `PUT /api/retention` 保存之后立刻一次。几百棵树也不会卡住服务：规划是对内存里摘要的一次同步遍历，写盘按每批 25 棵、批与批之间让出事件循环，每批之前重新规划（两批之间又有动静的树不会被归档）。
- **取值**：`keepDays` 是 1–3650 的整数，`keepCount` 是 1–10000 的整数，或 `null`；`0`、负数、小数、过大的数与字符串都会被明确拒绝（`400 invalid_request`，说明是哪一项），不会悄悄取整。两个键都必须出现，省略不等于不限。文件里手写的不合格值按“关闭”处理，原值原样保留，直到在页面里重新保存。保存成两项都不限时删掉这个键。
- **接口**：`GET /api/retention` 与 `PUT /api/retention`（请求体 `{ "keepDays": 30, "keepCount": null }`）都回 `{ "retention": { "keepDays", "keepCount" }, "lastSweep"?: { "at", "archived" } }`；PUT 先落盘再立刻清扫一次，`archived` 是这次归档的会话数（含随根一起归档的后代，不是树的数量）。服务端没有为留存设置单独推送消息：其他标签页要刷新后才看得到改动。

**MCP。** 没有新工具；`status` 多一个可选参数 `includeArchived`（缺省 `false`）：默认不列已归档的会话，输出末尾一行写明略去了几个（`Not listed: N archived sessions …`，结构化结果里是 `archivedOmitted`）；点名的 `sessionIds` 一律返回，带 `(archived)` 标记；会话行与结构化结果里已归档的会话都有标记。`read` 与 `wait` 对已归档的、冷的会话照常工作，头部标 `(archived)`；`wait` 不传 `sessionIds` 时的默认范围不含已归档的（它们早已结束）。桥为此请求 `GET /api/sessions?archived=include`，再按 `archivedAt` 在本地过滤。

**兼容。** 没有提升 `PROTOCOL_VERSION`，新增的字段与参数都是可选的；`features` 里新增 `session-archive`。四种组合：
- 旧桥 + 新服务：照常工作，但旧桥不带 `archived` 参数，列表只含未归档的会话——旧桥的 `status` 点名一个已归档的会话会得到 “Not found”，`follows` 也认不到它（`read`、`send`、`wait` 直接按 id 请求，不受影响）；升级插件后恢复。
- 新桥 + 旧服务：旧服务不认识 `archived` 参数、返回全部，也没有归档这回事，`includeArchived` 没有效果，不报错。
- 老数据（没有 `summary.json`）+ 新服务：首次启动逐个重放并写快照，见上。
- 新数据 + 旧服务：旧服务忽略 `summary.json` 与 `archive.json`，照旧完整重放；已归档的会话在旧服务里照常出现。旧服务不会更新快照，下次新服务启动时发现字节数对不上，就退回完整重放并重写；若那个旧服务本身也写快照（格式 1，只可能出自升版前的中间构建），新服务因版本不符拒收它，同样完整重放。`settings.json` 里的 `retention` 也一样是旧服务不认识的键：旧服务若还不保留不认识的顶层键，在它那里改任何设置都会把它一并抹掉（留存策略变回关闭，已有的归档标记不受影响）。

**取舍与限制**（实现时的取舍，用户没有逐项确认）：
- 持有运行时连接的会话不会变冷：已经在页面或 MCP 里被继续过的会话，在连接断开 / 关闭之前一直占着内存，所以“本次服务生命周期内跑过的会话”不会被放出，只有启动时就已结束的历史会话是冷的。
- 待命（`ready`）的会话不能归档，也让它所在的树不被留存策略归档、还占着 `keepCount` 的名额。
- 留存策略不记得谁取消过归档：开着留存策略时，用户手动取消归档的一棵老会话树，只要还是已结束的、最后活动仍早于 `keepDays`（或仍排在 `keepCount` 之外），下一次清扫（每小时一次、改设置时、服务重启后）又会把它归档；它之后有了新的活动（比如被继续用了）就不会。要让“取消归档”对老会话持久，需要另外记一个“用户保留”的标记，目前没有做，是留给用户的一个决定。
- `keepCount` 数的是“未归档的根会话树”，不是会话个数；一棵树里带多少个会话都只占一个名额。
- 保温期 10 分钟、清扫间隔 60 秒、缓存 8 个 / 64 MB、留存每小时一次、每批 25 棵、一次最多 2000 个 id 都是实现时定的数值。
- 归档标记是一份会话目录里的 `archive.json`，而不是一条事件：不改 `updatedAt`、不需要载回会话、旧服务不受影响；代价是它不在事件日志里，也就没有“谁在什么时候取消了归档”的历史记录。
- 摘要快照里的摘要字段集合若变了（`SessionSummary` 加字段）而没有同步提高 `SNAPSHOT_FORMAT`，类型检查会失败（`src/server/snapshot.ts` 里的字段对照表）；这是有意的提醒。版本不符的快照不会被采信，只是让下一次启动慢一次。这条规则没有例外：连“只在特定情形才出现”的可选字段（例如只在汇聚时才有的 `parentSessionIds`），以及摘要里某个值的算法变了（例如投影里助手文字条目的键带上了运行标识，`lastAssistantPreview` 的取值可能随之不同），都要提高 `SNAPSHOT_FORMAT`。原因是快照不只有写它的那一版服务会读：装着不同版本插件的宿主会轮流起服务，旧版本重放后写出的快照缺字段（或带着旧算法的值），却和正常的快照长得一样，新服务分不出来，版本号是两边互相拒收对方快照的唯一办法。
- 写快照与归档标记失败（磁盘问题）时不丢数据：快照写不了，会话留在内存里；归档标记写不了，内存里的标记回滚并报错。残留的 `*.tmp` 临时文件可能存在，不影响读取。事件日志本身写失败过的会话（失败的那一批事件已经离开写缓冲、不会重试，日志里缺了它们而内存里有）在本进程内不再做快照、不会冻结，一直留在内存里；下次启动照日志重放，读到读不出的行或序号缺口时，会在时间线里补一条“日志不完整”的诊断，而不是被一份与日志对不上的快照当成完好的冷会话（缺的恰好是最后一批、什么残迹都没留下时，日志只是比内存里短，看不出来，也就没有这条诊断）。
- 归档与取消归档的标记，是在改内存的同一步里就交给存储落盘的（同一批里各会话的写同时发起，同一个文件的写与删仍按调用先后排队），所以两次重叠的操作在磁盘上的先后与内存一致，重启后不会与页面相反。

## 导出会话报告（Markdown）

把一个会话——或它名下的整棵任务树——一键导成一份干净的 Markdown：委派原文、关键步骤、改动文件清单、最终结果、用量。用来存档、贴进 PR 说明、发给别人复盘。**验证范围**：HTTP 与 MCP 两个入口在隔离的服务里验证过，也对着真实历史记录的一份副本导出过（那些真实会话全部成功导出，日志的哈希没变、没有解冻会话）：内容来自真实事件、没有编造，任务树、已归档与冷会话、提问、值得留意、多次运行、失败、中英文与多字节字符的边界、`maxChars` 截断与大日志的耗时都核对过。**没有验证**：浏览器里“导出”下载文件的逐字核对（只完整核对了少数几个下载文件）、Chrome 之外的浏览器、真实宿主里的端到端。这些验证早于之后的修复与拆分，改动后的代码只由 2026-11-24 最后一次完整运行（三份类型检查没有错误、完整测试没有失败）覆盖。

**真实性。** 报告里的每一句都是从已记录的事件里原文引用或计数得到的：不做摘要、不做推断、不让模型改写；做不到的事如实写出（没有最终回答、费用未上报、某处被截掉了多少字符），不编造成功的叙述。推理内容从不收录，文件 diff 也没有（事件里没有）。渲染是一个纯函数（入口是 `src/shared/report.ts`，具体写法按职责分在同目录的 `report-options.ts`〔范围、详细程度、语言与字符上限〕、`report-labels.ts`〔固定措辞〕、`report-markdown.ts`〔Markdown 原语〕、`report-facts.ts`〔从事件日志里整理事实〕、`report-steps.ts`〔过程里的各条步骤〕、`report-session.ts`〔单个会话的片段〕里；不读时钟、导出时刻由调用方传入、排序一律按字符串码元比较、不依赖 locale）：HTTP 路由、MCP 与网页共用这一份，同一个会话除导出时刻外得到的是同一份输出。

**HTTP：`GET /api/sessions/<id>/report`。** 与其他读取接口一样要令牌（请求头 `x-ensemble-token`，或查询参数 `token`）。查询参数都是可选的，写错了明确拒绝（`400 invalid_request`，消息里写明是哪个参数）而不是悄悄当成缺省值——误拼的 `detail=ful` 会让调用方以为拿到了完整版。

| 参数 | 取值（缺省） | 说明 |
| --- | --- | --- |
| `scope` | `session`（缺省）、`tree` | 只要这个会话自己；或连同它名下的整棵子树（含已归档的后代：归档只决定默认视图里看不看得见，不是数据的一部分） |
| `detail` | `brief`（缺省）、`full` | `brief` 只逐条列关键步骤、不收录工具输出；`full` 列出每一次工具调用、助手消息与诊断，并收录工具的输入与（截短的）输出 |
| `lang` | `en`（缺省）、`zh` | 只决定报告里固定标签的语言；引用的原文永远原样。网页按当前界面语言请求，MCP 一律用 `en` |
| `maxChars` | 整数 6000–2000000（缺省 2000000） | 输出的字符数上限；缺省等于不截断。低于 6000 被拒绝（再小连概览与页脚说明都放不下）；怎样放进上限见下面“长度上限” |
| `format` | `markdown`（缺省） | 目前只有这一个；写成别的（比如还没有的 `bundle`）得到 `400`，而不是悄悄回一份 Markdown |

成功回 `200`，`Content-Type: text/markdown; charset=utf-8`，`Content-Disposition: attachment; filename="<ASCII 名>"`（文件名含非 ASCII 字符时再加 `filename*=UTF-8''…`），`Cache-Control: no-store`。文件名是 `<标题>-<会话 id>[-tree][-full].md`：标题里不能出现在文件名里的字符折成连字符、最多保留 48 个字符（按码点，不会切开代理对），标题为空时写 `session`；会话 id 完整保留，主 Agent 可以直接拿去 `read`；树与完整版带后缀，同一个会话的几份导出不会重名。会话不存在回 `404 not_found`（先于参数校验）。路由**只读**：不写、不删、不改写任何会话记录（与读事件、读详情一样，对仍在输出的热会话，它先让已经收到、还停在合并缓冲里的那一小段流式文字落账，保证读到的是最新内容——那是会话自己的输出，不是导出产生的新记录）；冷的、已归档的会话读的就是磁盘上的事件日志（不载回内存，与热会话走同一条 `readEvents`），所以内容与归档前、冻结前一致。大树按会话逐个读取事件、读完一个就放掉，不会把整棵树的事件同时放进内存。

**MCP：`read` 的 `view="report"`。** 没有新工具。参数：`sessionId`（只接受单个会话；不能与 `sessionIds` 合用）、`scope`（`"session"` 缺省 / `"tree"`）、`detail`（`"brief"` 缺省 / `"full"`）、`maxChars`（沿用 `read` 的预算参数，缺省 12000，最大 40000；报告的下限是 6000，低于它时抬到 6000，并在输出末尾写明“要的是多少、实际用了多少”）。`runIndex`、`afterSeq`、`includeReasoning` 对报告没有意义（报告永远覆盖整个会话、从不含推理），一起传会得到明确的错误；`scope` 与 `detail` 只属于 `report`，配别的视角同样报错，而不是被悄悄忽略。输出就是服务端渲染的那份 Markdown（桥不改写、不加叙述，也没有 `cursor:` 行），用户干预通知照常附在最后；结构化结果是 `{ view: "report", sessionId, scope, detail, chars }`。语言固定为英文（MCP 的输出一律是英文）。桥用 `ServiceClient.request` 新增的 `as: "text"` 取正文——出错时服务回的仍是 JSON 错误体，业务错误照样带 `code`。

**报告里有什么**（每个会话一份，`brief` 与 `full` 都有）：

- **概览**：会话 id、状态、执行端、模型、推理档位、访问级别、工作目录、发起端（及它的工作区与对话标识的来历）、原生会话编号、上级、下级个数（`scope=session` 时注明“未包含，用 `scope=tree` 导出”）、创建 / 结束 / 最近活动时间（UTC）、运行时长合计、运行次数。
- **委派**：委派原文原样引用，以及随任务传入的上下文条目。
- **过程**：按运行分组。每次运行先写触发方式（委派 / 补充消息）、排队 / 开始 / 结束时间与停止原因，失败的运行写错误，被取消的运行写是谁取消的；然后是下面这些关键步骤（运行中的纠偏与补充消息连同投递状态、执行端的提问及它是怎样被回答或没被回答的，也在其中），没有被列出的按类别计数，写在步骤之后；再是这次运行结束时的计划。最后一次已开始的运行的回答放在“最终结果”里，更早的运行的回答放在各自的运行下面。不属于任何运行的东西（会话被停止、失败、失联）另列在“会话级事件”里。
- **改动文件清单**：来自执行端文件改动事件的去重路径，标注变更类型与被上报的次数；只有清单没有 diff；经由 shell 命令间接改动的文件不在其中。
- **最终结果**：最后一次已经开始的运行的最终回答原文。没有最终回答、运行失败、被取消、导出时仍在运行或排队，都如实写明——还在运行时，最新的一条助手文字标成“不是最终回答”。
- **用量**：每次运行一行（输入 / 输出 / 缓存 / 推理 token、费用、时长），多次运行有合计行；执行端没有上报的写“未上报”，合计只加总上报过的并标星，不把缺的当成 0。
- **生成说明**：来源与事件数、“没有任何摘要或推断”、关键步骤的挑选规则、从不收录什么、不做脱敏的提醒、时间一律是 UTC。

`brief` 的**关键步骤**由写死的规则挑出，不做“重要性”的判断：没有正常完成的工具调用（失败、取消、从未上报结束、导出时仍在运行）、退出码非 0 的、shell 命令、写 / 改文件类的、上报了文件改动的、MCP 调用；警告与错误级的诊断；纠偏与补充消息；执行端的提问。每次运行最多逐条列 40 步（取开头与结尾各一半，中间只计数）。助手的过程说明、普通的读 / 搜索类调用、info 级诊断只计数；推理只说明有多少段。`full` 列出全部，工具输入与其余引用块在 1500 个字符处截断，工具输出同样 1500（头尾各留一部分、中间写明省略了多少）。

**`scope=tree` 的组织。** 标题、概览（根会话、会话数与各状态个数、运行次数、运行时长合计、改动的不同路径数）、任务树（按层缩进的目录，每个会话一行：编号、标题、执行端、状态、时长、会话 id）、各会话的完整片段、整棵树的用量总表、生成说明。会话按先序展开，同一上级下按创建时间、再按会话 id 排；编号 `1`、`1.1`、`1.2`、`1.1.1`……与目录、正文、用量表里的一致。已归档的后代照样在里面，报告里没有“已归档”这一行。跟随多个上级的会话（汇聚）在树里只展开一次，放在它的上级里排在最前、又确实在这份报告里的那一个下面（通常就是第一个上级），它自己那一块的字段表里多一行“还跟随”，写出其余上级的标题与会话 id（上级不在这份报告里时也只写标题与 id、不展开；服务里已经找不到它时只写 id）；`scope=session` 的报告里这一行同样有。

**长度上限。** 给了 `maxChars` 就先扣掉头尾要占的篇幅，把余下的预算分给各会话；某个会话的片段放不下它那一份时，按固定的阶梯逐级收紧各类引用的上限（只完整展开最近的几次运行、更早的各留一行；步骤条数；长文本；其余引用；工具输出；文件清单），收紧过的会话在“过程”开头明文写出这些数字；最紧一级也放不下的非根会话整段略去，任务树目录里标出“未包含（超出大小限制）”并给总数；根会话总是要有的。最后还有一道只裁剪正文的安全网，按整行截断、补上没闭合的代码围栏，并在末尾写明被截断。任何一处缩减都是明文写在报告里的，不会悄悄发生；预算用完之后，后面的会话连事件都不再读取。每处引用也各有上限（`brief` / `full`）：委派原文与最终回答 3 万 / 10 万字符，补充消息、上下文条目与助手文字等其余块 600 / 1500，行内引用 240，改动文件最多列 200 / 2000 个路径，计划最多 40 条；超出的部分在原处写明被截掉了多少字符。

**不脱敏。** 委派原文、回答、消息、命令、路径与错误文本都是原样引用，没有做任何脱敏（控制字符显示为可见符号，所有引用放进围栏代码块，里面的 Markdown 与 HTML 不会漏出来影响版式）。事件里有什么，报告里就可能有什么：命令行里的令牌、路径里的用户名、工具输出里的密钥……转给别人、贴进公开的 PR 之前请先自己检查。`detail=full` 还会收录工具输出，更要小心。这里说的“不脱敏”只指导出这一步：个别文字在写进事件日志之前，执行端适配器已经遮过少数几种密钥形状（例如 OpenCode 的错误信息与 stderr、执行端提问的问题与可选项、提问转交的诊断），报告引用的是日志里的现状，不会还原，也不会再遮别的。

**兼容。** 没有提升 `PROTOCOL_VERSION`（仍是 1），所有新字段与参数都是可选的；`features` 里新增 `session-report`。新桥配旧服务：旧服务没有这条路由，桥看到 `features` 里没有它，就在不发请求的情况下直接说明“服务比插件旧、不能导出报告”并给出出路（改用别的视角，或请用户重启 Ensemble），不是撞一个 404；其余视角照常。万一请求是在桥查过 `features` 之后才撞上旧服务（发送时连接被拒绝或令牌被拒，重新发现落到了没有这条路由的旧服务；`read` 的 report 视角是只读请求，重新发现后原样重发），服务回 `404 not_found`、消息 `No route for GET /api/sessions/<id>/report.`。桥把这一类（消息以 `No route for ` 开头的 `not_found`）翻译成“运行中的服务很可能比插件旧、没有这个端点，请告诉用户把它重启到与插件相同的版本，在那之前重试没有用”，不再说“去 `status` 里核对会话编号”；其余 `not_found`（会话、提问、角色、执行端不存在，`details.via` 为 `"context"` 的那一支）措辞不变。旧桥配新服务：旧桥的 `view` 取值里没有 `report`，不会用到它，没有影响。

**没有做。** **Bundle**（把 `report.md`、各会话的 `events.jsonl` 与摘要 JSON 打成 zip，即 `format=bundle`）：路由现在对它回明确的 `400`。原因：事件中枢只交出解析后的事件，没有“原始日志文件”的读取口；冷热分离与归档的存储布局另有人在改，在它上面再加一条直接读文件的路径，最容易在存储改动时悄悄坏掉。网页里的“复制为 Markdown”也没有做（网页只有下载）。

**取舍**（实现时的取舍，用户没有逐项确认）：不脱敏，而不是遮掉看起来像密钥的内容（遮挡规则漏一次就是假的安全感）；`brief` 缺省不收录工具输出；关键步骤的挑选规则与上面所有数值（40 步、各类字符上限、最小 `maxChars` 6000、每个会话至少 1500 字符预算才展开、任务树目录最多占预算的四分之一）；`brief` 里也逐条列出执行端的提问（量少、都是决定性的事实）；任务树按先序展开、含已归档的后代；时间一律是 UTC；`maxChars` 缺省不截断，MCP 的缺省是 12000；`lang` 只翻译固定标签；MCP 不能一次导出多个会话（要多份就各调一次）。

## 数据与隐私

- 服务只监听 `127.0.0.1`；`/api/*` 需要令牌（写在状态目录的 `run/service.json` 里），页面由服务直接下发。
- 所有数据都在 `ENSEMBLE_HOME` 下：`data/sessions/<会话>/events.jsonl`（按会话追加的事件记录，是页面与 MCP 的唯一事实来源；同目录里还可能有两份派生文件 `summary.json` 与 `archive.json`，见“历史会话”一节）、`settings.json`（见下一条）、`logs/`、`run/`、`runtime/`。
- 执行端的提问写在同一份事件记录里（`question.asked` / `question.resolved`），没有单独的存储文件，随会话一起保留、归档与删除：问题与可选项经脱敏与长度上限处理后记下（Codex 标了机密的提问不记）；回答与备注是用户或主 Agent 写下的原文，**不做脱敏**（它们是任务内容本身，你在页面里自己输入的敏感内容也会原样落盘），连同回答者、时间、投递状态与过期原因一起记录。
- 设置窗口「执行端」分区里勾选的模型存在 `settings.json`（`{ "version": 1, "harnesses": { "<执行端>": { "allowedModels": [...] } } }`）：各宿主共用，重启后保留。逐项勾选只开放名单中的模型；点「全部开放」也允许以后新增的模型；空名单不接受新委派。有限制时，服务会在创建会话时固定实际选用的模型，名单外的请求会得到 `model_not_allowed`。每个执行端还可以指定一个默认模型（`userDefaultModel`，与 `allowedModels` 同级，缺省即不指定）：主 Agent 不写 `model` 时用它，`harnesses` 会写明它是用户指定的；它必须是主 Agent 能选用的模型（有限制时在名单里，不设限时是执行端目录里的模型），保存时越界会被拒绝；取消勾选它、清空名单或名单不再含它时，指定在同一次写入里被清掉，网页就地说明现在用哪个，「全部开放」则保留。手改文件造成的失效（执行端已不再提供它，或没被开放）不报错，服务退回没有指定时的规则，设置页与 `harnesses` 写明失效的是哪个、为什么；“不设限”与“空名单不接受委派”的规则不受影响，防重复判断看到的也是固定下来的同一个模型。单个执行端的名单损坏时，其他名单照常生效，损坏的名单可在页面重新选择。整个文件无法读取时会留在原处，暂不接受新委派或改写设置；可先修复文件，再重启服务。历史会话仍然可查看。
- 设置窗口「通用」分区里指定的并发上限存在 `settings.json` 的顶层键 `maxConcurrentRuns`（与 `harnesses` 同级，例如 `{ "version": 1, "harnesses": {}, "maxConcurrentRuns": 8 }`）：1–1000 的正整数，或字符串 `"unlimited"`（不设上限）。没有这个键就是没指定，回落到环境变量 `ENSEMBLE_MAX_CONCURRENT_RUNS`，再回落到内置默认 20；“恢复默认”就是删掉这个键。写入成功之后才生效并推给所有页面。文件里写了但不合格的值（负数、小数、`0`、字符串形式的数字、超出范围）按“没指定”处理：服务照常启动，文件原样保留、不会被悄悄改写——改别的设置时它也随整份文件原样写回——页面如实写明“文件里的值无效，现在用的是 …”，直到你在页面里重新设置或点“恢复默认”才被覆盖；整个文件读不出来时，上限落回环境变量 / 默认，页面上也暂时不能改（见上一条）。这项设置只能在网页里改，MCP 没有对应的工具：写入口是 `PUT /api/settings/concurrency`（请求体 `{"max": 8}`、`{"max": "unlimited"}` 或 `{"max": null}`，最后一种清掉指定；与其他写入口一样要令牌与同源检查，落盘成功之后新上限已在服务里生效）；`GET /api/state` 的快照里多一个可选的 `concurrency`（来源、用户存的值、恢复默认会落到的值与文件里的问题），SSE 多一种 `capacity` 消息（名额的占用 / 等待与这项设置成对给，内容没变不发），不认识它们的老页面、老桥照常工作（没有提升 `PROTOCOL_VERSION`）。更早、还不保留未知顶层键的服务版本若重写了 `settings.json`，会把这个键一并抹掉。
- 已开放且目录报告了推理强度的模型，可以展开「强度」多选允许的档位。设置按模型 ID 记录在 `allowedEfforts`，网页、MCP 和委派入口共用。点「取消档位限制」才恢复执行端的原生行为，勾满当前档位仍保留名单。有名单时，服务在委派入队前固定允许的档位：省略档位先用名单内的原生默认，否则用第一个允许的档位。
- 设置窗口「角色」分区里定义的角色存在 `settings.json` 的顶层键 `profiles`（与 `harnesses` 同级，`version` 仍是 1）：键是角色名，值是它固定的取值，例如 `{ "version": 1, "profiles": { "verify": { "harness": "codex", "model": "<模型 id>", "effort": "high", "access": "read_only" }, "scout": { "harness": "pi" } } }`。`harness` 必填；`model`、`effort`、`access`（`"full"` 或 `"read_only"`）可省，省略就是“不固定”，委派时照原有规则走（见“委派角色”）。没有“说明”之类的字段，也不预置任何角色，没有这个键就是没有角色。名称 1–24 个字符，只用小写字母、数字、`-`、`_`，以字母或数字开头，不能全是数字（最后这条是实现时加的，用户没提：JSON 对象遍历时整数形的键永远排在最前面，全数字的名字会让“按创建顺序保留”失效）；存下来的名称一律是小写，查找时对大小写与首尾空白宽容，`constructor`、`__proto__` 之类的名字也照常可用。最多 20 个，顺序就是创建顺序（改名保持原位）。写入由服务端统一做，每次只动一个角色、从不整表覆盖；模型开放、角色、并发上限、留存四类设置共用同一个排队与提交点（同一时刻只有一次写，轮到自己时取内存里最近一次落盘的整份设置、不重新读盘；服务运行期间手改 `settings.json` 本进程看不到，下一次写入会把内存里的整份写回、盖掉手改的内容，所以手改请在服务停止时做）：先写临时文件再改名替换，落盘成功之后才在服务里生效并通知订阅者（角色的变化会推给所有页面；留存没有订阅者），写失败时内存里的设置不变；内容没变的写入不落盘、不通知；其他顶层键与条目里这一版不认识的字段原样写回。手改文件造成的问题不挡启动，也不会被悄悄改写：名称不合规的条目、内容读不出来的条目照样列在页面里并标为无效，主 Agent 引用不到它们，用户可以在页面里改名、重新选执行端或删除；执行端这一版不认识的角色保留并标为暂时不可用；整个文件读不出来时，角色列表是“不可用”（不是“没有角色”），文件原样留着，页面上也不能改角色。写入口：`PUT /api/profiles/<名称>`（请求体 `{"harness": "codex", "model": "…", "effort": "high", "access": "read_only"}`，整条改写，没给的字段就是不固定、会被去掉；`"create": true` 时名称已存在就拒绝，网页的“新增”用它，两个标签页同时用同一个名称新增时后到的不会悄悄覆盖先到的；名称不合规、执行端 id 不是这台服务启用的、新增超过 20 个都拒绝，手改文件已超过上限的仍可改可删）、`DELETE /api/profiles/<名称>`（删除不存在的角色不算错，也不写盘）与 `POST /api/profiles/<名称>/rename`（请求体 `{"to": "新名称"}`，保持原位；原名称不存在返回 404 `not_found`（`details.name` 是请求里写的名称），新名称不合规或已被占用返回 400 `invalid_request`），回执都是 `{ "profiles": { "entries": [...] } }`（生效后的整张角色表）；与其他写入口一样要令牌与同源检查。`GET /api/harnesses` 的返回里多一个 `profiles`（每个角色带此刻能不能用的评估），`GET /api/state` 的快照里多一个 `profiles`（整张表），SSE 多一种 `profiles` 消息（整张表）；`POST /api/sessions` 的请求体多一个可选的 `profile`、`harness` 变为可选（二者至少给一个），回执里多一个 `profile`（这次用了哪个角色、每个字段取自哪里）。更早、还不保留未知顶层键的服务版本若重写了 `settings.json`，会把 `profiles` 一并抹掉。
- 如果崩溃留下写到一半的事件，重启会把它和新事件隔开；已有的历史缺失会在时间线里标明。
- 事件记录里有委派原文、传入的上下文、工具调用的输入输出预览（有长度上限，超出会标记截断）和文件路径——这些可能包含项目内容。需要清理时在页面上删除记录，或删除对应目录。
- 导出的 Markdown 报告（“导出会话报告”一节）是从这些记录里原样引用的，**不做脱敏**：命令行里的令牌、路径里的用户名、工具输出里的密钥，事件里有什么报告里就可能有什么。导出本身只读、不改动任何记录，也不会自己发到别处；转给别人或贴进公开的 PR 之前请先自己检查，`detail=full` 还会收录工具输出。通过 MCP 的 `read` 取到的报告，内容同样会进入发起端那个 Agent 的上下文。
- `logs/origin-debug.jsonl` 记录宿主在 MCP 调用里给出的识别线索（客户端名、`_meta` 字段、环境变量**名字**，不含值，密钥类字段会被遮蔽），用于排查“由谁派发”的识别问题；数量有上限。
- 委派时，桥会只读地查一次发起端宿主给**这段对话起的标题**，显示在画布的来源卡片上并随会话记录保存：Codex 读 `<CODEX_HOME 或 ~/.codex>/session_index.jsonl`，Cursor 读它本机的 `state.vscdb`（只按对话 ID 取这一行里的标题和所在工作区两个字段，不碰对话内容；工作区只用于来源卡的目录，见“Folder 节点”一条，这一取法还没有在真实的 Cursor 里端到端试过），Claude Code 读 `~/.claude/projects/` 下该会话记录文件里的 `custom-title` 行（会话 ID 取自它交给 MCP 进程的环境变量 `CLAUDE_CODE_SESSION_ID`，精确匹配），Pi 读 `~/.pi/agent/sessions/` 里的 `session_info` 行（`pi --name` 或 `/name` 起的名）。读不到就不显示，其他宿主不读，没起过名的对话也不会用第一句话或占位文案顶替。Agent 自报的对话标识（见“按对话区分 Main Agent”）只用于 Cursor 的这一条查找；Codex 与 Claude Code 只读宿主自己交出的标识，不拿自报的去匹配它们的记录文件。2026-11-17 对 Cursor 核对过一次：用户给出的一个对话 UUID（`<UUID>`）在本机 `state.vscdb` 的 `composerHeaders` 里有对应的一行，能读出标题（只读了这一行的 `name` 字段）。样本只有这一个，所以“Agent 上下文里看到的 UUID 就是 `composerId`”只在这个例子里得到印证，新建、分叉、重开的对话没有逐一核对；对不上时只是读不到标题，卡片上不显示。Pi 是例外：它没有把会话标识交给 MCP 进程（环境变量与 `_meta` 里都没有），只能按工作目录找最近写过的会话文件，所以同一目录下另一个会话 2 分钟内也写过、或最新的文件已超过 5 分钟没写过时宁可不显示；极少数情况下（同目录另一个会话恰好在本会话最后一次落盘之后写了盘，而本会话此前已安静超过 2 分钟）仍可能认错。Claude Code（2.1.325）与 Pi（1.5.2）这两条于 2026-11-14 用真实进程核对过：经构建好的桥委派后，服务里记下的来源与标题都对；没有覆盖的是 Claude Code 交互界面里的 `/rename` 是否同样写 `custom-title`。这些都是各宿主的内部存储，格式随版本可能变化。
- 画布上的 Git 节点由服务对来源的工作目录运行只读的 `git` 命令得到：带 `--no-optional-locks`，并关掉仓库配置里可能执行外部命令的 `core.fsmonitor`；不会 fetch、不联网、不修改仓库。读取的是当前分支、HEAD 提交的说明与时间、`git status` 的计数和远程地址（显示前会去掉地址里的账号口令）。`GET /api/git` 只对已经出现在 Ensemble 里的来源或会话工作目录响应，不会为任意路径读取；结果只在内存里短暂缓存，不写进事件记录。
- Ensemble 没有遥测，不会主动联网；联网的只有各执行端自己（它们本来就要访问各自的模型服务）。
- Ensemble 不读取、不转存各 Harness 的登录凭据：Codex、Pi 与 Claude Code 用它们自己的登录；Cursor 通过 SDK 自己的凭据存储或 `CURSOR_API_KEY`；OpenCode 的登录、`auth.json` 与 `opencode.json` 里的密钥由 OpenCode 自己读取，Ensemble 既不读也不保存，从 OpenCode 模型目录里取模型信息时带凭据的设置字段也从不拷贝（只取模型名、提供商、档位与上下文窗口）；DSH 的 DeepSeek 凭据（在 `dsh web` 的 Settings → Models 里填的，或环境变量 `DEEPSEEK_API_KEY`）由 dsh 自己读取，Ensemble 既不读也不保存，不会去碰 `$DSH_HOME` 下的凭据文件，模型信息只取 dsh 的 ACP 配置选项里的模型名、提供商与推理档位。

目录结构：`src/shared`（领域类型、事件、投递状态机、投影，服务端与网页共用）、`src/server`（事件中枢、会话管理、各执行端适配器、HTTP/SSE 服务）、`src/mcp`（MCP 桥）、`src/cli`（命令行与安装器）、`src/web`（React 界面）、`skills/`、`assets/`。

执行端适配器统一实现 `Executor` 接口（探测 / 打开会话 / 开始运行 / 纠偏 / 取消 / 关闭）。Cursor 执行端的 `open()` 经过 Driver Kernel（`src/server/driver`、`vendor/mosoo-agent-driver`）；Codex、Pi、Claude Code、OpenCode 和 DSH 直接对接各自的控制接口（Codex 的适配器拆成 `codex.ts`〔执行端与会话〕、`codex-setup.ts`〔能力声明与握手：能力表、访问级别说明、超时、`initialize`、模型目录与账号标签的查询〕、`codex-item-flow.ts`〔条目、计划与用量到统一事件的转换，回合结束与会话关闭时清理它的状态〕、`codex-items.ts`〔app-server 的条目、用量、错误到统一事件的纯函数映射，另含访问级别对应的沙箱与模型条目的解析〕、`codex-rpc.ts`〔app-server 的启动方式定位与 stdio 上的 JSON-RPC 传输〕、`codex-side-channel.ts`〔回合与条目之外的旁路消息：只需变成诊断的通知，以及授权、提问、征询这几类服务端请求的分派与应答〕，业务提问的转交在 `codex-questions.ts`（见下一段）；OpenCode 的适配器拆成 `opencode.ts` 接口层与 `opencode-events.ts` 事件映射等文件；DSH 的拆成 `dsh.ts`〔会话与运行〕、`dsh-rpc.ts`〔JSON-RPC 连接〕、`dsh-events.ts`〔事件映射〕、`dsh-launch.ts`〔查找与启动环境〕、`dsh-probe.ts`〔探测〕，取消后清理孤儿进程的逻辑在 `process-tree.ts`；Linux / macOS 的读进程表在 `process-list.ts`，结束整棵进程树的冻结收敛在 `process-kill.ts`，`killTree` 本身仍在 `process.ts`）。

执行端的提问（见“子会话的提问”）：共用的类型、固定用语、长度上限与回答核对在 `src/shared/questions.ts`，服务端的登记、回复与过期在 `src/server/questions.ts`（`QuestionDesk`），两个适配器的转交在 `src/server/executors/codex-questions.ts` 与 `opencode-questions.ts`（`ExecutorSession` 上可选的 `answerQuestion` / `declineQuestion` 加能力项 `capabilities.question`；不接收回复的执行端只记录过期），MCP 的呈现在 `src/mcp/format-questions.ts`，网页是 `QuestionCard.tsx` 与 `lib/question.ts`。这部分的测试都写好了：文件名里带 `question` 的那些（共用逻辑、`QuestionDesk` 及其超时、HTTP、MCP、两个适配器与网页组件各一层），以及对着假 Codex / 假 OpenCode（`test/fixtures`）的 `codex.questions.test.ts`、`opencode.test.ts`，还有覆盖转交退回老办法时那条诊断的 `codex-side-channel.test.ts`。它们在 2026-11-24 最后一次完整运行（三份类型检查没有错误、完整测试没有失败）里通过；对着的都是模拟的执行端，没有对真实的 Codex 或 OpenCode 跑过。

`SessionManager` 负责委派准入和查找会话；每条原生连接对应一个 `SessionRuntime`，统一处理运行、队列、取消和执行端回执。一次转换里的事件全部写入投影后，才通知 `wait` 和实时推送。执行端报告的 `run.started` 与 Ensemble 自己分配到运行名额时的 `run.starting` 分开记录。

“值得留意”由 `AttentionSupervisor`（`src/server/supervisor.ts`）计算：它订阅事件中枢，记录各会话上报的文件写入，每 10 秒（以及事件到来后 1 秒内）重算一次，把结果挂到会话摘要的 `attention` 上，只有变化时才通知。判断规则在 `src/shared/attention.ts`，阈值在 `LIMITS.attention`，目前是固定值、不可配置。`long_tool` 与 `quiet` 都按**静默时长**判断（运行中的工具调用后面仍在持续来事件时不算），所以执行端漏发“工具完成”事件造成的悬挂条目不会误报。`wait` 把“开始等待那一刻已经存在的提示”当作基线，只有之后新出现的才会提前返回，不为每个调用方单独记账；已存在的提示仍会作为 `attention:` 行列在会话下面。提问是例外：它不进基线，而是按“这个来源是否已被告知过这个提问”判断（见“子会话的提问”）。

看门狗脚本（`skills/ensemble-delegate/scripts/watch.mjs`）是纯 ESM、无依赖的独立文件，要能脱离本仓库运行（它随 `skills/` 被安装器原样复制，不经过 `scripts/build.mjs`，也不进 `dist/ensemble.mjs`），所以它自己带了几份与应用同口径的小拷贝：`formatDuration`、`sliceHead` / `sliceTail`（与 `src/shared/safe-slice.ts` 同一语义）、`clip` / `shortenPath`、`harnessLabel`、`isSettled`（对应应用里的 `isSessionSettled`）、`attentionKey` 与 `describeAttention` 的措辞、`resolveHome`。这些拷贝由 `test/watch-script.copies.test.ts` 与 `test/watch-wake.test.ts` 逐项对照应用里的实现（后者含 emoji 逐刀对照；`SessionPhase` 与 `AttentionKind` 各多一个取值，对照测试也会红，提醒去教脚本）。脚本里的判断逻辑都是时间由参数传入的纯函数（`test/watch-script.test.ts`）；巡检用可替换的读取函数驱动（`test/watch-script.pass.test.ts`），所以测试不等真实时间。测试夹具在 `test/watch-script.fixtures.ts`（值得留意的样本放在 `test/watch-script.shared.fixtures.ts`），唤醒、状态文件与来源过滤的新测试在 `test/watch-wake.test.ts`：合并窗口与时钟都走注入的 `sleep` / `now`，不等真实时间。

## 已知限制

- Cursor 执行端已在 2026-11-14 经 Ensemble 完成一次真实只读任务；纠偏、取消、恢复和只读强制仍需分别以真实账号验证。
- Claude Code 的模型名称是常见别名或用户配置值，不代表当前账号或模型服务一定可用；嵌套子 Agent 的事件目前不会被误当作主会话事件展示。
- OpenCode 的模型清单来自它自己的目录，列出来不代表当前账号一定能调用；私有服务会加载你自己的 OpenCode 配置（其中的插件与 MCP 服务会随每个会话各起一份），这一点没有在你的真实配置下核对过。
- DSH 是开发者预览版（本机验证的是 0.2.2-rc.1，npm 上目前只有预发布版本）：协议与行为可能随版本变化，换版本后需要重新验证。它的模型清单来自它自己的 acp profile，列出来不代表你配好的凭据一定能调用；本机没有 DeepSeek 凭据，真实的 DeepSeek 模型没有跑过（只用脚本化的假模型端点验证过），所以真实模型下的首次响应耗时、用量口径与真实的 429 / 5xx 重试表现都没有核对。dsh 一次只收一个 prompt，运行中的纠偏只能排到这一轮结束后；第一次模型调用返回之前它不发任何事件，页面会一直显示“正在连接”。取消后留下的孤儿进程：Windows 上已验证会清理；Linux 与 macOS 已实现、没有在真实系统上验证过；其它系统（BSD、Solaris、AIX 等）不清理，也不声称做了。
- “结束整棵进程树”（OpenCode 取消与关闭时的 shell 工具、dsh 运行中的关闭、执行端子进程的最后一步关闭、命令超时）靠沿父子关系找后代：Windows 上是 `taskkill /T`（已验证），Linux 与 macOS 上是 `process-kill.ts` 的冻结收敛（已实现、没有在真实系统上验证过）。共同的边界：已经脱离父子关系的进程（先 fork 再让父进程退出、被 init 收养的守护进程）只有在取消前拍过快照的路径（目前只有 dsh）里才找得到，其余路径找不到它们；Linux 与 macOS 上执行端没有被放进自己的进程组（没有改 spawn 的方式——那样可以 `kill(-pgid)` 一次结束整组、没有 fork 竞态，但会改变 Ctrl+C 与服务崩溃时的行为，逃出进程组的守护进程也照样漏掉，是否改留给你决定），所以靠冻结而不是进程组。BSD、Solaris、AIX 等系统读不了进程表，`killTree` 在那里只对这一个进程发信号（取消、关闭与超时路径直接强制，不再先发 SIGTERM 等 1.5 秒；执行端进程自己的关闭仍保留那一步），也不会声称结束了整棵树。Pi 与 Codex 的取消走各自的控制接口，没有做进程树清理，它们的工具子进程在取消后会不会留下也没有调查过（关闭整个会话时才会结束整棵树）。
- 完全访问没有任何执行端强制的沙箱：被委派的会话能碰到这个系统用户能碰到的一切，所以任务说明里要把边界写清楚；需要“只读”时请显式声明。
- 以斜杠开头的任务文本会被 Pi 当成命令解释。
- Codex 会话里由执行端自己发起的、不是 Ensemble 请求的回合不会被追踪。
- 执行端的提问只有 Codex（`item/tool/requestUserInput`）与 OpenCode（`question`）会转交，而且只对着模拟的执行端验证过，没有在真实的 Codex 或 OpenCode 上触发过；Claude Code、Cursor、Pi、DSH 的提问没有转交（调查结果见“子会话的提问”一节末尾），它们遇到歧义时由执行端自己决定怎么办。Codex 的 MCP 服务器表单（`mcpServer/elicitation/request`）仍然取消。旧桥（没升级的插件）看不到提问：它发起的会话遇到提问要等一小时的超时兜底，除非用户在网页里回答。回答是否被执行端读到并采纳，Ensemble 只能说“已交给执行端”。
- 全局并发运行数上限默认为 20，只是安全阀：常规使用里派发的会话都会立即开始；超出时会话不会被拒绝，而是如实排队（显示为“等待并发名额”），有名额释放后先到先得。这时 `delegate` 的回执首句也如实写成排队：`Delegated to <Harness> — session <id>, run <id>. It is queued: the concurrent-run limit is full, so it starts when a slot frees up. You do not need to poll.`，其余阶段仍是 `It is working in the background; you do not need to poll.`（回执首句的这处改动与测试〔`src/mcp/bridge.queued.test.ts`、`src/mcp/delegate-output.test.ts`〕在 2026-11-24 最后一次完整运行里通过）。上限有三个来源，按优先级取：设置窗口「通用」分区里指定的（存在 `settings.json` 的 `maxConcurrentRuns`，各宿主与页面共用）＞ 环境变量 `ENSEMBLE_MAX_CONCURRENT_RUNS` ＞ 内置默认 20。在设置里改了立即生效，不必重启服务：调高时排队的会话按先到先得马上开始；调低不会中断任何运行中的会话——占用数可以暂时高于新上限，新委派排队，名额随会话结束逐渐收回。环境变量现在只是“没在设置里指定过”时的初始值：正整数为上限，`0` 或 `unlimited` 表示不设上限，写错（空串、负数、小数、非数字）时回到默认的 20，只在服务日志里记一行警告、不挡启动；它在启动服务的进程环境里读取，改动后要重启服务才有变化，并且一旦在设置里指定过就以设置为准，点“恢复默认”之后才回到它。设置里的取值是 1–1000 的整数或“不限制”（环境变量仍可写任意正整数）。服务日志里 `service started` 一行写明生效的上限与来源（`maxConcurrentRuns`、`maxConcurrentRunsSource`），之后每次真的改了上限记一行 `concurrency limit changed`（旧值、新值、来源、占用、等待）；委派嵌套深度上限为 2（跟随多个会话时取最长的那条上级链；被委派的会话再委派时，桥先看环境变量 `ENSEMBLE_PARENT_SESSION`——Codex、Pi、Claude Code、OpenCode、DSH 执行端会写入，Cursor 执行端没有——再用宿主会话标识去匹配已知会话，把它挂到父会话下——Agent 自报的 `conversationId` 不参与这次匹配，因为它无法核对，需要连线时请用 `follows`；宿主若过滤了子进程环境则只能尽力而为）。
- “值得留意”只做通用判断：服务本身不检查项目自己的规矩（例如不该改哪些目录、不该读哪些文件；想检查的话交给随 Skill 分发的看门狗脚本的 `--rules`，见上文），也不扫描残留进程或校验文件完整性——这两样脚本也没有。文件重叠只统计执行端明确报告的文件变更，通过 shell 命令写入的看不到；路径比较在 Windows 与 macOS 上不区分大小写，相对路径按会话的工作目录解析。长时间静默可能是一次正常的构建或测试，所以提示的措辞只陈述事实，由主 Agent 或用户读过过程记录后判断。

- 已有的卡原地不动之后，相机仍按宽度取景（见“画布排布与重置”里的“仍放不下才缩小”）：页面缩放可以比“全部节点入画”大得多，下面的卡留在画面外，要平移（或点边缘提示）才看得到。在隔离服务加无头 Chrome 里测得：把一块真实画布的 59 个会话按到达顺序逐个放进去，窗口 1440×900 时终局页面缩放 55.7%、全部入画要 29.3%，16 张卡完全在画面外、5 张局部露出，底边有一枚“↓ 16”的提示；同一批会话刷新后是 49% 的整齐方阵、全部可见。真机没测。
- 一个个到达的画布与同一批会话刷新后的画布不一样：已有的卡不动，所以到达顺序会留在排布里，缩放也可能比刷新后低。在隔离服务加无头 Chrome 里用 14 波、33 个并行子会话的夹具测得，逐个到达的终局页面缩放在 1440×900 是 56%（刷新后 67%）、1920×1080 是 80%（95%）、1280×720 是 48%（56%）；先载入一批会话再追加的 9 组里，点“重置节点布局”后与刷新后的排布逐卡相同。真机没测。
- 竖屏与很窄的取景区域里，根会话一个个到达时仍排成一列：在隔离服务加无头 Chrome 里测得，832×1234 的窗口里 3~8 个根会话、328×740 的窗口里 3~5 个根会话都是一条竖列（8 个时单列 94%，同一批刷新后排成两列是 100%）；单列在窄长的取景区域里本来更装得下，要不要在这里也换成多列没有定。真机没测。
- 拖动过节点之后刷新页面：被拖过的卡保留手动位置，其余的卡按新排出来的默认排布走，所以有一部分卡会挪位、个别卡可能与手动摆放的卡重叠，目前没有处理。在隔离服务加无头 Chrome 里测得，19 张卡里有 9~10 张移位（最大约 851px）、2~3 处卡与卡重叠（没有逐处查是哪几张）、页面缩放从 100% 到 90%；真机没测。
- 开着“仅工作中”时，两个早就见过的会话在相邻的两次渲染里先后回到画面（例如先后给两个已经离开画面的会话各发一条补充消息），第二个回来的会拿最早那份只有几个节点的小排布去还原，已有的卡整张画布挪位，与“已有的卡原地不动”不符，目前没有处理。在隔离服务加无头 Chrome 里这样复现出 11 张卡全部移位（最大约 644px）；“隐藏相关节点”后再显示走的是同一条还原路径，没有用它复现过这个两次渲染的情形；两个会话在同一次渲染里一起回来的那一例（另测的一例与对应的单元测试）没有这个现象。现实里有多常见没有量过。
- 节点数很多时页面本身会卡：在隔离服务加无头 Chrome 里测得，400 个节点的画布（其中 10 个在工作）上关掉“仅工作中”、把收起的会话全部显示回来，主线程阻塞约 7~8 秒，1000 个节点约 50 秒；交替对照了一份较早的副本，读数相同，据此判断主要是一次渲染这么多卡片的代价，而不是排布算法的耗时（这是推断）。真机没测。
- Git 节点是定期刷新的快照：两次读取之间的改动要等下一次才看得到；超大仓库上 `git status` 可能超过 8 秒，这时保留上一次的结果并标为旧状态。工作目录若是某个工作树里的子目录，按这个工作树的根目录合并（头部显示根目录名，悬停提示里是完整路径）；裸仓库或 `.git` 目录内部没有工作区，不画节点。
- Folder 节点是在 Git 节点之后加的。升级后第一次出现的 Folder 节点放在它的来源旁边；如果你此前把来源和 Git 节点都拖到过别处（位置已保存），这张新卡可能压在 Git 节点上，把它拖开即可，已保存的 Git 节点位置不会被改动。Folder 节点按路径字符串合并，不读文件系统：指向同一个真实目录的不同别名（`subst` 盘、junction、8.3 短名）会被当成不同的目录，各画一张。
- 宿主退出时服务的存活取决于宿主如何清理子进程（见上文“服务寿命”）。你已确认这在预期之内、不额外做常驻；需要常驻时自己运行 `serve`。
- 历史会话的冷热分离、归档与留存有自己的取舍与限制（持有运行时连接的会话不会变冷、旧桥看不到已归档的会话、留存设置在其他标签页不实时同步等），见“历史会话”一节末尾；那一节只在隔离的服务（含一份真实历史记录的副本）与无头 Chrome 里验证过，没有在真实宿主里试过，验证早于之后的修复与拆分，范围见那一节开头的“验证范围”。
- 导出会话报告（Markdown）：不脱敏、没有 Bundle（zip）、没有“复制为 Markdown”；关键步骤的挑选规则与各处字符上限是实现时的取舍；新桥配旧服务时 MCP 的 `report` 视角不可用（如实说明，不是报错到 404）；那一节只在隔离的服务（含一份真实历史记录的副本）里验证过，浏览器里导出的下载文件没有逐字核对，没有在真实宿主里试过，验证早于之后的修复与拆分，范围见那一节开头的“验证范围”。详见“导出会话报告（Markdown）”一节。
